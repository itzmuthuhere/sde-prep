1 · 1D & 2D Arrays

An array is a fixed block of contiguous memory, so a[i] is O(1): the JVM computes base + i · elementSize directly. A 2D array in Java is really an array of arrays — int[][] g = new int[rows][cols] allocates one outer array of references, each pointing at its own row. That means rows can have different lengths (a jagged array), g.length is the row count and g[i].length is that row's column count. Logically, though, you address a grid as g[row][col] and iterate rows in the outer loop, columns in the inner.

The dominant pattern for arrays is the prefix sum: precompute pre[i+1] = pre[i] + a[i] once, and then the sum of any range a[l..r] is pre[r+1] - pre[l] in O(1). This turns "answer Q range-sum queries" from O(Q·n) into O(n + Q), and it composes: paired with a hash map it answers "how many subarrays sum to k"; extended to two dimensions it answers "sum of any sub-rectangle". Its cousin, the difference array, does the reverse — O(1) range updates, one final pass to materialise the result.

The other array staples are in-place techniques (reversing, rotating, partitioning without an auxiliary array — O(1) extra space), and structured 2D traversals (row-major, column-major, diagonal, spiral, boundary). Almost every "matrix" interview problem is a disciplined double loop where the trick is expressing the second index as a function of the first.

Core intuition

If a brute force re-scans a stretch of the array for every query or every starting index, ask: "can I precompute a table so each answer is a subtraction?" For grids: fix which index the outer loop owns, then write every other index as an expression in it — don't try to picture the whole traversal at once.

Worked example — prefix sums for range-sum queries

public class PrefixSum {
    public static void main(String[] args) {
        int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
        int n = a.length;

        long[] pre = new long[n + 1];            // pre[0] = 0; long guards overflow
        for (int i = 0; i < n; i++)
            pre[i + 1] = pre[i] + a[i];

        // sum of a[l..r] inclusive = pre[r + 1] - pre[l]
        System.out.println(rangeSum(pre, 2, 5)); // 4 + 1 + 5 + 9 = 19
        System.out.println(rangeSum(pre, 0, 7)); // whole array   = 31
    }

    static long rangeSum(long[] pre, int l, int r) {
        return pre[r + 1] - pre[l];
    }
}

How to recognise it in an unseen problem

Arrays are the default container, so the useful signal is not "is there an array" but "which array pattern is hiding here."

Trigger signals
  • "Sum / average / count over a range" — especially many ranges, or the same array queried repeatedly → prefix sum.
  • "Number of subarrays with sum equal to k", "subarray sums divisible by k" → prefix sum + hash map.
  • "Apply +v to every index in [l, r], many times, then report the array" → difference array.
  • "Rotate / reverse / partition in place", "O(1) extra space" → in-place two-pointer or cyclic-replacement.
  • Words like grid, matrix, board, island, region, spiral, diagonal → structured 2D traversal; sum-of-sub-rectangle → 2D prefix sum.
  • "Next / previous element with property X" → this is usually a monotonic-stack problem (§12), not a nested loop.
Common mistakes
  • pre sized n instead of n + 1, then fighting off-by-one on pre[r + 1].
  • Prefix sums overflowing int on a long array of large values — use long.
  • g[0].length on an empty or jagged 2D array → ArrayIndexOutOfBounds / wrong column count.
  • Swapping rows and columns: g.length is rows, g[i].length is columns.
  • Modifying the array while iterating and letting indices shift under you.
  • Assuming new int[r][c] is one contiguous block — it is r separate row arrays.

2 · Two Pointers

Two pointers replaces a nested "for every pair" loop with two indices whose movement is monotonic — each pointer only ever moves in one direction, so the total work is O(n) instead of O(n²), with O(1) extra space. There are two distinct shapes.

Converging pointers start at opposite ends and move inward. This is the shape for a sorted array ("find a pair summing to target": if the current sum is too small move the left pointer right, if too big move the right pointer left), for palindromes ("compare s[i] and s[j], step both inward"), and for "container with most water" style area problems.

Same-direction pointers (often called slow and fast, or read and write) both move left-to-right at different rates or under different conditions. slow marks where the next kept element should go; fast scans ahead. This is how you remove duplicates from a sorted array, move all zeros to the end, or compact a list in place — all in one pass without an auxiliary array.

Core intuition

You are collapsing a 2D search (all pairs i < j) into a 1D walk. That only works when moving a pointer provably rules out a whole set of possibilities — e.g. in a sorted array, if a[i] + a[j] is already too big, every pair using a[j] with a larger left element is also too big, so j-- loses nothing.

Worked example — pair with a given sum in a sorted array

public class TwoSumSorted {
    static int[] twoSum(int[] a, int target) {
        int i = 0, j = a.length - 1;
        while (i < j) {
            int sum = a[i] + a[j];
            if (sum == target) return new int[]{i, j};
            if (sum < target) i++;      // need a bigger sum: raise the low end
            else                j--;    // need a smaller sum: lower the high end
        }
        return new int[]{-1, -1};
    }

    public static void main(String[] args) {
        int[] a = {1, 3, 4, 5, 7, 11};
        int[] r = twoSum(a, 9);
        System.out.println(r[0] + " " + r[1]);   // 2 3   (a[2]=4, a[3]=5)
    }
}

How to recognise it in an unseen problem

The tell is a brute force of the form "for each i, for each j > i …" combined with either a sorted input or a structure that lets you decide which end to move.

Trigger signals
  • Input is sorted (or you are allowed to sort it) and you need a pair / triplet with a sum, difference, or product property.
  • "Compare from both ends" — palindrome, reverse in place, is-subsequence, valid mountain array.
  • "Two lines / bars / walls" and an area or distance between them — move the pointer at the limiting side.
  • "Remove / move / dedup elements in place, keep relative order" → slow write-pointer, fast read-pointer.
  • "Merge two sorted arrays / lists" → one pointer per input.
  • Partitioning into two or three groups by a predicate (Dutch national flag).
Common mistakes
  • Applying sorted-array logic to unsorted data — the "move the smaller side" argument no longer holds.
  • Sorting when the problem needs original indices, then returning the sorted positions.
  • i <= j instead of i < j, double-counting the middle element.
  • Moving neither pointer on some branch → infinite loop.
  • 3Sum / 4Sum: not skipping over duplicate values, producing duplicate tuples.
  • Slow/fast compaction: forgetting to only advance slow when you actually keep an element.

3 · Sliding Window

A sliding window is a contiguous range [left, right] over an array or string that you grow and shrink instead of recomputing. The right pointer marches forward one step at a time, adding each new element to a running summary (a sum, a count, a character-frequency map, a distinct-element count). Whenever the window breaks its constraint, you advance left, removing elements from the summary, until the window is valid again. Because every index is added once and removed once, the whole scan is O(n) even though it "feels" nested.

Fixed-size windows (exactly k elements) are the simplest: add the incoming element, remove the one that fell off the back, read the answer. Variable-size windows come in two flavours — "longest window that stays valid" (grow greedily, shrink only when invalid, record the max length) and "shortest window that becomes valid" (grow until valid, then shrink as far as you can while staying valid, record the min).

The technique depends on the constraint being monotonic with respect to window size: adding elements can only push the window further from valid (or further into valid), never flip it back and forth unpredictably. "At most k distinct characters", "sum ≥ target with non-negative numbers", and "no repeated character" all have this property. "Sum ≥ target with negative numbers" does not — that one needs a prefix sum plus a deque.

Core intuition

Never look inside the window. Keep an O(1)-updatable summary of it, and let the two edges do all the work: right always moves forward; left only moves forward, and only when forced. If you catch yourself writing a loop that re-scans left..right, the pattern has slipped.

Worked example — longest substring with no repeating character

import java.util.Arrays;

public class LongestUnique {
    static int lengthOfLongest(String s) {
        int[] lastSeen = new int[128];
        Arrays.fill(lastSeen, -1);

        int left = 0, best = 0;
        for (int right = 0; right < s.length(); right++) {
            char c = s.charAt(right);
            if (lastSeen[c] >= left)        // a copy of c is inside the window
                left = lastSeen[c] + 1;     // jump left just past that copy
            lastSeen[c] = right;
            best = Math.max(best, right - left + 1);
        }
        return best;
    }

    public static void main(String[] args) {
        System.out.println(lengthOfLongest("abcabcbb"));  // 3  -> "abc"
    }
}

How to recognise it in an unseen problem

Two conditions together: the thing you are optimising is a contiguous run, and the validity of a run changes monotonically as it grows.

Trigger signals
  • "Subarray / substring" (contiguous!) plus "longest", "shortest", "maximum sum of", "count of", or "does one exist".
  • A size is fixed: "window of size k", "every k consecutive", "k-length" → fixed window.
  • A budget you can spend and reclaim: "at most k distinct", "at most k replacements / flips / removals", "at most k zeros".
  • "Smallest window containing all of T", "permutation / anagram of T as a substring".
  • Brute force is "try every start and extend" and the input is not tiny.
  • Not sliding window: subsequence (non-contiguous), or a sum constraint with negative numbers.
Common mistakes
  • Shrinking with if when the invariant needs a while (or vice versa).
  • Recomputing the window's sum / counts from scratch each step — silently back to O(n²).
  • Off-by-one in window length: it is right - left + 1.
  • Forgetting to undo the outgoing element's contribution when left advances.
  • Using it on a problem with negative numbers where "growing grows the sum" is false.
  • Recording the answer at the wrong moment (before shrinking for a "shortest", after shrinking for a "longest").

4 · Binary Search & the "Search Space" Reframing

Textbook binary search: on a sorted array, look at the middle element, compare with the target, and throw away the half that cannot contain it — O(log n). Compute the midpoint as lo + (hi - lo) / 2 to avoid int overflow. Keep two templates straight: the exact-match template (while (lo <= hi), return on hit, else lo = mid + 1 or hi = mid - 1), and the boundary template (while (lo < hi), hi = mid or lo = mid + 1, the answer is lo) for "first index that satisfies P" / lower-bound style questions.

The bigger idea — the one that separates people who "know binary search" from people who see it — is that binary search works on any monotonic predicate over an ordered space. If there is some value axis where a yes/no test flips exactly once, from false…false true…true, you can binary-search for the flip point even when no sorted array is anywhere in sight. The array is replaced by the range of possible answers, and the comparison is replaced by a feasibility check.

This is often called "binary search on the answer". Typical forms: "minimum capacity so all packages ship within D days", "minimum eating speed to finish in H hours", "largest minimum distance between k placed items", "smallest divisor so the sum of ceilings ≤ threshold". In each, you cannot compute the answer directly, but given a candidate answer you can check "is this enough?" in O(n), and that check is monotonic in the candidate. Binary-search the candidate: O(n log(range)).

Core intuition

Ask: "can I phrase this as find the smallest (or largest) x for which feasible(x) is true, where feasible never goes true → false as x grows?" If yes, you don't need the data sorted — you need the answer to live on an ordered line, and you need a cheap feasibility test.

Worked example — minimum eating speed (search on the answer)

public class MinEatingSpeed {
    static int minSpeed(int[] piles, int h) {
        int lo = 1, hi = 0;
        for (int p : piles) hi = Math.max(hi, p);   // fastest useful speed

        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (hoursNeeded(piles, mid) <= h) hi = mid;   // feasible: try slower
            else                              lo = mid + 1; // too slow: speed up
        }
        return lo;                                   // smallest feasible speed
    }

    static long hoursNeeded(int[] piles, int speed) {
        long hours = 0;
        for (int p : piles) hours += (p + speed - 1) / speed;   // ceil(p / speed)
        return hours;
    }

    public static void main(String[] args) {
        System.out.println(minSpeed(new int[]{3, 6, 7, 11}, 8));  // 4
    }
}

How to recognise it in an unseen problem

Trigger signals
  • Sorted or rotated-sorted array + "find / count / insertion position / first or last occurrence".
  • "Minimize the maximum" or "maximize the minimum" of something.
  • "Smallest / largest x such that <condition>", where the condition clearly gets easier (or harder) as x grows.
  • The answer is an integer in a known range [lo, hi], you can't compute it directly, but checking a guess is a simple O(n) pass.
  • Tuning a resource: days, speed, capacity, length, budget, divisor — "within / at most / at least".
  • Required complexity is O(log n) or O(n log n) and a linear scan is too slow.
Common mistakes
  • (lo + hi) / 2 overflowing — use lo + (hi - lo) / 2.
  • lo = mid without + 1 in a lo < hi loop → infinite loop.
  • Mixing the two templates and losing track of the invariant (is the answer lo, hi, or lo - 1?).
  • Binary-searching a predicate that isn't actually monotonic.
  • Feasibility check overflowing — accumulate hours / counts in a long.
  • Rotated array: comparing a[mid] against the wrong endpoint to decide which half is sorted.

5 · Strings

A Java String is an immutable char sequence — every "modifying" call returns a new object. Building a result character by character with += in a loop is therefore O(n²); use a StringBuilder and one final toString(). Compare contents with .equals(), never ==. Because char is an integer type, c - 'a' maps 'a'..'z' onto 0..25, which is the whole basis of the frequency-array trick.

Most string problems reduce to one of four techniques: frequency counting with an int[26] (or int[128], or a HashMap for Unicode) — anagrams, permutations, first-unique, "can we form"; two pointers — palindrome checks, reversal, comparing from both ends; sliding window — longest / shortest substring with a property (§3); and building with a StringBuilder — compression, encoding, run-length, reversing words.

A few problems need more: "longest palindromic substring" is cleanest with expand around centre (try each of the 2n - 1 centres, grow outward while the two sides match — O(n²)), and substring search at scale uses KMP or a rolling hash (Rabin–Karp) to hit O(n + m). Know those two by name and when they apply, even if you re-derive the details.

Core intuition

Before coding, classify: am I counting characters, walking from both ends, sliding a window, or building an output? A phrase like "lowercase English letters" is a near-certain signal to reach for int[26].

Worked example — are two strings anagrams (single frequency array)

public class Anagram {
    static boolean isAnagram(String s, String t) {
        if (s.length() != t.length()) return false;

        int[] count = new int[26];
        for (int i = 0; i < s.length(); i++) {
            count[s.charAt(i) - 'a']++;    // +1 for a char in s
            count[t.charAt(i) - 'a']--;    // -1 for a char in t
        }
        for (int c : count) if (c != 0) return false;   // any imbalance -> not anagram
        return true;
    }

    public static void main(String[] args) {
        System.out.println(isAnagram("anagram", "nagaram"));  // true
        System.out.println(isAnagram("rat", "car"));          // false
    }
}

How to recognise it in an unseen problem

Trigger signals
  • "Anagram", "permutation", "rearrange", "same characters" → frequency array / map.
  • "First non-repeating", "character that appears once", "most frequent character" → frequency then scan.
  • "Palindrome", "reverse", "is it symmetric" → two pointers; "longest palindromic substring / count palindromes" → expand around centre.
  • "Find pattern P in text T", "does T contain a rotation of P" → KMP / rolling hash.
  • "Compress", "encode / decode", "run length", "reverse the words" → build with StringBuilder.
  • "Isomorphic", "word pattern", "group anagrams" → map each char / word to a canonical key.
  • Small fixed alphabet stated explicitly → int[26].
Common mistakes
  • s1 == s2 for content comparison — use .equals().
  • result += c in a loop — quietly O(n²); use StringBuilder.
  • int[26] when the input can contain uppercase, digits, spaces, or Unicode.
  • Forgetting immutability: s.trim(); on its own line does nothing.
  • substring(i, j) treating j as inclusive — it is exclusive.
  • Expand-around-centre: handling only odd-length centres and missing even-length palindromes.
  • Using s.length (arrays) instead of s.length() (strings).

6 · Bit Manipulation

Integers are stored in binary, with negatives in two's complement (-n == ~n + 1). The operators are & (AND), | (OR), ^ (XOR), ~ (NOT), << (left shift), >> (arithmetic / sign-preserving right shift), and >>> (logical / zero-fill right shift). A Java int is 32-bit signed; shifting by a count ≥ 32 wraps the count modulo 32.

A handful of identities do almost all the work. n & 1 is 1 exactly when n is odd. n & (n - 1) clears the lowest set bit — loop it to count set bits (Brian Kernighan), and (n & (n - 1)) == 0 tests power-of-two. n & -n isolates the lowest set bit. 1 << k is a mask for bit k: set with x | (1 << k), clear with x & ~(1 << k), toggle with x ^ (1 << k), test with (x >> k) & 1.

XOR deserves its own line: x ^ x == 0 and x ^ 0 == x, and XOR is commutative and associative. So XOR-ing a whole array cancels every value that appears an even number of times, leaving the one odd-count value — the "single number" trick, and the basis of swap-without-a-temp. For subset enumeration over ≤ ~20 items, a bitmask 0 .. (1 << n) - 1 represents every subset, one bit per element.

Core intuition

XOR means "parity / difference — pairs disappear". AND with a mask means "keep only these bits". n & (n - 1) means "peel off one set bit". Ninety percent of a bit problem is recognising which of those three it wants.

Worked example — the one number that isn't duplicated

public class SingleNumber {
    static int singleNumber(int[] nums) {
        int acc = 0;
        for (int x : nums) acc ^= x;   // every pair cancels to 0
        return acc;                    // the lone survivor
    }

    public static void main(String[] args) {
        System.out.println(singleNumber(new int[]{4, 1, 2, 1, 2}));  // 4
    }
}

How to recognise it in an unseen problem

Trigger signals
  • "Every element appears twice (or three times) except one" → XOR fold (or bit-count mod 3).
  • "Without extra memory" / "O(1) space" on a problem that otherwise wants a set or counter.
  • "Swap two numbers without a temporary variable."
  • "Count bits", "is it a power of two / four", "reverse the bits", "Hamming distance".
  • "Generate all subsets", "iterate over every combination", with n small (≤ ~20) → bitmask.
  • Constraints mention "32-bit signed integer" or the answer must fit specific bit widths.
  • "Add / multiply without using + / *."
Common mistakes
  • Precedence: n & 1 == 0 parses as n & (1 == 0) — always parenthesise: (n & 1) == 0.
  • >> vs >>> on negative numbers (sign-fill vs zero-fill).
  • 1 << 32 is 1, not 0 — the shift count wraps mod 32. Use 1L << k for wide masks.
  • Sign extension when reading bits of a negative int.
  • Using Math.pow(2, k) instead of 1 << k (double, imprecise, slow).
  • Assuming n & -n behaves for Integer.MIN_VALUE.

7 · Number Systems & Maths

Positional notation: in base b, the digit at position k from the right is worth digit · bk. Decimal → base b: repeatedly take n % b (next lowest digit) and n /= b; digits come out lowest-first, so reverse. Base b → decimal: result = result * b + digit, scanning left to right.

The recurring number-theory tools: modular arithmetic — (a + b) % m, (a * b) % m, take the mod early and often, cast to long before multiplying, and use ((a % m) + m) % m for a non-negative result (Java's % keeps the sign of the dividend, so -7 % 3 == -1). GCD by Euclid: gcd(a, b) = gcd(b, a % b), stopping at b == 0; lcm(a, b) = a / gcd * b (divide first to avoid overflow). Primes: trial-divide up to √n for one number; Sieve of Eratosthenes in O(n log log n) to list all primes up to N.

Fast exponentiation computes ab in O(log b) by squaring the base and halving the exponent — essential once b is large or a modulus is involved, and more accurate than Math.pow for integers. In practice, the "maths" label on an interview problem usually means one of: watch for overflow, or find the O(√n) / O(log n) instead of the obvious O(n).

Core intuition

Cast to long before you multiply. And whenever a loop runs for i in 1..n over a number's value, ask whether √n or log n is enough — factorisation, primality, and exponentiation all have sub-linear forms.

Worked example — fast modular exponentiation

public class FastPow {
    static long power(long base, long exp, long mod) {
        long result = 1 % mod;
        base %= mod;
        while (exp > 0) {
            if ((exp & 1) == 1) result = (result * base) % mod;  // odd bit: fold in
            base = (base * base) % mod;                          // square the base
            exp >>= 1;                                           // drop the low bit
        }
        return result;
    }

    public static void main(String[] args) {
        System.out.println(power(2, 10, 1_000_000_007));  // 1024
        System.out.println(power(5, 3, 13));              // 125 % 13 = 8
    }
}

How to recognise it in an unseen problem

Trigger signals

  • "Is it prime", "count primes up to N", "prime factorisation" → trial division to √n or a sieve.
  • "GCD", "LCM", "reduce the fraction", "co-prime".
  • "Digits of a number", "sum / reverse / rotate digits", "convert between bases".
  • "ab" with big b, "x raised to n", "number of ways mod m".
  • "Trailing zeros of n!", "how many multiples", "n-th ugly / happy number".
  • Inputs up to 109–1018 → you need O(√n) / O(log n) and long care.
Common mistakes
  • a * b overflowing int before the % m — multiply as long.
  • Expecting -7 % 3 == 2; in Java it is -1. Normalise with ((a % m) + m) % m.
  • Math.pow for integer powers → 124.99999.
  • Sieve inner loop not starting at i * i or not stepping by i.
  • Trial-dividing up to n instead of √n.
  • lcm = a * b / gcd overflowing — do a / gcd * b.
  • Integer division truncating when you needed a ceiling: use (a + b - 1) / b.

8 · Recursion

A recursive method solves a problem by calling itself on a smaller input. It needs a base case that returns without recursing, and a recursive case that makes measurable progress toward the base case and combines the sub-result. The mental model is "trust the recursion": assume the recursive call already returns the correct answer for the smaller input, and figure out only how to build the current answer from it — then handle the smallest case explicitly.

Draw the recursion tree: each node is a call, labelled with its arguments; a node's children are the calls it makes. The number of nodes is the time complexity; the longest root-to-leaf path is the stack-space complexity. Two shapes recur. Reduce: one recursive call per node (factorial, sum of a list, binary search) — a linear chain, O(n) nodes, O(n) depth. Branch: several recursive calls per node (Fibonacci, subsets, permutations, tree traversal) — an exponential or factorial tree. If the same argument tuple appears at many nodes, you have overlapping subproblems and should memoise (that is the bridge to dynamic programming, covered on the non-linear page).

Backtracking is branch recursion where each node makes a choice, recurses, and then undoes the choice before trying the next one — so the shared state (a list, a board, a visited set) is exactly restored on the way back up. "Make a move, recurse, unmake the move" is the whole skeleton.

Core intuition

For a tiny input, sketch the call tree on paper. Nodes = work done; height = stack used; repeated nodes = memoise. If you can state "answer(n) in terms of answer(smaller)", or you must enumerate a combinatorial space, it is recursion — and if it enumerates, it is probably backtracking.

Worked example — all subsets by include / exclude (backtracking)

import java.util.*;

public class Subsets {
    static List<List<Integer>> subsets(int[] nums) {
        List<List<Integer>> out = new ArrayList<>();
        backtrack(nums, 0, new ArrayList<>(), out);
        return out;
    }

    static void backtrack(int[] nums, int i, List<Integer> cur, List<List<Integer>> out) {
        if (i == nums.length) {              // base case: every element decided
            out.add(new ArrayList<>(cur));   // copy! cur keeps mutating
            return;
        }
        cur.add(nums[i]);                    // choice 1: include nums[i]
        backtrack(nums, i + 1, cur, out);
        cur.remove(cur.size() - 1);          // undo the choice
        backtrack(nums, i + 1, cur, out);    // choice 2: exclude nums[i]
    }

    public static void main(String[] args) {
        System.out.println(subsets(new int[]{1, 2, 3}));
        // [[1, 2, 3], [1, 2], [1, 3], [1], [2, 3], [2], [3], []]
    }
}
Recursion tree — nums = {1, 2, 3}

Root is backtrack(i = 0, cur = []). Every node branches twice: left = "include nums[i]", right = "exclude". Depth is 3 (one level per element), so there are 2³ = 8 leaves, each a finished subset. A left-to-right DFS visits them in this order:

How to recognise it in an unseen problem

Trigger signals
  • "All / every / generate": subsets, permutations, combinations, partitions, valid arrangements, paths.
  • The answer for n is naturally defined from the answer for n − 1 or halves of n.
  • Self-similar / nested structure: nested parentheses, folder trees, expression parsing, matryoshka-style inputs.
  • "Can the input be split / segmented so that …" (word break, palindrome partitioning).
  • Explore-all-options with a constraint that prunes branches (N-Queens, Sudoku, maze).
  • A tree or graph is the input and you need to visit every node.
  • If identical sub-calls repeat → add memoisation (→ DP).
Common mistakes
  • Missing or unreachable base case, or a recursive case that doesn't shrink the input → StackOverflowError.
  • Backtracking without the undo step — state leaks between branches.
  • Storing cur by reference at a leaf instead of a copy — every result ends up equal (or empty).
  • Exponential recomputation when subproblems overlap — memoise.
  • Deep recursion (n ≈ 10⁵) overflowing the call stack — convert to an explicit stack / iteration.
  • Returning the recursive result on only one branch and forgetting the other.

9 · Hashing

A hash map or set maps a key to a bucket via the key's hashCode(), giving average O(1) insert, lookup, and delete. Collisions are resolved by chaining, so the worst case is O(n), but with reasonable keys that essentially never happens. The everyday uses: membership ("have I seen x?"), counting (a frequency map), grouping (key → list of members), complement lookup ("is target − x present?"), memoisation, and remembering the last index at which something occurred.

Choose the right structure. HashMap / HashSet when keys are arbitrary and you only need presence or a value. A plain int[] or boolean[] when keys are a small dense integer range (letters, digits, small bounded values) — it is a faster, allocation-free hash map. TreeMap / TreeSet (O(log n)) when you also need order — floor, ceiling, range. LinkedHashMap when insertion order matters (and it is the natural backbone of an LRU cache).

Hashing is the single most common way to turn an O(n²) brute force into O(n): any time the inner loop is "scan the rest to find or count something", a hash structure usually removes it, at the cost of O(n) extra space. It also composes with prefix sums ("subarrays summing to k": store how many times each prefix sum has occurred).

Core intuition

When you're about to write "for each element, look through the others", stop and ask what you're looking for — a value, a count, a previous index — and put that in a map keyed for O(1) retrieval as you go. One pass, build-as-you-check.

Worked example — Two Sum with a complement map

import java.util.*;

public class TwoSum {
    static int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();   // value -> its index
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            if (seen.containsKey(need))
                return new int[]{seen.get(need), i};
            seen.put(nums[i], i);                        // record after checking
        }
        return new int[]{-1, -1};
    }

    public static void main(String[] args) {
        int[] r = twoSum(new int[]{2, 7, 11, 15}, 9);
        System.out.println(r[0] + " " + r[1]);   // 0 1
    }
}
Dry run — nums = {2, 7, 11, 15}, target = 9

Checking before inserting nums[i] stops an element from pairing with itself. One pass, O(n) time, O(n) space.

How to recognise it in an unseen problem

Trigger signals
  • "Has this appeared before", "contains duplicate", "find the repeated / missing element".
  • "Count occurrences", "frequency", "most / least common", "first unique".
  • "Two (or three) values with a sum / difference / product" — and the array is not sorted (if it is, consider two pointers).
  • "Group / bucket by some computed key" (anagrams, by remainder, by shape).
  • "Subarray / substring with sum (or count) equal to k" → prefix value → count map.
  • "Longest consecutive run of integers" (unordered) — a set gives O(n).
  • You need memoisation for a recursive solution.
Common mistakes
  • map.get(k) + 1 when k is absent → NullPointerException on unboxing. Use getOrDefault or merge.
  • Comparing boxed Integer keys with == in your own code.
  • Relying on HashMap iteration order.
  • Mutating an object after using it as a key.
  • Using a Set when you needed counts (it collapses duplicates).
  • containsKey then get — two lookups where one (get + null check) suffices.
  • A custom key class without overriding both equals and hashCode.

10 · Sorting

Comparison sorts cannot beat Θ(n log n). Java's Arrays.sort uses a dual-pivot quicksort for primitives (O(n log n) average, not stable, O(n²) adversarial worst case) and Timsort for object arrays and Collections.sort (stable, O(n log n) worst, exploits existing runs). Know the mechanics of the two classics: merge sort (split in half, sort each, merge — stable, O(n) extra) and quicksort (partition around a pivot, recurse on each side — in place, worst case on already-sorted input with a bad pivot).

When the values are small integers, you can skip comparisons entirely: counting sort is O(n + k), and radix / bucket sort extend the idea. And quickselect — quicksort's partition step, recursing into only one side — finds the k-th smallest in O(n) average without fully sorting.

But the reason sorting is a pattern and not just a library call is that it is the setup move. A huge class of problems becomes trivial "if only the input were sorted": pair/triple finding (→ two pointers), interval merging and scheduling (→ linear sweep), greedy choices (take the smallest / largest next), deduplication, and "closest values" (adjacent after sorting). The recipe is: sort in O(n log n), then one linear pass.

Core intuition

If the problem gets obviously easier when you assume the data is ordered — and the order of the input doesn't otherwise matter — sort first, then look for the linear-time idea that the sorted order unlocks. Sorting is almost never the last step.

Worked example — merge overlapping intervals (sort, then sweep)

import java.util.*;

public class MergeIntervals {
    static int[][] merge(int[][] intervals) {
        Arrays.sort(intervals, (x, y) -> Integer.compare(x[0], y[0]));  // by start

        List<int[]> out = new ArrayList<>();
        int[] cur = intervals[0];
        for (int i = 1; i < intervals.length; i++) {
            if (intervals[i][0] <= cur[1]) {                  // overlaps current
                cur[1] = Math.max(cur[1], intervals[i][1]);   // extend the end
            } else {
                out.add(cur);                                 // gap: close current
                cur = intervals[i];
            }
        }
        out.add(cur);
        return out.toArray(new int[0][]);
    }

    public static void main(String[] args) {
        int[][] r = merge(new int[][]{{1, 3}, {2, 6}, {8, 10}, {15, 18}});
        System.out.println(Arrays.deepToString(r));   // [[1, 6], [8, 10], [15, 18]]
    }
}

How to recognise it in an unseen problem

Trigger signals
  • "Intervals", "meetings", "ranges" + "merge", "overlap", "minimum rooms", "can attend all".
  • "k-th largest / smallest", "top k", "median" → sort, or heap / quickselect for better than O(n log n).
  • "Find pairs / triplets with property X" → sort, then two pointers.
  • "Minimum number of X to cover / remove / connect Y" → greedy after sorting by the right key.
  • "Arrange numbers to form the largest / smallest value" → sort with a custom comparator.
  • "Closest pair", "smallest absolute difference", "can we form an arithmetic sequence".
  • Order of the input is irrelevant and a sorted view makes the invariant obvious.
  • Not sorting: when the required complexity is below O(n log n).
Common mistakes
  • Assuming Arrays.sort(int[]) is stable — it isn't; box to Integer[] if stability matters.
  • Comparator written as a[0] - b[0] overflowing for large / negative values — use Integer.compare.
  • A comparator that isn't transitive / consistent → IllegalArgumentException: Comparison method violates its general contract.
  • Sorting when the caller still needs the original order (sort a copy, or sort indices).
  • Forgetting to sort before the two-pointer or greedy step that depends on it.
  • Using a full sort where counting sort / a heap would be asymptotically better.

11 · Linked Lists

A singly linked list is a chain of nodes, each holding a value and a next reference. There is no indexing — reaching the k-th node is O(k) — but splicing a node in or out at a known position is O(1). Two habits remove most of the pain: use a dummy (sentinel) head node so inserting or deleting at the front is not a special case, and never overwrite cur.next before saving it, or you lose the rest of the list.

In-place reversal walks three pointers — prev, cur, next: save next = cur.next, flip cur.next = prev, then advance both prev and cur. O(n) time, O(1) space, and prev is the new head. This generalises to "reverse the first k", "reverse in groups of k", and "reverse between positions m and n".

Fast & slow pointers (Floyd's tortoise and hare): slow steps once per iteration, fast twice. If they ever meet, the list has a cycle; restarting one pointer at the head and stepping both one-at-a-time then finds the cycle's entry node. The same two-speed walk finds the middle (when fast reaches the end, slow is at the midpoint) and the n-th node from the end in a single pass (start fast n steps ahead, move both until fast falls off).

Core intuition

You can only hold a few references, so name them for their jobs — dummy, prev, cur, next, slow, fast — and change exactly one link per step. Whenever you're about to reassign a next field, first ask "have I saved what it currently points to?"

Worked example — reverse a singly linked list in place

public class ReverseList {
    static class ListNode {
        int val;
        ListNode next;
        ListNode(int v) { val = v; }
    }

    static ListNode reverse(ListNode head) {
        ListNode prev = null, cur = head;
        while (cur != null) {
            ListNode next = cur.next;   // 1. save the rest of the list
            cur.next = prev;            // 2. flip this link backwards
            prev = cur;                 // 3. prev catches up
            cur  = next;                // 4. cur moves on
        }
        return prev;                    // prev is the new head
    }

    public static void main(String[] args) {
        ListNode a = new ListNode(1);
        a.next = new ListNode(2);
        a.next.next = new ListNode(3);

        for (ListNode p = reverse(a); p != null; p = p.next)
            System.out.print(p.val + " ");   // 3 2 1
    }
}

How to recognise it in an unseen problem

Trigger signals
  • The input is a linked list (obvious) — but the sub-pattern is the real question.
  • "Detect a cycle", "does it loop", "find where the loop starts" → fast & slow.
  • "Middle of the list", "n-th node from the end", in one pass → fast & slow / gap of n.
  • "Reverse", "reverse in groups of k", "swap nodes in pairs", "rotate", "reorder" → in-place pointer surgery, usually with a dummy head.
  • "Merge two sorted lists", "add two numbers as lists", "remove duplicates from a sorted list".
  • "Is the list a palindrome" → fast/slow to the middle, reverse the second half, compare.
  • Cycle-detection reasoning applies beyond lists: "Happy Number", "Find the Duplicate Number" (values as next-pointers).
Common mistakes
  • Reassigning cur.next before saving it — the tail of the list is gone.
  • Not using a dummy head and then mishandling operations on the first node.
  • Loop guard order: fast != null && fast.next != null — reverse it and you get an NPE.
  • Off-by-one in fast/slow: starting fast at head vs head.next changes which middle you land on for even length.
  • Forgetting to null-terminate the new tail after a reversal / split → an accidental cycle.
  • Returning head instead of prev / dummy.next.
  • Not handling an empty list or a single node.

12 · Stacks & Queues

A stack is LIFO (push / pop / peek, all O(1)); a queue is FIFO (offer / poll / peek, all O(1)). In Java, back both with ArrayDeque — not the legacy synchronised Stack class, not LinkedList. Stacks model bracket matching, expression evaluation (infix → postfix, reverse Polish notation), undo, and iterative DFS. Queues model breadth-first search, level-order traversal, and anything processed in arrival order.

The pattern worth drilling is the monotonic stack: keep the stack's contents sorted (strictly increasing or strictly decreasing from bottom to top). When the incoming element would break that order, pop elements until it fits — and each element you pop has just found its answer. Because every element is pushed once and popped once, the whole scan is O(n) even though it replaces a nested loop. The classic use is "for each element, find the nearest greater (or smaller) element to the left / right".

The same idea with a monotonic deque (pop from both ends) solves sliding-window maximum / minimum in O(n): the front of the deque always holds the current window's extreme, stale indices are dropped from the front, and dominated indices are dropped from the back.

Core intuition

Monotonic stack = "for each element, look back to the most recent unresolved one." The stack holds exactly the elements still waiting for their next-greater / next-smaller neighbour. The moment the current element resolves one, pop it and record the answer.

Worked example — next greater element (monotonic stack, right to left)

import java.util.*;

public class NextGreater {
    static int[] nextGreater(int[] a) {
        int n = a.length;
        int[] ans = new int[n];
        Deque<Integer> stack = new ArrayDeque<>();   // values, decreasing bottom→top

        for (int i = n - 1; i >= 0; i--) {
            while (!stack.isEmpty() && stack.peek() <= a[i])
                stack.pop();                          // too small to ever be "next greater"
            ans[i] = stack.isEmpty() ? -1 : stack.peek();
            stack.push(a[i]);
        }
        return ans;
    }

    public static void main(String[] args) {
        System.out.println(Arrays.toString(nextGreater(new int[]{2, 1, 2, 4, 3})));
        // [4, 2, 4, -1, -1]
    }
}

How to recognise it in an unseen problem

Trigger signals
  • Stack: "valid / balanced / matching" brackets or tags; "evaluate this expression"; "simplify the path".
  • Monotonic stack: "next / previous greater / smaller / warmer", "stock span", "how many days until", "largest rectangle in histogram", "trapping rain water", "remove k digits for the smallest number", "asteroid collision".
  • Any "for each element, scan left/right until a bigger/smaller one" brute force on a non-tiny array.
  • Queue: "level order", "shortest path in an unweighted grid / graph", "rotting oranges", "process in order of arrival".
  • Monotonic deque: "maximum / minimum of every window of size k".
  • "Implement a queue using stacks" (or vice versa), "design a data structure with O(1) …".
Common mistakes
  • pop() / peek() without an isEmpty() check first.
  • Using java.util.Stack or LinkedList instead of ArrayDeque; also, ArrayDeque rejects null.
  • Wrong monotonic direction (increasing vs decreasing) for the question asked.
  • Storing values when you need indices (indices let you compute distances / widths) — or vice versa.
  • Forgetting that elements left on the stack at the end have no next-greater (answer -1).
  • Sliding-window max with a plain queue → O(nk); use a monotonic deque for O(n).
  • Mixing up which end push / pop / offer / poll act on for a Deque.
