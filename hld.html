High-Level Design — Scaling, Data & Distributed Systems

Phase 2. An HLD round hands you one sentence ("design a URL shortener", "design Instagram's feed") and 45 minutes. The interviewer is checking whether you can turn a vague ask into numbers, propose components that fit those numbers, go deep on the one hard part, and name the trade-off you made instead of pretending there wasn't one. This page is the toolbox — eight core concepts, each with the back-of-envelope math that tells you when it applies — and then a repeatable framework run end-to-end on a URL shortener.

How to use this page. Every concept has a capacity math block — those numbers are the point, not decoration. Read each concept, then do the arithmetic yourself on a scratchpad before looking at mine. Distributed systems fundamentals

A distributed system is a set of machines that appears to its users as a single coherent service. You go distributed for three reasons: scale (one machine can't hold the data or serve the traffic), availability (one machine's failure shouldn't take the service down), and latency (put data near users in different regions). Every one of those benefits is bought with the same currency: you now have a network in the middle, and networks drop messages, reorder them, and delay them unpredictably.

The CAP theorem is the one-liner everyone quotes: when a network partition splits your nodes, you must choose between consistency (every read sees the latest write, or an error) and availability (every request gets a non-error answer, possibly stale). You don't get to pick "CA" — partitions happen whether you like them or not, so the real choice is CP or AP during a partition. A bank ledger picks CP (refuse the withdrawal rather than double-spend); a social feed picks AP (show a slightly old feed rather than an error page). PACELC extends this: else, when there's no partition, you still trade latency against consistency (a synchronous quorum write is slower than a fire-and-forget one).

Consistency models form a spectrum, not a binary. Strong / linearizable: reads always see the most recent write, as if there were one copy. Read-your-writes: you see your own updates, others may lag. Eventual: replicas converge if writes stop. Most large systems are a deliberate mix — strong for the checkout, eventual for the "people also bought" widget. Interviewers want you to say which parts of your design need which model and why.

Core intuition — the latency numbers you must know

Design decisions fall out of the fact that operations differ by orders of magnitude: 

L1 cache reference .................... 1 ns
Main memory reference ................ 100 ns      (~100x L1)
Read 1 MB sequentially from memory .... 3 us
SSD random read ...................... 100 us     (~1000x memory)
Round trip within a datacenter ....... 500 us
Read 1 MB sequentially from SSD ....... 1 ms
Disk (HDD) seek ...................... 10 ms      (~100x SSD read)
Round trip CA <-> Netherlands ........ 150 ms

Takeaways you will actually use: a cross-region round trip (150 ms) is ~300× a same-DC one, so chatty cross-region calls are death — batch or replicate. A disk seek (10 ms) is ~20× an SSD read, which is why nobody spec's spinning disks for random-access workloads any more. Memory is ~1000× faster than SSD for random reads — that single ratio is the entire economic case for caching.

Capacity math — what "three nines" actually costs you

Availability is downtime budget per year (365 × 24 × 60 ≈ 525,600 minutes): 

99%     ("two nines")  -> 5,256 min/yr  = 3.65 days   down
99.9%   ("three nines")-> 526 min/yr    = 8.8 hours   down
99.99%  ("four nines") -> 52.6 min/yr   = 52 minutes  down
99.999% ("five nines") -> 5.26 min/yr   = 5 minutes   down

Components in series multiply: a request that must pass through an LB (99.99%), a service (99.9%), and a DB (99.9%) has 0.9999 × 0.999 × 0.999 ≈ 0.9979 → 99.79%, worse than any single part (~16 hours/yr down). Redundant components in parallel do the opposite: two independent replicas each at 99% give 1 − (0.01)² = 99.99%. This is why you add replicas and why every hop you remove from the critical path buys availability for free.

Common mistakes
  • Treating CAP as a system-wide switch. It's per-operation. Say "the write path is CP, the read path is AP."
  • Claiming "CA". There is no partition-free distributed system; if you have replicas across a network, P is a given.
  • "We'll just make it strongly consistent." Then price it: every write is a cross-node quorum round trip, and availability drops when a quorum can't be formed.
  • Ignoring the tail. p50 latency of 20 ms with p99 of 800 ms means 1 in 100 users has a bad time — and a page that fans out to 100 services hits that p99 almost every load.
  • Forgetting clocks lie. Wall-clock timestamps across machines can disagree by tens of ms; don't order events by them. Use logical clocks / versions.

Load balancing

A load balancer spreads incoming requests across a pool of identical backends so no single one is overwhelmed, and so a dead backend is taken out of rotation automatically. It's the thing that turns "one server" into "a tier you can grow by adding boxes." It also becomes a single point of failure, so in practice you run it redundantly (two LB nodes with a floating IP, or a managed L7 service fronted by anycast DNS).

Layer 4 vs Layer 7. An L4 balancer forwards TCP/UDP by IP and port — fast, protocol-agnostic, but blind to what's inside. An L7 balancer terminates HTTP, so it can route by path (/api vs /static), do TLS termination, retry idempotent requests, inject headers, and rate-limit per user. Most modern designs put an L7 proxy (Envoy, NGINX, ALB) at the edge. The cost is CPU for TLS and parsing, and a bit more latency.

Algorithms. Round robin is the default and is fine when requests cost about the same. Least connections routes to the backend with the fewest in-flight requests — better when request durations vary wildly. Consistent hashing on a key (see the next section) pins a given user or cache key to the same backend, which you want for sticky sessions or cache locality. Weighted variants let you send more traffic to bigger instances or shift load during a canary deploy. Layer on active health checks (LB pings /healthz every few seconds) and passive ones (eject a backend after N consecutive 5xx).

Capacity math — how many backends do I need?

Say each app server handles 500 requests/second at acceptable latency (you'd get this number from a load test; it's set by CPU per request and the thread/connection pool). Your traffic: 

Daily requests ............. 500,000,000  (500M)
Seconds per day ............ 86,400
Average QPS ................ 500M / 86,400        ~= 5,800 req/s
Peak factor (diurnal) ...... 3x                   -> ~17,400 req/s peak
Servers at 500 rps each .... 17,400 / 500         = 35 servers
Headroom for failures (N+2). +2                   = 37 servers
Rolling-deploy / spike pad . x1.3                 ~= 48 servers

Now you know the app tier is ~50 boxes, not 5 and not 500. If one machine could do it (say 200 QPS total), you wouldn't need a load balancer or this section — that's the signal that tells you whether horizontal scaling is even on the table.

Core intuition

A load balancer only works if the backends are stateless — any box can serve any request. The moment a server keeps session data in local memory, you've created affinity, and affinity fights elasticity (you can't freely drain a box) and fault tolerance (its death loses sessions). Push state to a shared store (Redis, a signed cookie, a JWT) and the LB problem becomes trivial.

Common mistakes
  • Making the LB stateful. Sticky sessions by server IP defeat the purpose; hash on a stable user key instead, or externalize the session.
  • One LB, no redundancy. It's now your single point of failure; pair it, or use a managed anycast service.
  • Health check that only checks the port is open. Check a real endpoint that touches the DB, or you'll route to a box that's up but broken.
  • Retrying non-idempotent requests. An LB retrying a POST /charge on timeout can double-charge. Only retry safe methods or requests with an idempotency key.
  • Ignoring connection draining. Killing a backend with in-flight requests returns errors; drain first.

Consistent hashing — why naive hashing breaks at scale

You have a set of keys (cache entries, user records, shards) and a set of N nodes, and you need a deterministic function key → node. The obvious answer is node = hash(key) % N. It distributes evenly and is O(1). It also has a fatal property: change N and almost every key moves.

Concretely, with % N, a key stays put after resizing to N+1 only if hash(key) % N == hash(key) % (N+1), which happens for roughly 1/(N+1) of keys. So going from 4 nodes to 5 remaps about 80% of keys; from 100 to 101, about 99%. For a cache that means a near-total cold cache the instant you add or lose a node — every miss stampedes to the database, and you've turned "one extra server" into an outage. For a sharded database it means moving nearly the whole dataset.

Consistent hashing fixes this. Map both nodes and keys onto the same circular hash space (say 0 to 2³²−1). A key is owned by the first node encountered walking clockwise from the key's position. Now adding a node only steals the arc between it and its predecessor — only ~K/N keys move, and only from one neighbour. Removing a node hands its arc to the next node clockwise; again only that node's share moves. The rest of the ring is undisturbed.

One problem remains: with few nodes, random placement makes the arcs uneven — one node might own 40% of the ring. The fix is virtual nodes: each physical node is hashed to the ring at (say) 150 positions. Load evens out (standard deviation shrinks as 1/√V), and when a node dies its load spreads across many neighbours instead of dumping entirely on one.

Capacity math — keys moved when the cluster grows 
Cache with 1,000,000,000 (1B) entries.

Naive  hash % N,  N: 10 -> 11
  fraction that stay = 1/11  ->  ~91% of keys remap
  = 910,000,000 entries suddenly missing -> DB sees ~10x its normal read load

Consistent hashing,  N: 10 -> 11
  keys moved ~= K / (N+1) = 1B / 11  ->  ~9% remap
  = ~91,000,000 entries move, all from ONE node's former arc
  DB sees a ~1.09x blip, not a stampede

Virtual nodes, V = 150 per physical node
  per-node load spread: ~ +/- 1/sqrt(150) ~= +/-8%  (vs +/-30-40% with V=1)
  node failure: its ~9% of keys reassigned across ~150 arcs -> many nodes each +~0.06%
Core intuition

Naive modulo hashing couples every key's location to the total count of nodes, so any membership change is global. Consistent hashing couples a key's location only to its immediate clockwise neighbour, so a membership change is local. You're trading a trivially-even distribution for one that's "even enough" (with vnodes) in exchange for cheap elasticity — and elasticity is the whole reason you're sharding.

Common mistakes
  • Reaching for it when you don't resize. A fixed 16-shard scheme that never changes can just use % 16. Consistent hashing earns its keep when the node set churns.
  • Forgetting virtual nodes. Plain consistent hashing with 5 nodes has badly skewed arcs; interviewers will ask how you balance them.
  • Assuming it gives replication. It gives placement. For replicas you also store the key on the next R distinct physical nodes clockwise.
  • Hot keys. Consistent hashing balances key count, not traffic. One viral key still cooks its node — you need per-key replication or request coalescing for that.
  • Ignoring "jump hash" / rendezvous. When you don't need to remove arbitrary nodes, these are simpler and need no ring state — worth a mention.

Caching

A cache is a small, fast store in front of a big, slow one, holding the subset of data that's asked for most. It works because access is skewed — a small fraction of keys gets most of the traffic (a "Zipfian" distribution) — so a cache far smaller than the dataset can still absorb most reads. The number that matters is the hit ratio, and small improvements there have outsized effects on the backend.

Write strategies

Cache-aside (lazy loading). The application checks the cache; on a miss it reads the DB, populates the cache, and returns. Writes go to the DB and invalidate (delete) the cache key. Simple, and the cache only ever holds data someone actually asked for. Downsides: the first request for any key is always a miss, and there's a race where a stale value can be re-populated by a slow reader that overlapped a writer. This is the default for most systems (it's how you use Redis + Postgres).

Write-through. The application writes to the cache, and the cache synchronously writes to the DB before acknowledging. Reads are always warm for recently-written data and the cache is never staler than the DB. The cost is write latency (two hops on every write) and cache churn from data that's written but never read.

Write-back (write-behind). The application writes to the cache, which acknowledges immediately and flushes to the DB asynchronously in batches. Fastest writes, and it absorbs write bursts and coalesces repeated writes to the same key. The danger is obvious: a cache node crash loses un-flushed writes. Use it only where some loss is tolerable (view counts, "last seen" timestamps) or where the cache itself is durable/replicated.

Eviction policies

When the cache is full, something must go. LRU (evict the least recently used) is the safe default and matches temporal locality. LFU (least frequently used) is better when popularity is stable over time but reacts slowly to shifts (a once-hot key lingers). FIFO is cheap but ignores access. TTL isn't really eviction — it's a correctness knob that bounds staleness and should usually be set in addition to a size-based policy. Real systems blend: e.g. TinyLFU (a frequency filter guarding an LRU window), which is what Caffeine and many CDNs use.

Capacity math — hit ratio drives backend load, and cache size

Read traffic: 100,000 QPS. Backend (DB) can serve 20,000 QPS before it falls over. 

Hit ratio   Misses hitting DB          Verdict
--------    ----------------------     ---------------------------
80%         100k x 0.20 = 20,000 QPS   DB exactly at its limit - fragile
90%         100k x 0.10 = 10,000 QPS   comfortable
95%         100k x 0.05 =  5,000 QPS   lots of headroom
99%         100k x 0.01 =  1,000 QPS   DB barely notices

=> Going 90% -> 95% HALVES DB load. Hit ratio is the highest-leverage knob.

Sizing the cache: suppose 200M items, average 2 KB each = 400 GB for the full set. Measurements show the hottest 10% of keys serve 90% of reads. Cache that 10%: 20M items × 2 KB = 40 GB → fits in a small Redis cluster (3–6 nodes with replicas), and buys you the 90% hit ratio above. Doubling the cache to 80 GB might get you to 94% — diminishing returns, and that's the curve you're always riding.

Core intuition

A cache is a bet that the near future looks like the recent past. It pays when access is skewed and data changes slowly relative to how often it's read. It doesn't help uniform-random access over a huge keyspace (nothing is "hot"), write-heavy workloads (you're invalidating as fast as you fill), or data that must be perfectly fresh. Always ask: what's the read:write ratio, and how stale can this be?

Common mistakes
  • Cache stampede / thundering herd. A hot key expires and 10,000 concurrent requests all miss and hit the DB at once. Fix: request coalescing (single-flight), a short "lock" on recompute, or probabilistic early expiration.
  • No answer for consistency. "The DB was updated but the cache still has the old value." Decide: TTL-bounded staleness, delete-on-write (cache-aside), or write-through.
  • Caching negative results forever. A miss for a key that doesn't exist should be cached briefly (to stop lookups for garbage keys) but not indefinitely.
  • Unbounded cache. No eviction policy = OOM. Always cap size and set a policy.
  • Putting the cache on the critical write path with write-back and no durability. One crash, silent data loss.
  • Ignoring the client and CDN layers. The cheapest cache hit is the one that never leaves the user's browser or the edge POP.

Transactions — ACID & isolation levels

A transaction groups several reads and writes so they succeed or fail as a unit. ACID names the four guarantees: Atomicity (all the writes commit or none do — no partial state after a crash), Consistency (the transaction moves the DB from one valid state to another, respecting constraints — this "C" is the odd one out, more an application property than a DB mechanism), Isolation (concurrent transactions don't step on each other — ideally each runs as if alone), and Durability (once committed, it survives a crash — the write is on disk / replicated, not just in memory).

Isolation is where the interesting interview questions live, because full isolation (serializability) is expensive, so databases offer weaker isolation levels that permit specific anomalies in exchange for concurrency. The classic anomalies: dirty read (you read another transaction's uncommitted write), non-repeatable read (you read a row twice and get different values because someone committed in between), phantom read (you re-run a range query and new rows have appeared), and lost update (two read-modify-write cycles overlap and one is silently overwritten).

Isolation levelDirty readNon-repeatable readPhantomLost update
Read Uncommittedpossiblepossiblepossiblepossible
Read Committed (Postgres default)preventedpossiblepossiblepossible
Repeatable Read (MySQL/InnoDB default)preventedpreventedpossible*prevented**
Serializablepreventedpreventedpreventedprevented

* The SQL standard allows phantoms at Repeatable Read; InnoDB's next-key locking actually prevents most of them. ** Postgres Read Committed does not prevent lost update; its Repeatable Read (snapshot isolation) aborts the second writer with a serialization error.

A concrete race — the lost update

Two support agents both process a $80 refund against the same account, which has a $100 balance. The app does read-modify-write: 

-- both transactions run this logic, interleaved:
BEGIN;
SELECT balance FROM accounts WHERE id = 42;      -- both read 100
-- app computes new balance = 100 - 80 = 20
UPDATE accounts SET balance = 20 WHERE id = 42;  -- both write 20
COMMIT;

-- Timeline at READ COMMITTED:
--   T1: SELECT -> 100
--   T2: SELECT -> 100        (T1 hasn't committed; even if it had, T2 re-reads fresh each statement)
--   T1: UPDATE balance = 20
--   T1: COMMIT
--   T2: UPDATE balance = 20  (overwrites; T2 never saw T1's 20)
--   T2: COMMIT
-- Result: balance = 20. Two $80 refunds were issued but only $80 left the account.

How each level handles it:

  • Read Committed: anomaly occurs, as above. The second UPDATE blocks until T1 commits (row lock), then proceeds using the stale value it read earlier. Money lost.
  • Repeatable Read (snapshot isolation, Postgres): T2's UPDATE detects the row changed since its snapshot and aborts with could not serialize access due to concurrent update. The app retries the whole transaction, re-reads 20, computes −60, and (correctly) rejects it.
  • Serializable: same safe outcome; the engine guarantees some serial order exists.
  • Explicit locking at any level: SELECT ... FOR UPDATE takes a write lock on the read, so T2 blocks until T1 commits and then reads the fresh 20. This is the usual fix without bumping the isolation level.
  • Atomic write: UPDATE accounts SET balance = balance - 80 WHERE id = 42 AND balance >= 80 sidesteps the read entirely — one statement, and the WHERE guards the invariant.

A related anomaly, write skew, is nastier: two transactions read an overlapping set, each checks an invariant ("at least one doctor is on call"), each sees it holds, and each takes itself off call. No single row is double-written, so FOR UPDATE on individual rows doesn't save you — you need Serializable or a materialized lock on the predicate.

Capacity math — the cost of stronger isolation 
Contended row, read-modify-write, single DB node:

Read Committed + retry loop:  ~0 extra latency when uncontended;
   under contention, aborts/retries scale with concurrency C:
   ~ (C-1)/2 retries expected for the last writer -> throughput per row
   collapses toward  1 / (txn_latency)  as C grows.

FOR UPDATE (pessimistic):  serializes writers on that row.
   If txn holds the lock ~5 ms, max throughput for that row ~= 200 txn/s,
   regardless of how many app servers you add.

=> Per-row hotspots cap out around  1000 / lock_hold_ms  writes/sec.
   Design so the hot row isn't hot: shard the counter into N sub-rows and
   sum on read (N=100 sub-rows -> ~100x the write throughput).
Core intuition

Isolation levels are the database letting you buy concurrency by accepting a named, bounded risk. Default (Read Committed) is right for most reads. The moment your logic is read → decide → write on the same data, that default is unsafe — reach for an atomic UPDATE, SELECT ... FOR UPDATE, a compare-and-set version column, or snapshot isolation with a retry loop. Name which one and why.

Common mistakes
  • Assuming the default prevents lost updates. Read Committed does not.
  • "Just use Serializable everywhere." It works, but throughput on contended rows drops and you must handle serialization-failure retries in every transaction.
  • Confusing the "C" in ACID with CAP's "C". Different things — ACID consistency is constraint-preservation; CAP consistency is replica agreement.
  • Doing the arithmetic in the app when the DB can do it atomically. SET x = x + 1 beats SELECT then UPDATE.
  • Long transactions. Holding locks across a network call or user think-time throttles everyone behind you.
  • Forgetting distributed transactions are a different beast. Two-phase commit across services is slow and blocks on the coordinator; sagas (compensating actions) are the usual alternative.

SQL vs NoSQL — a decision framework

This is not "relational is old, NoSQL is web-scale." It's a set of questions about your data and access patterns. Walk them in order; the answers point at a category.

  1. Is your access pattern known and narrow, or ad-hoc? If you always fetch "user by id" and "posts by user id, newest first", a key-value or wide-column store models that directly and scales it trivially. If analysts will slice the data ten unforeseen ways tomorrow, you want SQL's ad-hoc joins and aggregations.
  2. Do you need multi-record ACID transactions? Money movement, inventory, bookings, anything with an invariant across rows — relational engines give you this for free and it is genuinely hard to bolt on later. Many document stores now offer single-document atomicity and some offer multi-document transactions, but with caveats and cost.
  3. What's the write volume and does it exceed one primary node? A single Postgres primary handles a lot (tens of thousands of writes/sec with good hardware). If you genuinely need more sustained write throughput than one node — or seamless multi-region writes — a horizontally-partitioned store (Cassandra, DynamoDB, Spanner) is built for it; sharding classic SQL yourself is possible but you give up cross-shard joins and transactions anyway.
  4. Is the schema stable or genuinely polymorphic? Stable-ish schema → SQL (and use JSONB columns for the rare flexible bits). Every record has wildly different fields (product catalog across categories, event payloads) → a document store fits the grain.
  5. What shape is the data? Deeply connected, "friends of friends who liked X" → a graph database. Time-ordered metrics → a time-series DB. Full-text search → a search engine (Elasticsearch) alongside your system of record, not instead of it.
  6. How strong is your consistency requirement? Need read-your-writes and strong consistency by default → single-primary SQL or Spanner-class. Fine with eventual consistency and tunable quorums → Dynamo-style.

Default recommendation: start with a relational database (Postgres). It's flexible, transactional, and one node goes further than people expect. Introduce a specialized store when a specific access pattern outgrows it — and say which pattern. The mature systems you're being asked to design almost always end up polyglot: Postgres for the core entities and money, Redis for cache and rate limits, a wide-column store for the high-volume append-only stream, a search index for text, an object store for blobs.

Capacity math — does one SQL node actually suffice? 
Product: 50M users, each does ~20 writes/day (posts, likes, profile edits).

Writes/day ........ 50M x 20         = 1,000,000,000  (1B)
Average write QPS . 1B / 86,400      ~= 11,600 w/s
Peak (3x) ......... ~35,000 w/s

One tuned Postgres primary: order of 10-20k simple write TPS sustained.
=> Peak is ~2x a single node. Options, cheapest first:
   1. Absorb the peak with a write-ahead queue + batching       (buys ~5x)
   2. Move the heaviest table (likes/feed) to a partitioned store
   3. Functional sharding: separate DBs per bounded context
   4. Full horizontal sharding by user_id                        (last resort)

   -> you are partitioning/archiving by time regardless of engine.

The lesson: "we need NoSQL for scale" is only true above a threshold you should be able to compute. Below it, reach for a queue, a cache, read replicas, and table partitioning first.

Core intuition

Relational databases optimize for flexibility of querying and correctness of writes at the cost of easy horizontal scaling. NoSQL stores flip that: pick your access pattern up front, model the data as answers to those queries (often denormalized, duplicated), and get near-linear scale-out — but ad-hoc queries and cross-entity invariants become your problem. Choose based on which set of costs you'd rather pay.

Common mistakes
  • Feature-table thinking. "NoSQL is schemaless and fast" — every store has trade-offs; name the access pattern that motivates the choice.
  • Picking NoSQL then needing transactions. Retrofitting cross-document atomicity is painful; know this before you commit.
  • Sharding SQL prematurely. You lose joins and transactions across shards — the very things you chose SQL for.
  • Using one store for everything. Forcing full-text search or a social graph into Postgres, or analytics onto Cassandra, fights the engine.
  • Ignoring operational maturity. "Postgres, because the team knows how to run it" is a legitimate, senior answer.

Microservices — the honest trade-offs

A microservice architecture splits a system into independently deployable services, each owning its own data and communicating over the network. The pitch is real: teams ship without coordinating a monolith release, each service scales and fails independently, and you can use the right language/store per service. But the costs are also real, and often undersold.

What you actually gain

  • Independent deploys. A 3-person team owns "payments" and releases twice a day without a company-wide train.
  • Independent scaling. The image-resize service runs 200 pods; the settings service runs 3. In a monolith you scale the whole thing to the hottest path.
  • Fault isolation — if you design for it. Recommendations being down shows an empty carousel, not a 500, provided the caller degrades gracefully.
  • Clear ownership. A bounded context with an API contract is easier to reason about and staff than a shared 2M-line codebase.

What it costs you

  • A distributed system, on purpose. Every in-process call that used to be nanoseconds and always-succeeds is now a network call that's milliseconds and sometimes-fails. You need timeouts, retries, circuit breakers, and idempotency everywhere.
  • No more distributed transactions (cheaply). "Create order + charge card + reserve stock" spanning three services means sagas with compensating actions, or an outbox pattern — and eventual consistency the product team has to accept.
  • Operational surface area. 40 services = 40 pipelines, dashboards, on-call rotations, and a service mesh or you drown in it. Distributed tracing stops being optional.
  • Data is scattered. A report that was one SQL join is now an API composition or a data pipeline into a warehouse.
  • Versioning and contracts. You can't change an API in lockstep with all callers; you support N and N−1 and run consumer-driven contract tests.
Capacity math — latency and availability of a fan-out 
A page render calls 6 services in sequence, each: p50 = 10 ms, p99 = 80 ms.

Sequential p50 total ....... 6 x 10 ms  = 60 ms      (fine)
Sequential p99-ish total ... dominated by tail; ~1 - 0.99^6 = 6% chance
   at least one call is at its p99 -> tail latency balloons.

Availability: 6 services each at 99.9% (independent), all required:
   0.999^6 = 0.994  ->  99.4%  = ~52 hours/year of page failures
   (worse than any single service)

Mitigations you must name:
   - parallelize independent calls (total ~= slowest, not sum)
   - make non-critical calls optional with fast fallbacks (feed w/o "who to follow")
   - hedged requests / tight timeouts + retries for the critical few
   - cache aggressively so most renders touch 1-2 services, not 6
Core intuition

Microservices trade local complexity (a big codebase) for distributed complexity (a network of small ones). That trade pays off past a certain team size, not a certain traffic level — the bottleneck it solves is human coordination. The right first answer for most designs is "a well-structured modular monolith, split out the one or two services that have a different scaling profile or a different team." Start splitting when deploy contention and ownership ambiguity — not performance — become the pain.

Common mistakes
  • Distributed monolith. Services so chatty and co-dependent that they must deploy together — all the costs, none of the benefits.
  • Shared database. Two services writing the same tables aren't independent; a schema change breaks both. Each service owns its schema.
  • Synchronous call chains. A → B → C → D synchronously means D's latency and downtime are everyone's. Use async events where you can.
  • Nano-services. A service per class. The network overhead and operational tax dwarf any benefit.
  • No platform investment. Adopting microservices without CI/CD, centralized logging, tracing, and a deployment platform first.
  • Splitting by technical layer (a "database service", a "business-logic service") instead of by business capability.

Distributed queues

A distributed queue (or log) sits between producers and consumers so they don't have to be available at the same time or run at the same speed. The producer writes a message and moves on; consumers pull and process at their own pace. This buys you three things: decoupling (the producer doesn't know or care who consumes), buffering (a traffic spike fills the queue instead of knocking over the downstream), and smoothing (a slow downstream just means the queue drains later).

Two broad shapes. A traditional message queue (RabbitMQ, SQS) hands each message to one consumer and deletes it on ack; good for task distribution ("resize this image", "send this email"). A distributed log (Kafka, Kinesis, Pulsar) keeps messages in an ordered, partitioned, append-only log with a retention window; consumers track their own offset and can replay. The log shape wins when you have multiple independent consumer groups, need ordering within a key, or want to reprocess history (rebuild a search index, backfill a new feature).

Delivery semantics. At-most-once (fire and forget, may lose messages). At-least-once (retry until acked, may deliver duplicates — the common default). Exactly-once is mostly a marketing term for "at-least-once delivery + idempotent processing"; you get it by making the consumer safe to run twice (dedupe on a message id, or make the write idempotent). Design every consumer as if it will see duplicates, because it will.

Ordering is only guaranteed within a partition. If you need "events for user 42 in order," partition by user_id so they all land on one partition — at the cost that one hot user can't be parallelized. Dead-letter queues catch messages that fail repeatedly so one poison message doesn't block the partition forever.

Capacity math — sizing consumers and spotting a backlog 
Producers emit:  avg 10,000 msg/s,  peak 50,000 msg/s
One consumer processes:  200 msg/s  (limited by a downstream API call ~5 ms each)

Consumers to keep up with the AVERAGE:  10,000 / 200  =  50 consumers
Consumers to keep up with the PEAK:     50,000 / 200  =  250 consumers

You don't provision for peak. Run ~60 consumers and let the queue absorb bursts:

  30-minute spike at 50k/s, drained by 60 consumers (12k/s capacity):
    inflow  = 50,000 x 1,800 s = 90,000,000 msgs
    drained = 12,000 x 1,800 s = 21,600,000 msgs
    backlog peak = 68,400,000 msgs
    time to clear after spike ends: 68.4M / (12,000 - 10,000) = ~9.5 hours  (!)

=> 60 is too few if spikes are frequent. Autoscale consumers on queue depth:
   target "drain any backlog within 15 min" -> need ~230 consumers during the spike.

Partitions must be >= max consumers you'll ever want:  pick 256 partitions now.
Retention: 50k/s x 1 KB x 7 days = ~30 TB on the brokers -> plan disk accordingly.
Core intuition

A queue converts a latency problem into a throughput problem. The user's request returns as soon as the message is enqueued (fast); the actual work happens later, sized for average load, with the queue as shock absorber. The catch: the caller now gets an ack, not a result, so the product must tolerate "we're processing your upload" and you must design for the queue backing up (alert on depth and on consumer lag, not just on errors).

Common mistakes
  • No idempotency. At-least-once means duplicates; a non-idempotent consumer double-charges, double-emails, double-increments.
  • Monitoring throughput but not lag. Consumers keeping up on average while falling permanently behind after each spike — watch backlog depth and oldest-message age.
  • Fewer partitions than desired parallelism. Consumer count is capped at partition count; you can't repartition Kafka cheaply.
  • Using a queue for request/response. If the caller must wait for the result anyway, the queue just adds a hop; use it for genuinely async work.
  • No dead-letter handling. One un-processable message retried forever blocks its partition.
  • Unbounded retention or unbounded queue. Decide the retention window and what happens when the queue is full (block producers? drop? shed load?).

Designing real systems — the framework

The interviewer is not grading the "right answer" — there isn't one. They are grading whether you drive the conversation in a structured way, make your assumptions explicit, and can defend your choices. Use these six steps, out loud, in order, and manage the clock (a 45-minute round: ~5 / 5 / 5 / 10 / 15 / 5).

  1. Requirements (5 min). Ask questions until scope is pinned. Separate functional ("shorten a URL, redirect, custom aliases, analytics?") from non-functional ("how much traffic, read:write ratio, latency target, how available, how consistent"). Write the agreed list down. Explicitly state what's out of scope. The single most common failure is designing the wrong system because you never clarified.
  2. Capacity estimation (5 min). Turn the scale into numbers: QPS (average and peak), storage per year, bandwidth, memory for caches. These numbers choose the architecture — they tell you whether it's one server or a fleet, whether the data fits on a node, whether you need a cache. Round aggressively; the interviewer wants the method, not precision.
  3. API design (5 min). Define the handful of endpoints: method, path, key params, response, and error cases. This nails down the contract before you draw boxes and often surfaces a requirement you missed ("wait, who owns the custom alias namespace?").
  4. High-level components (10 min). Draw the boxes: clients → LB → app tier → datastores / cache / queue. Show the data flow for the main read path and the main write path. Keep it boring and standard; this is the skeleton, not the interesting part.
  5. Deep dive (15 min). The interviewer picks (or you propose) the one hard part and you go deep: the data model and partitioning, the algorithm (key generation, ranking, dedup), the consistency story, the failure modes, the hot-key or celebrity problem. This is where the signal is. Have an opinion.
  6. Trade-offs & wrap-up (5 min). State what you chose and what you gave up: "SQL + a counter service, so I get strong uniqueness and simple ops, at the cost of the counter being a scaling chokepoint I'd shard by range." Name what you'd monitor, what breaks first at 10× scale, and what you'd do next.
Core intuition

Every step feeds the next: requirements set the numbers, the numbers pick the components, the components have trade-offs, the deep dive defends one of them. If you skip estimation you'll over- or under-build; if you skip the API you'll wave your hands at the data model; if you skip trade-offs you look like you think your design is perfect. The framework is the same for every prompt — only the deep dive changes.

Common mistakes
  • Jumping to boxes in minute two. No requirements, no numbers — you're designing blind.
  • Estimation theatre. Computing QPS and then never using it. Tie each number to a decision.
  • Boiling the ocean. Trying to design analytics, spam detection, and multi-region all at once. Nail the core, mention the rest as extensions.
  • Going silent to think. Narrate. The interviewer can only grade what you say.
  • No opinion. "We could do A or B or C" without picking one and justifying it reads as inexperience.
  • Ignoring the interviewer's nudges. "How would that handle a burst?" is a hint about where they want depth — follow it.

Worked example — URL shortener (end to end)

Running the framework top to bottom. This is the canonical warm-up question; doing it crisply in 30 minutes is a strong baseline signal.

1 · Requirements

Functional:

  • Given a long URL, return a short URL on a domain we own (sho.rt/aB3xK9q).
  • Hitting the short URL redirects (HTTP 301/302) to the long URL.
  • Optional custom alias (sho.rt/my-launch).
  • Optional expiry (link stops working after a date).
  • Basic analytics: click count per link. (Kept lightweight; full analytics is out of scope.)

Non-functional:

  • Scale: assume 100M new URLs/day; read:write = 100:1.
  • Redirect latency: < 50 ms p99 — this is the money path.
  • Availability: redirects should be highly available (99.99%); the create path can be a notch lower.
  • Short codes must be non-guessable-ish and not expose a sequential counter directly.
  • Links are effectively permanent unless an expiry is set.

2 · Capacity estimation

WRITES
  New URLs/day ............ 100,000,000
  Write QPS (avg) ........ 100M / 86,400        ~= 1,160 /s
  Write QPS (peak, 3x) ... ~3,500 /s

READS (redirects)
  Reads/day .............. 100 x 100M = 10,000,000,000  (10B)
  Read QPS (avg) ........ 10B / 86,400          ~= 115,000 /s
  Read QPS (peak, 3x) ... ~350,000 /s

STORAGE  (per row)
  short code ........ 7 bytes
  long URL ......... ~200 bytes (avg; cap at 2 KB)
  metadata ......... created_at 8, expiry 8, owner_id 8, click_count 8  = 32 bytes
  row + index overhead .. call it ~500 bytes/row
  Per day .......... 100M x 500 B          = 50 GB/day
  Per year ......... 50 GB x 365           ~= 18 TB/year
  5 years ......... ~90 TB   -> fits comfortably on a modest sharded cluster

BANDWIDTH
  Redirect response ~ 500 B (headers + Location)
  Egress ........... 350,000 /s x 500 B    ~= 175 MB/s at peak  (trivial)

CACHE  (hot set)
  Assume 20% of links get 80% of clicks; cache the hot 20% of a day's links
  plus a rolling week: ~ 150M entries x 500 B  ~= 75 GB
  -> a Redis cluster of ~6 nodes (with replicas) holds the working set

KEY SPACE  (base62: a-z A-Z 0-9)
  6 chars: 62^6  ~= 5.7 x 10^10   -> exhausted in  57B / 100M  ~= 570 days  (too soon)
  7 chars: 62^7  ~= 3.5 x 10^12   -> lasts  3.5T / 100M  ~= 96 years         (use 7)

What the numbers decided: 7-character codes; a cache is mandatory (115k read QPS vs a DB that does maybe 20–50k); the write path is small enough for a single logical primary (or a lightly sharded one); total storage is large but not exotic, so partition by code and move on.

3 · API design

POST /api/v1/urls
  body:  { "longUrl": "https://...", "customAlias": "my-launch"?, "expiresAt": "2027-01-01"? }
  201 -> { "shortUrl": "https://sho.rt/aB3xK9q", "code": "aB3xK9q", "expiresAt": null }
  409 -> custom alias already taken
  400 -> malformed URL

GET /{code}
  302 -> Location: https://original-long-url        (redirect; the hot path)
  404 -> unknown or expired code
  410 -> known but expired (optional, nicer than 404)

GET /api/v1/urls/{code}          (owner only)
  200 -> { code, longUrl, createdAt, expiresAt, clickCount }

DELETE /api/v1/urls/{code}       (owner only)  -> 204

301 (permanent) lets browsers cache the redirect — great for load, but you lose per-click analytics and can't easily change the target. 302 (found) keeps every click coming to you. Given we want click counts, use 302 and cache aggressively server-side.

4 · High-level components

              (write path)                         (read path - 100x heavier)

  Client --POST--> [ LB ] --> [ Write API ]        Client --GET /code--> [ LB ]
                                  |                                        |
                        [ Key Generation ]                        [ Redirect API ]
                                  |                                    |       |
                                  v                              (hit) |       | (miss)
                            [ Metadata DB ] <-------- read-through -----+       v
                            (partitioned by code)                        [ Cache: Redis ]
                                  |                                          |
                                  +--> [ Analytics queue ] <----------- click event
                                            |
                                      [ Click aggregator ] --> updates click_count
  • Redirect API is its own stateless service, scaled and deployed independently from the write side because it carries 100× the traffic and a stricter SLA.
  • Cache (Redis) holds code → longUrl. Read-through: on miss, fetch from DB, populate with a TTL (say 24h) plus refresh-on-access. Hit ratio target > 95%.
  • Metadata DB: the system of record. code (PK), long_url, created_at, expires_at, owner_id. Partition by a hash of code so lookups are single-shard and point-queries.
  • Analytics is fully async: the redirect fires a click event onto a queue and returns immediately; an aggregator batches increments to click_count (or a separate counter store). A lost click event is acceptable; a slow redirect is not.

5 · Deep dive — generating the short code

Three approaches; pick one and defend it.

(a) Hash the URL, take a prefix. base62(md5(longUrl + salt))[:7]. Stateless, no coordination. Problems: collisions (two URLs → same 7 chars) must be detected (insert with a uniqueness constraint; on conflict, re-hash with a bumped salt) and the same URL submitted twice yields the same code unless you add per-request entropy — sometimes desired (dedup), usually not.

(b) Distributed counter + base62 encode. A monotonically increasing 64-bit id, base62-encoded, gives collision-free codes. Get the ids without a global bottleneck by handing out ranges: a coordination service (or an auto-increment table) gives each Write API instance a block of 100,000 ids at a time; the instance encodes locally and only talks to the coordinator once per 100k URLs. At peak 3,500 writes/s that's one coordinator call every ~30 seconds — trivial. 

counter value 1,000,000,007  --base62-->  "15FTGp7"   (7 chars)
To avoid exposing "the 1,000,000,007th link" and to make codes look random,
scramble the id before encoding with a fixed bijective transform:
  scrambled = (id * ODD_CONSTANT) XOR MASK   (mod 62^7), fully reversible
=> sequential ids, non-sequential-looking codes, still zero collisions.

(c) Pre-generated key pool. A separate service generates random unused 7-char codes offline, validates uniqueness once, and stores millions of them in a "available keys" table. The Write API pops one under a transaction. Simple hot path, no encoding logic, but an extra service and storage to run.

Choice: (b) counter + range allocation + scramble. Zero collisions (no retry loop on the write path), no per-request coordination, codes don't leak the sequence, and the only stateful piece is a range allocator that's called ~once a minute. Custom aliases are a separate INSERT into the same table with the user-supplied code and a uniqueness constraint — a 409 on conflict.

Deep dive — the redirect path, traced 
GET sho.rt/aB3xK9q

1. LB -> nearest Redirect API pod                             (~1 ms)
2. Redis GET code:aB3xK9q
     HIT  (>95%): returns longUrl                             (~1 ms)     --> total ~5 ms
     MISS (<5%):  SELECT long_url, expires_at FROM urls
                  WHERE code = 'aB3xK9q'   (single shard)      (~5-10 ms)
                  SETEX code:aB3xK9q 86400 
3. if expires_at in the past -> 410, and delete cache key
4. else  302 Location: 
5. fire-and-forget: XADD clicks * code aB3xK9q ts        (non-blocking)

p99 budget 50 ms: cache hit path ~5 ms, miss path ~15 ms, both well under.
Even a total analytics outage doesn't touch steps 1-4.

Other deep-dive threads to be ready for:

  • Hot link (a tweet goes viral): one code gets 50k req/s. It's a single cache key, so Redis handles it — but protect against the key expiring under load with single-flight recompute, or pin ultra-hot codes with no TTL. A CDN / edge cache on the 302 also absorbs it.
  • Cache node loss: consistent hashing across Redis nodes means losing one drops ~1/N of the hot set; those become DB reads. With N=6 that's a ~16% miss spike → DB goes from ~5k to maybe ~25k QPS briefly — survivable with read replicas, and the cache refills in minutes.
  • Expiry cleanup: don't scan. Lazily 410 + delete on access, plus a low-priority batch job that deletes rows past expires_at partition by partition.
  • Abuse / malware URLs: check the long URL against a safe-browsing list on create (async is fine), and support takedown by flagging the row.
  • Multi-region: the read path is read-mostly and tolerant of seconds of staleness, so replicate the DB and cache to each region and serve redirects locally; route writes to a home region.

6 · Trade-offs & wrap-up

  • 302 over 301: chose per-click visibility and mutable targets over letting browsers cache the redirect. If analytics didn't matter, 301 + long cache would cut our read traffic by a large factor.
  • Counter + scramble over hashing: chose a collision-free write path (no retry loop) and a tiny coordination cost over the fully-stateless hash approach.
  • Cache is load-bearing, not optional: a Redis outage takes the DB from ~5k to ~115k read QPS — it would fall over. Mitigation: multi-node cache with replicas, read replicas on the DB as a backstop, and a small in-process LRU on each Redirect pod for the very hottest codes.
  • Analytics is best-effort: we accept losing some click events on a queue or aggregator failure in exchange for never slowing or failing a redirect.
  • Storage grows ~18 TB/year forever: partition by code hash from day one; archive cold rows (no clicks in a year) to cheaper storage.
  • What breaks first at 10×: the DB write path (~35k/s) and cache memory (~750 GB). Both scale horizontally by the partitioning we already have — this is why we picked hash partitioning on code up front.
