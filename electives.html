Advanced DSA

You already have the core patterns from DSA · Linear and DSA · Non-linear. This is the next layer — the structures and recurrences that show up in the harder online-assessment questions and the occasional "we want to see how you handle something unfamiliar" onsite problem.

Segment trees

A segment tree answers range queries (sum, min, max, gcd) and applies updates on an array, both in O(log n), after an O(n) build. Each node covers a contiguous range; a leaf covers one element, an internal node's value is built from its two children. A query splits into O(log n) node ranges that exactly tile the query interval; a point update walks one root-to-leaf path and re-combines on the way back up.

Lazy propagation extends this to range updates ("add 5 to every element in [l, r]"). Instead of touching every leaf, you stamp the update on the highest nodes fully inside the range and store a pending "lazy" value; you push it down to children only when a later query or update actually needs to descend through that node. Still O(log n) per operation.

Recursive segment tree — range-sum, range-add (lazy)

class SegTree:
    def __init__(self, a):
        self.n = len(a)
        self.tree = [0] * (4 * self.n)
        self.lazy = [0] * (4 * self.n)
        self._build(a, 1, 0, self.n - 1)

    def _build(self, a, node, lo, hi):
        if lo == hi:
            self.tree[node] = a[lo]; return
        mid = (lo + hi) // 2
        self._build(a, 2*node,   lo,    mid)
        self._build(a, 2*node+1, mid+1, hi)
        self.tree[node] = self.tree[2*node] + self.tree[2*node+1]

    def _push(self, node, lo, hi):           # apply & propagate pending add
        if self.lazy[node]:
            self.tree[node] += self.lazy[node] * (hi - lo + 1)
            if lo != hi:
                self.lazy[2*node]   += self.lazy[node]
                self.lazy[2*node+1] += self.lazy[node]
            self.lazy[node] = 0

    def update(self, l, r, val, node=1, lo=0, hi=None):
        if hi is None: hi = self.n - 1
        self._push(node, lo, hi)
        if r < lo or hi < l:            return          # no overlap
        if l <= lo and hi <= r:                          # full overlap
            self.lazy[node] += val
            self._push(node, lo, hi); return
        mid = (lo + hi) // 2                             # partial overlap
        self.update(l, r, val, 2*node,   lo,    mid)
        self.update(l, r, val, 2*node+1, mid+1, hi)
        self.tree[node] = self.tree[2*node] + self.tree[2*node+1]

    def query(self, l, r, node=1, lo=0, hi=None):
        if hi is None: hi = self.n - 1
        self._push(node, lo, hi)
        if r < lo or hi < l:      return 0
        if l <= lo and hi <= r:   return self.tree[node]
        mid = (lo + hi) // 2
        return (self.query(l, r, 2*node,   lo,    mid) +
                self.query(l, r, 2*node+1, mid+1, hi))
Core intuition

A segment tree is a balanced binary tree over array intervals where every node stores an aggregate of its range. Any interval decomposes into O(log n) node ranges, so any associative query is O(log n). If you only need prefix sums with point updates, a Fenwick / BIT is simpler and faster (same big-O, tiny constant). Reach for a segment tree when you need arbitrary range queries, range updates, or non-invertible ops like min/max.

Common mistakes
  • Sizing tree as 2n for the recursive version — use 4n to be safe (or 2 * 2^ceil(log2 n)).
  • Forgetting to push lazy before reading a node, or before recursing into children.
  • Using min/max with a wrong identity — 0 is fine for sum, but you need +inf / -inf for min / max.
  • Reaching for a segment tree when sorting + prefix sums, or a heap, already solves it.

Practice: Range Sum Query – Mutable (LC 307), Range Sum Query 2D – Mutable (LC 308), Count of Range Sum (LC 327), My Calendar III (LC 732), Falling Squares (LC 699), Longest Increasing Subsequence II (LC 2407).

String matching — KMP

Naive substring search re-scans the text every time a match breaks: O(n·m). KMP (Knuth–Morris–Pratt) gets O(n + m) by precomputing, for the pattern, a prefix function (a.k.a. failure / LPS array): lps[i] = length of the longest proper prefix of pattern[0..i] that is also a suffix of it. When a mismatch happens at pattern index j, you don't restart — you jump to lps[j-1], because those characters are guaranteed to already match.

Prefix function + search

def build_lps(p):
    lps = [0] * len(p)
    k = 0                                # length of current longest prefix-suffix
    for i in range(1, len(p)):
        while k > 0 and p[i] != p[k]:
            k = lps[k-1]                 # fall back
        if p[i] == p[k]:
            k += 1
        lps[i] = k
    return lps

def kmp(text, p):
    if not p: return 0
    lps = build_lps(p)
    k = 0
    for i, ch in enumerate(text):
        while k > 0 and ch != p[k]:
            k = lps[k-1]
        if ch == p[k]:
            k += 1
        if k == len(p):
            return i - k + 1            # first match start index
    return -1

# lps("ABABC") -> [0,0,1,2,0]   ;   lps("AAAA") -> [0,1,2,3]
Core intuition

The lps array is "how much of what I've already matched can I reuse after a mismatch." Rabin–Karp (rolling hash) and the Z-function solve the same problem; KMP is the one interviewers most often ask you to derive. The prefix function alone — without the search — answers a surprising number of string questions (periodicity, shortest repeating unit, shortest palindrome by prefixing).

Common mistakes
  • Confusing "proper prefix" — it can't be the whole string, so lps[i] < i + 1 always.
  • Using lps[k] instead of lps[k-1] on fallback.
  • Not resetting / continuing k correctly after a full match if you need all matches (set k = lps[k-1]).

Practice: Implement strStr() (LC 28), Repeated Substring Pattern (LC 459), Shortest Palindrome (LC 214), Longest Happy Prefix (LC 1392), Find Beautiful Indices in the Given Array I/II (LC 3006 / 3008), Sum of Scores of Built Strings (LC 2223, Z-function).

Advanced DP

Beyond the classic 1-D / grid recurrences from DSA · Non-linear, four shapes recur:

Bitmask DP — minimum cost to assign n tasks to n workers

def min_assignment(cost):                 # cost[worker][task]
    n = len(cost)
    FULL = (1 << n) - 1
    from functools import lru_cache

    @lru_cache(None)
    def dp(worker, mask):                 # mask = set of tasks already taken
        if worker == n:
            return 0
        best = float('inf')
        for task in range(n):
            if not (mask >> task) & 1:
                best = min(best, cost[worker][task] + dp(worker + 1, mask | (1 << task)))
        return best

    return dp(0, 0)
Core intuition

The state is still "the smallest thing that makes the rest of the problem independent of how you got here." Bitmask = the set matters but the order within it doesn't. Interval = the answer for a range is built from a split point, and you often iterate by increasing length. Tree = children are independent given the parent's choice, so combine bottom-up.

Common mistakes
  • Bitmask with n > ~22 — 2ⁿ blows up; the intended solution is something else.
  • Interval DP iterating i and j in the wrong order — you need smaller intervals solved first (loop on length, or memoize).
  • Tree DP with recursion depth — a 10⁵-node path graph overflows the default stack; use an explicit stack or raise the limit.
  • Digit DP forgetting the tight flag — once a prefix is strictly less than N's prefix, later digits are unconstrained.

Practice: Partition to K Equal Sum Subsets (LC 698), Shortest Path Visiting All Nodes (LC 847), Number of Ways to Wear Different Hats to Each Other (LC 1434), Burst Balloons (LC 312), Minimum Cost to Merge Stones (LC 1000), House Robber III (LC 337), Numbers At Most N Given Digit Set (LC 902), Count of Integers (LC 2827).

Dijkstra with a binary heap

import heapq

def dijkstra(n, adj, src):               # adj[u] = list of (v, weight)
    dist = [float('inf')] * n
    dist[src] = 0
    pq = [(0, src)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist[u]:                   # stale entry — skip
            continue
        for v, w in adj[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(pq, (dist[v], v))
    return dist
Core intuition

Dijkstra is BFS where the queue is a priority queue — it always finalizes the closest unfinalized node, which only works because no negative edge can later make a "finished" node cheaper. When you see negative weights, switch to Bellman–Ford (and one extra relaxation round that still improves something ⇒ negative cycle). "Shortest path with at most K stops" is Bellman–Ford with K iterations, not Dijkstra.

Common mistakes
  • Dijkstra with negative edges — silently wrong, not an error.
  • Not skipping stale heap entries (d > dist[u]) — still correct but degrades toward O(E²) and can TLE.
  • Floyd–Warshall loop order — k (the intermediate) must be the outermost loop.
  • MST when you actually need shortest paths — "connect all points cheaply" is MST; "get from A to B cheaply" is not.

Practice: Network Delay Time (LC 743), Cheapest Flights Within K Stops (LC 787), Path with Minimum Effort (LC 1631), Swim in Rising Water (LC 778), Min Cost to Connect All Points (LC 1584), Find the City With the Smallest Number of Neighbors at a Threshold Distance (LC 1334), Maximum Number of Non-overlapping... / bipartite-matching flavored (LC 1349).

System Design Case Studies

Short design sketches, not full write-ups — HLD has the framework and the deep worked example. For each: the requirements that shape it, the core architecture, and the one or two decisions an interviewer will actually push on. Two are backend HLD; two are frontend-architecture questions (increasingly common even for backend roles at product companies).

Chess game website (HLD)

Functional: real-time 2-player games, matchmaking by rating, move validation, clocks, spectators, reconnection, game history (PGN), Elo updates. Non-functional: low latency (<100 ms move round-trip), fairness (server-authoritative), survive a dropped connection.

Architecture. Clients hold a persistent WebSocket to a connection gateway. A game service owns live game state — one logical "game actor" per game, pinned to a server by consistent hashing on game_id, with state mirrored in Redis so another node can take over on failure. Every move is validated server-side against the authoritative board (never trust the client); the server broadcasts the new state to both players and any spectators via pub/sub. Finished games are written to Postgres (games, moves) for history and to a queue that triggers async Elo recalculation. Matchmaking is a queue keyed by rating bucket; if no match in N seconds, widen the bucket.

Capacity math

100k concurrent games ⇒ 200k connected players. Peak ~2 messages/sec per game (a move + a clock tick) ⇒ ~200k msg/s across the fleet — trivial per node if you shard. Live state ≈ 2 KB/game (board, clocks, history pointer) ⇒ ~200 MB, fits in Redis easily. The scaling pressure is connections, not compute: ~10k WebSockets/node ⇒ ~20 gateway nodes.

Interviewer probes
  • Clocks: server is the source of truth; send remaining-time on each move, tolerate client drift, handle "flag fall" on the server.
  • Reconnection: game actor keeps the seat for ~30–60 s; client resyncs full state on reconnect.
  • Cheating / engine use: out of scope for HLD, but mention move-time analysis and post-game review as an async pipeline.
  • Why not peer-to-peer: can't trust either client; NAT traversal; no authoritative clock.

Live streaming — Hotstar-style (HLD)

Functional: live sports to 10M+ concurrent viewers, adaptive bitrate, ~10–30 s glass-to-glass latency, VOD replay after, live concurrency counter. Non-functional: survive a massive spike at toss/kickoff, degrade gracefully, keep cost sane.

Ingest → package. The broadcaster feed hits a transcoder that produces multiple renditions (240p → 1080p) chopped into 2–6 s segments plus a rolling manifest (HLS/DASH). Segments land on an origin store. Delivery is origin → multi-CDN → edge → player. The player downloads the manifest, then segments over plain HTTP, stepping bitrate up/down based on measured bandwidth and buffer health. Everything rides on CDN cache-hit ratio — the origin only serves cache-fill.

Capacity math

10M viewers × ~5 Mbps average rendition ⇒ ~50 Tbps egress. That is categorically a CDN job; origin sees maybe 1 request per segment per edge PoP (say 200 PoPs × 1 segment/4 s ⇒ ~50 req/s to origin). Live concurrency counter: don't count exactly — sample or use probabilistic aggregation (HyperLogLog-style) and accept ±1–2%.

Interviewer probes
  • Spike at start: pre-scale transcoders and API tier, pre-warm CDN, use a "waiting room" / staged admission, cap starting bitrate.
  • Latency vs scale: smaller segments = lower latency but more requests and worse cache efficiency; LL-HLS / chunked transfer for the low-latency tier.
  • Ads: server-side ad insertion (SSAI) stitches ad segments into the same stream so ad-blockers and buffering behave.
  • VOD: the same segments, kept; just a static manifest afterward.

Netflix frontend architecture

The interesting problem is one product across TV, web, and mobile, each with different capabilities, all showing the same personalized "rows of titles" home screen fast.

  • Backend-for-frontend (BFF). Each client class talks to its own API layer (Netflix moved from Falcor to a federated GraphQL gateway) that aggregates dozens of microservices into exactly the shape that client needs — so the TV app isn't over-fetching web-only fields.
  • The home page is a "list of lists." Personalized rows ("Because you watched…", "Trending") are computed server-side; the client renders the first screenful and lazy-loads more rows and artwork as you scroll. Artwork itself is personalized and served from an image CDN sized per device.
  • Resilience over correctness. If the personalization service is slow, fall back to generic popular rows; render skeleton UI immediately; stale-while-revalidate cached responses. A blank screen is the only real failure.
  • Performance. Route-level code splitting, aggressive prefetch of the likely-next navigation, preloaded video preview on hover/focus, and a built-in A/B framework — practically every UI element is an experiment, so the architecture assumes multiple variants at once.
  • Telemetry. Real-user monitoring (startup time, rebuffer rate, errors) streams back continuously and gates rollouts.
Core intuition

Multi-platform product frontends converge on the same moves: a BFF per client to control payload shape, server-driven personalized layout, lazy-loading below the fold, a fallback for every remote dependency, and experimentation as a first-class concern rather than a bolt-on.

WhatsApp Web frontend design

A browser client for an end-to-end encrypted messenger that historically treated the phone as the source of truth (multi-device now gives the browser its own identity keys).

  • Pairing. The browser generates a keypair and shows a QR code encoding its public key; the phone scans it and establishes an encrypted session. Keys live in IndexedDB; losing them means re-pairing.
  • Transport. A single WebSocket to the server carries encrypted message payloads. The server routes ciphertext and never sees plaintext.
  • Local-first store. Messages, chats, contacts, and media metadata are kept in IndexedDB. The UI renders entirely from local state; the network only delivers deltas, which are decrypted and merged.
  • Offline & sync. A service worker + an outbound queue hold messages typed while offline; on reconnect the client replays the queue and pulls missed deltas.
  • Optimistic UI + status state machine. A sent message renders instantly as pending, then transitions sent → delivered → read as acks arrive (the check-mark states).
  • Media. Thumbnails first, full media downloaded on demand, decrypted to a blob: URL for display.
Things to get right
  • Never send keys or plaintext to the server — the whole model breaks.
  • IndexedDB is the database, not a cache — schema migrations, quota handling, and eviction all matter.
  • Message ordering across multiple devices needs logical timestamps / per-chat sequence, not wall-clock.
  • Large chat history — virtualize the message list, page from IndexedDB, don't hold 50k DOM nodes.

Computer Networks Essentials

Enough to answer "what happens when you type a URL and press enter" without hand-waving, and to reason about latency, retries, and why an API call is slow.

DNS

DNS resolves a name (api.example.com) to an IP address using a hierarchy: root servers → TLD servers (.com) → the domain's authoritative server. Your machine asks a recursive resolver (your ISP's, or 8.8.8.8 / 1.1.1.1), which does the walking and caches each answer for its TTL. Most lookups never leave the resolver's cache.

Cold lookup for api.example.com 
stub resolver (OS)  ─▶ recursive resolver:  "api.example.com A?"
recursive ─▶ root:        "who handles .com?"      ◀─ NS for .com
recursive ─▶ .com TLD:    "who handles example.com?" ◀─ NS for example.com
recursive ─▶ authoritative: "api.example.com A?"   ◀─ 93.184.x.x  (TTL 300)
recursive ─▶ stub:         93.184.x.x   (cached for 300s at every hop)

Record types worth knowing: A (IPv4), AAAA (IPv6), CNAME (alias to another name), MX (mail), NS (delegation), TXT (SPF/DKIM/verification). Transport is UDP port 53 (falls back to TCP for large responses / zone transfers); DoH/DoT wrap it in HTTPS/TLS for privacy. Root and TLD servers use anycast so "one IP" is answered by the nearest of many machines.

Common misconceptions
  • "DNS returns one IP." It often returns several; the client picks one, and round-robin / GeoDNS / latency-based routing is done here.
  • Ignoring TTL in incident response — a bad record with TTL 86400 is cached for a day.
  • CNAME at the zone apex — not allowed by the spec; providers fake it with "ALIAS/ANAME".

TCP/IP

The model has four layers: link (Ethernet/Wi-Fi), internet (IP — addressing and routing, best-effort, no guarantees), transport (TCP / UDP), and application (HTTP, DNS, SMTP). IP gets a packet toward a host; TCP or UDP decides what "delivery" means.

TCPUDP
Setup3-way handshake (SYN → SYN-ACK → ACK)None — just send
GuaranteesReliable, ordered, de-duplicatedNone; packets may drop, reorder, duplicate
ControlFlow control (receiver window) + congestion control (slow start, AIMD)None (app must handle)
OverheadHigher (state, acks, retransmit)Minimal
Use forHTTP, DB connections, anything that must be correctDNS, VoIP, live video, games, QUIC

TCP reliability = sequence numbers + cumulative ACKs + retransmission on timeout / triple-duplicate ACK. Congestion control keeps the network from collapsing: start small, ramp exponentially (slow start), then additive-increase / multiplicative-decrease on loss. Teardown is a FIN from each side. Head-of-line blocking — one lost segment stalls everything behind it — is why HTTP/3 runs over QUIC (on UDP), which gives independent streams.

Core intuition

IP is the postal system (addressed, best-effort, might lose your letter). TCP is registered mail with tracking and re-sends, at the cost of a setup round-trip and bookkeeping. UDP is shouting across the room — fast, and it's on you if it's not heard.

HTTP request lifecycle

"You type https://example.com and press Enter":

  1. URL parse → scheme, host, path.
  2. DNS → example.com to an IP (cache → resolver → hierarchy).
  3. TCP handshake to the IP on port 443 (1 RTT).
  4. TLS handshake — validate the certificate chain, agree on keys (1–2 RTT; 0–1 with TLS 1.3 resumption).
  5. HTTP request — GET / HTTP/2 + headers (Host, cookies, Accept, User-Agent).
  6. Server — load balancer → app → maybe DB/cache → builds the response.
  7. Response — status line (200, 301, 404, 500), headers (Content-Type, Cache-Control, ETag, Set-Cookie), body.
  8. Client — parse HTML, discover sub-resources (CSS/JS/img), repeat (mostly on the same connection), render.

Versions: HTTP/1.1 = one request at a time per connection (browsers open ~6). HTTP/2 = multiplexing many streams over one TCP connection + header compression (HPACK). HTTP/3 = same, over QUIC/UDP, removing TCP head-of-line blocking. Caching: Cache-Control: max-age for freshness; ETag + If-None-Match → 304 Not Modified to revalidate cheaply. CORS: a cross-origin non-simple request triggers an OPTIONS preflight the server must approve.

Common mistakes
  • Confusing 301 and 302 — 301 is permanent and cached hard; 302/307 is temporary.
  • Thinking HTTP/2 removes head-of-line blocking — it removes it at the HTTP layer, not the TCP layer; that's HTTP/3's job.
  • "HTTPS encrypts the URL" — path and query are encrypted; the domain (SNI) and IP are visible.
  • Ignoring connection reuse — keep-alive / a warm pool saves the TCP+TLS round-trips on every call after the first.

Operating Systems Essentials

The three areas interviewers actually ask a backend engineer about: concurrency units, virtual memory, and the scheduler.

Processes vs threads

ProcessThread
Address spaceOwn, isolated (separate page tables)Shared with other threads in the process
OwnsCode, heap, globals, file descriptors, PCBStack, registers, program counter, thread-local
Crash blast radiusContained to the processTakes down the whole process
Context switchExpensive (TLB flush, page-table swap)Cheaper (same address space)
CommunicationIPC: pipes, sockets, shared memory, message queuesShared memory directly — needs locks

Threads sharing memory is the whole point and the whole danger: race conditions require mutexes / semaphores / atomics, and careless locking causes deadlock (circular wait — break it by always acquiring locks in a fixed order). Choose multi-process for isolation and to sidestep a runtime global lock (Python's GIL, historically); multi-thread for shared state and cheap switching. fork() duplicates a process (copy-on-write); a child not reaped becomes a zombie, a parent that dies first leaves an orphan adopted by init.

Core intuition

A process is an isolated container with its own memory; threads are workers inside that share everything by default. "Shared by default" is why threads are fast to coordinate and easy to corrupt.

Memory management

Each process sees a private, contiguous virtual address space. The MMU translates virtual → physical addresses per access using page tables, caching recent translations in the TLB. Memory is handed out in fixed-size pages (typically 4 KB).

  • Page fault: accessing a page not currently in RAM → the OS traps, loads it from disk (or the executable, or zero-fills), updates the page table, resumes. A minor fault just needs a mapping; a major fault hits disk.
  • Demand paging: pages are loaded only when first touched, so processes start fast and use less RAM.
  • Replacement: when RAM is full, evict a page — approximations of LRU (the clock/second-chance algorithm) in practice.
  • Thrashing: too many processes, not enough RAM → the system spends all its time paging. Fix by reducing multiprogramming (working-set model).
  • Fragmentation: paging kills external fragmentation but causes a little internal (the slack in the last page).
  • Stack vs heap: stack is per-thread, LIFO, auto-managed, small; heap is process-wide, explicitly managed (malloc/GC), can fragment.
Common mistakes
  • "Virtual memory = swap." Virtual memory is the address-translation abstraction; swap is just one thing it enables.
  • Assuming malloc touches RAM — on Linux it often just extends the mapping; physical pages appear on first write (and overcommit can OOM-kill later).
  • Ignoring the TLB — a TLB miss is a real cost; huge pages exist to reduce it.

CPU scheduling

The scheduler decides which ready thread runs next on a core. Goals trade off: throughput, latency / response time, fairness, and CPU utilization.

AlgorithmIdeaWeakness
FCFSRun in arrival orderConvoy effect — one long job stalls everyone
SJF / SRTFShortest (remaining) job first — optimal average waitNeeds to know burst length; starves long jobs
Round RobinFixed time quantum, cycle throughQuantum too small → switch overhead; too big → FCFS
PriorityHighest priority firstStarvation — fix with aging
MLFQMultiple queues; jobs that use full quanta sink, I/O-bound jobs stay highTuning-heavy

Preemptive (the OS can interrupt a running thread — needed for responsiveness and to enforce fairness) vs non-preemptive (thread runs until it yields/blocks). Every switch has a context-switch cost (save/restore registers, possible TLB and cache effects). Real systems: Linux CFS tracks each task's vruntime (virtual runtime, weighted by nice value) in a red-black tree and always runs the task with the smallest vruntime — "fair" rather than strict priority. Metrics to define: turnaround (finish − arrival), waiting (turnaround − burst), response (first-run − arrival).

Core intuition

There's no universally best scheduler — batch systems optimize throughput, interactive systems optimize response time. Modern general-purpose schedulers (CFS) aim for fairness: everyone gets a proportional slice, and I/O-bound tasks are implicitly favored because they rarely use their whole slice.

React Native + Expo basics

React Native lets you write UI as React components that render to real native views (not a webview) on iOS and Android from one codebase. Expo is the batteries-included toolchain on top: a managed build service (EAS), over-the-air JS updates, and pre-packaged native modules (camera, location, notifications) so you rarely touch Xcode/Gradle.

  • Core components: View (≈ div), Text, Image, ScrollView, FlatList (virtualized list — use it for the restaurant/menu lists), Pressable. Styling is StyleSheet objects with flexbox (default flexDirection: 'column').
  • Navigation: React Navigation — native stack for screen-to-screen, bottom tabs for the app shell.
  • Platform bits: SafeAreaView for notches, Platform.OS for the few divergences.
  • State/data: same as web React — Context or Redux Toolkit for cart state, React Query / fetch for server data.

Firebase basics

A backend-as-a-service that covers what a small app needs without you running servers:

  • Auth — email/password, phone OTP, Google sign-in; gives you a stable uid.
  • Firestore — a NoSQL document database (collections → documents → subcollections). Real-time listeners push changes to the client; security rules enforce access server-side. No joins — you denormalize and duplicate data.
  • Cloud Storage — user-uploaded images (restaurant photos, profile pics).
  • Cloud Functions — server-side logic on triggers (a new order doc → compute total, assign a driver, send a notification).
  • FCM — push notifications.
  • Offline persistence is built in — the client reads/writes a local cache and syncs when online.

FoodExpress — app structure

Screens & data flow 
Screens (native stack + bottom tabs)
  Auth ─▶ Restaurants (FlatList + search) ─▶ Menu ─▶ Cart ─▶ Checkout
                                                         └─▶ Order Tracking (realtime)
  Tabs: Home · Orders (history) · Profile

Firestore model
  users/{uid}                     { name, phone, addresses[] }
  restaurants/{rid}               { name, cuisine, rating, image }
  restaurants/{rid}/menuItems/{id}{ name, price, veg }
  orders/{oid}                    { uid, rid, items[], total,
                                    status: placed|accepted|preparing|out|delivered,
                                    driverId, createdAt }

Flow
  cart = local state (Context/Redux)
  checkout ─▶ create orders/{oid} with status "placed"
  Cloud Function onCreate(orders) ─▶ validate total, assign driver, FCM to user
  Order Tracking screen ─▶ onSnapshot(orders/{oid}) ─▶ live status + driver location
Common mistakes
  • Computing the order total on the client — do it in a Cloud Function; the client can be tampered with.
  • No Firestore security rules — the default is open; a user must only read their own orders.
  • Using ScrollView for long lists — it renders everything; use FlatList.
  • Over-normalizing — Firestore has no joins; store restaurantName on the order rather than re-fetching.
  • Unbounded real-time listeners — detach onSnapshot on unmount, scope queries with where/limit.
