Spring Core — IoC, DI, bean lifecycle

Inversion of Control (IoC) means your classes no longer build their own collaborators — a container does, and hands them in. The concrete mechanism Spring uses is Dependency Injection (DI): you declare what you need (a constructor parameter), and the ApplicationContext supplies a fully wired instance. The win is testability (pass a fake in the test), swappability (one interface, several implementations chosen by config), and lifecycle management (one shared, thread-safe instance instead of new everywhere).

A bean is just an object the container creates and manages. You declare beans with stereotype annotations (@Component, @Service, @Repository, @Controller — all @Component with intent) that component-scanning picks up, or explicitly with @Bean methods inside a @Configuration class (the right tool for wiring types you don't own). Default scope is singleton: one instance per container. prototype gives a new one per injection point; request/session are web-scoped.

Prefer constructor injection over field injection: it makes dependencies explicit and final, fails fast if a dependency is missing, and needs no Spring annotations to unit-test. Field injection (@Autowired on a private field) hides dependencies and only works through reflection. When two beans satisfy one type, disambiguate with @Qualifier("name") or mark one @Primary.

Constructor injection — the default you should write

public interface PricingPolicy { long priceOf(Product p); }

@Component
class StandardPricing implements PricingPolicy {
    public long priceOf(Product p) { return p.getListPricePaise(); }
}

@Service
public class CartService {
    private final PricingPolicy pricing;
    private final CartRepository carts;

    // No @Autowired needed since Spring 4.3 when there is one constructor
    public CartService(PricingPolicy pricing, CartRepository carts) {
        this.pricing = pricing;
        this.carts = carts;
    }

    public long total(Cart cart) {
        return cart.getItems().stream()
                   .mapToLong(i -> pricing.priceOf(i.getProduct()) * i.getQty())
                   .sum();
    }
}
Core intuition

Spring is a big Map<name, object> plus rules for building the objects in dependency order. "Injecting a bean" = the container looks up (or lazily creates) the collaborator and passes it to your constructor. Everything else — AOP proxies, transactions, security — is the container wrapping those beans before it hands them out.

Bean lifecycle — the order that matters

For a singleton bean, the container: (1) instantiates it (constructor), (2) populates dependencies (setter/field injection), (3) calls *Aware callbacks (BeanNameAware, ApplicationContextAware), (4) runs BeanPostProcessor.postProcessBeforeInitialization, (5) runs init callbacks — @PostConstruct, then InitializingBean.afterPropertiesSet(), then a custom initMethod, (6) runs postProcessAfterInitialization (this is where AOP/proxy wrapping happens), and the bean is ready. On shutdown it runs @PreDestroy, then DisposableBean.destroy(), then a custom destroyMethod.

Lifecycle hooks in practice

@Component
public class ConnectionWarmup {

    private final DataSource dataSource;
    ConnectionWarmup(DataSource dataSource) { this.dataSource = dataSource; }

    @PostConstruct               // after DI, before the bean serves traffic
    void prime() {
        try (var c = dataSource.getConnection()) {
            c.isValid(2);        // open one connection so the first request is fast
        } catch (SQLException e) {
            throw new IllegalStateException("DB unreachable at startup", e);
        }
    }

    @PreDestroy                  // on context close / SIGTERM
    void drain() {
        // flush metrics, close custom resources
    }
}
Common mistakes
  • Field injection everywhere. Can't construct the object in a plain JUnit test without reflection; circular dependencies get silently tolerated instead of caught.
  • Calling @PostConstruct logic in the constructor. Dependencies may not be injected yet if you ever switch to setter injection, and the object escapes half-built.
  • Injecting a prototype bean into a singleton and expecting a fresh one each call — you get one, captured at creation. Use ObjectProvider<T> or a lookup method.
  • Assuming @Transactional / @Cacheable work on self-calls. They're proxy-based; a method calling another method on this bypasses the proxy.
  • Putting state on a singleton bean. Singletons are shared across all request threads — mutable instance fields are a race condition.
Interviewer probe

"Constructor vs field vs setter injection?" — constructor for required, immutable deps (the default); setter for optional deps; field only in throwaway code. "How does Spring break a circular dependency?" — for setter/field injection it exposes an early bean reference from the singleton cache; for constructor injection on both sides it can't, and fails at startup (fix the design, or @Lazy one side). "What is a BeanPostProcessor?" — the hook the framework itself uses to wrap your beans in proxies for AOP, @Async, @Transactional.

Spring MVC — the request lifecycle

Every HTTP request into a Spring Boot web app hits one servlet: DispatcherServlet (the "front controller"). It owns the pipeline and delegates each step to a strategy bean, which is why the framework is so extensible — you replace a strategy, not the servlet.

Request trace — GET /api/products/42 returning JSON
#ComponentWhat happens
1Servlet container (Tomcat)Accepts the socket, builds HttpServletRequest, hands it to DispatcherServlet.
2Filter chainOncePerRequestFilters run — Spring Security, request logging, CORS. Can short-circuit here (401).
3HandlerMappingRequestMappingHandlerMapping matches the URL + method to ProductController#getOne(long).
4HandlerInterceptorpreHandle() runs (auth checks, timing start). Can veto.
5HandlerAdapterResolves method arguments: @PathVariable 42 parsed to long via a Converter; @RequestBody would use an HttpMessageConverter.
6Controller methodRuns your code, returns a Product (or ResponseEntity<Product>).
7Return value handler@RestController ⇒ @ResponseBody path: MappingJackson2HttpMessageConverter serializes to JSON, sets Content-Type.
8Exception (if thrown)HandlerExceptionResolver → your @RestControllerAdvice maps it to a status + body. See Exception handling.
9HandlerInterceptorpostHandle() then afterCompletion() (timing stop, cleanup) — the latter runs even on exception.
10Filter chain unwindsResponse flushed to the socket.

For a classic server-rendered app the controller returns a view name (a String) instead; step 7 becomes ViewResolver → View.render(), which runs the Thymeleaf template against the Model and writes HTML. Same pipeline, different tail.

A controller that shows both tails

@RestController
@RequestMapping("/api/products")
class ProductApiController {
    private final ProductService products;
    ProductApiController(ProductService products) { this.products = products; }

    @GetMapping("/{id}")                              // JSON tail
    ResponseEntity<ProductDto> getOne(@PathVariable long id) {
        return ResponseEntity.ok(ProductDto.from(products.require(id)));
    }
}

@Controller
@RequestMapping("/products")
class ProductPageController {
    private final ProductService products;
    ProductPageController(ProductService products) { this.products = products; }

    @GetMapping("/{id}")                              // HTML tail
    String page(@PathVariable long id, Model model) {
        model.addAttribute("product", products.require(id));
        return "product/detail";                      // -> templates/product/detail.html
    }
}
Common mistakes
  • Confusing @Controller with @RestController. The latter adds @ResponseBody to every method; returning "product/detail" from it sends the literal string product/detail as the response body.
  • Filters vs interceptors. Filters are servlet-level (no Spring MVC context, run for every request including static resources); interceptors are MVC-level and know the handler. Put security in a filter, per-handler timing in an interceptor.
  • Doing blocking I/O on the Tomcat thread pool without sizing it — 200 threads default; a slow downstream call exhausts them and the app stops responding.
  • Returning entities directly instead of DTOs — leaks the schema, triggers lazy-loading during serialization (see next section), and couples your API to your tables.
Interviewer probe

"Walk me through what happens between the browser and your controller method." — name DispatcherServlet, filter chain, HandlerMapping, HandlerAdapter, argument resolvers, return-value handlers, HttpMessageConverter. "Where does JSON (de)serialization happen?" — HttpMessageConverter (Jackson), driven by Accept / Content-Type. "How would you add a request ID to every log line?" — a OncePerRequestFilter that puts it in the SLF4J MDC and clears it in a finally.

Spring Data JPA — relationships & lazy vs eager loading

Spring Data JPA sits on top of an ORM (Hibernate). You define @Entity classes that map to tables, and Repository interfaces whose method names Spring turns into queries (findByCustomerIdAndStatus). The behaviour that trips people up in interviews and in production is when related rows get loaded.

Relationship mapping

AnnotationDefault fetchOwning sideNote
@ManyToOneEAGERthe @ManyToOne side (has the FK column)Override to LAZY almost always.
@OneToManyLAZYmappedBy points to the ownerCollection is a proxy until touched.
@OneToOneEAGERside with the FK (or @JoinColumn)LAZY only reliably works on the owning side.
@ManyToManyLAZYeither; needs a join tablePrefer two @OneToMany to an explicit link entity.

The domain we'll break — Order 1─* OrderItem *─1 Product

@Entity
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String status;
    private Instant placedAt;

    @ManyToOne(fetch = FetchType.LAZY)          // FK: order.customer_id
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();
    // getters/setters/helpers
}

@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private int qty;
    private long unitPricePaise;

    @ManyToOne(fetch = FetchType.LAZY)          // FK: order_item.order_id
    @JoinColumn(name = "order_id")
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY)          // FK: order_item.product_id
    @JoinColumn(name = "product_id")
    private Product product;
}

The example that breaks

Naive service and controller. The service opens a transaction, loads the order, and returns the entity. The transaction commits (and the Hibernate Session closes) when the service method returns. Then the controller serializes it. 

@Service
class OrderService {
    private final OrderRepository orders;
    OrderService(OrderRepository orders) { this.orders = orders; }

    @Transactional(readOnly = true)
    public Order getOrder(long id) {
        return orders.findById(id)
                     .orElseThrow(() -> new NotFoundException("order " + id));
    }   // <-- transaction commits here, Session closes
}

@RestController
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @GetMapping("/api/orders/{id}")
    Order get(@PathVariable long id) {
        Order o = service.getOrder(id);
        return o;   // Jackson now walks o.getItems() ... to serialize it
    }
}
What actually happens

orders.findById(id) emits one SQL: SELECT * FROM orders WHERE id = ?. items is a lazy PersistentBag proxy — not loaded. The method returns, the transaction commits, the Session is closed.

Back in the controller, Jackson calls order.getItems().size(). The proxy tries to run its initialization SELECT — but there is no open Session. Hibernate throws: 

org.hibernate.LazyInitializationException:
  failed to lazily initialize a collection of role:
  com.shop.Order.items: could not initialize proxy - no Session

If you "fix" it by enabling open-session-in-view (Spring Boot's default, actually), the exception disappears but you get the N+1 problem instead: 1 query for the order, 1 for the items collection, then 1 SELECT per OrderItem to load its product. An order with 20 lines = 1 + 1 + 20 = 22 queries for one endpoint, executed lazily during JSON serialization where you can't even see them in your service code.

Why it breaks — and the four real fixes

The root cause: lazy loading needs an open persistence context, and the context's lifetime is the transaction, which ends inside the service. Serialization happens after. The fixes, best first:

  1. Return a DTO, assembled inside the transaction. The service maps Order → OrderDto while the session is open, so every field it needs is fetched deliberately. The controller serializes a plain object with no proxies. This also decouples the API from the schema.
  2. JOIN FETCH in the query so the data arrives in one round trip: 
    @Query("""
    select distinct o from Order o
    join fetch o.items i
    join fetch i.product
    where o.id = :id
""")
Optional<Order> findWithItems(@Param("id") long id);
  3. @EntityGraph — declarative fetch plan on a derived query, same effect as JOIN FETCH without JPQL: 
    @EntityGraph(attributePaths = {"items", "items.product"})
Optional<Order> findById(Long id);
  4. Batch fetching for the collection-of-collections case: @BatchSize(size = 50) or spring.jpa.properties.hibernate.default_batch_fetch_size=50 turns "N queries" into "N/50 queries" using IN (...).

Do not fix it by making everything EAGER: then every query for an Order drags the whole object graph, including from screens that only need the status. Eager is a decision you can't undo per-query; lazy + explicit fetch is.

The fixed service — DTO assembled in-transaction

@Service
class OrderService {
    private final OrderRepository orders;
    OrderService(OrderRepository orders) { this.orders = orders; }

    @Transactional(readOnly = true)
    public OrderDto getOrder(long id) {
        Order o = orders.findWithItems(id)
                        .orElseThrow(() -> new NotFoundException("order " + id));
        // still inside the tx: proxies resolve against the open Session
        List<OrderLineDto> lines = o.getItems().stream()
            .map(it -> new OrderLineDto(
                    it.getProduct().getName(),
                    it.getQty(),
                    it.getUnitPricePaise()))
            .toList();
        return new OrderDto(o.getId(), o.getStatus(), lines);
    }
}
Common mistakes
  • Serializing entities from controllers. The single biggest source of LazyInitializationException, N+1, and accidental schema leaks.
  • Relying on open-session-in-view. It hides N+1 and holds a DB connection for the whole request including view rendering. Many teams disable it (spring.jpa.open-in-view=false) to surface the problem at dev time.
  • JOIN FETCH with pagination. Fetching a collection + Pageable makes Hibernate paginate in memory (warns in the log). Use @EntityGraph on the entity IDs, or a two-step "IDs then fetch" query.
  • @ManyToOne left EAGER. It's the default; a chain of eager @ManyToOnes can load half the database for one findById.
  • equals()/hashCode() using the generated ID. The ID is null before persist; use a business key or a stable UUID assigned in the constructor.
Interviewer probe

"You call getItems() in the controller and it throws — why?" — session closed with the transaction; the lazy proxy has nothing to query against. "How do you fix N+1?" — JOIN FETCH / @EntityGraph for a known path, batch fetch size for the general case, DTO projection to fetch exactly the columns. "Why not make it eager?" — eager is global and un-opt-out-able per query; you trade one bug for a slower everything. "What's the owning side of @OneToMany?" — the many side with the FK; mappedBy names the field there.

Spring Security — authentication, authorization, the filter chain, JWT

Authentication answers "who are you?" — verify a credential (password, token, certificate) and establish a principal. Authorization answers "are you allowed to do this?" — check the authenticated principal's authorities/roles against the rule guarding a URL or method. Authentication happens once per request (early); authorization happens at the point of access (later, possibly per method).

The filter chain

Spring Security is a single servlet Filter (FilterChainProxy, registered as springSecurityFilterChain) that internally runs an ordered list of security filters before your DispatcherServlet ever sees the request. The ones that matter:

OrderFilterJob
1SecurityContextPersistenceFilter / SecurityContextHolderFilterLoad any existing SecurityContext (from the session, or nothing for stateless).
2CsrfFilterValidate the CSRF token for state-changing requests (disabled for stateless APIs).
3LogoutFilterHandle POST /logout.
4Authentication filter — UsernamePasswordAuthenticationFilter, or your custom JwtAuthFilterExtract the credential, build an Authentication, delegate to the AuthenticationManager, store the result in the SecurityContextHolder.
5ExceptionTranslationFilterCatch AuthenticationException (→ 401, entry point) and AccessDeniedException (→ 403).
6AuthorizationFilter (was FilterSecurityInterceptor)The last filter: apply the authorizeHttpRequests rules. Passes → your controller runs.

A stateless JWT security config (Spring Security 6 / Boot 3)

@Configuration
@EnableWebSecurity
@EnableMethodSecurity                 // enables @PreAuthorize
public class SecurityConfig {

    private final JwtAuthFilter jwtAuthFilter;
    SecurityConfig(JwtAuthFilter jwtAuthFilter) { this.jwtAuthFilter = jwtAuthFilter; }

    @Bean
    SecurityFilterChain chain(HttpSecurity http) throws Exception {
        http
          .csrf(csrf -> csrf.disable())                       // stateless: no cookie, no CSRF
          .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
          .authorizeHttpRequests(auth -> auth
              .requestMatchers("/api/auth/**", "/actuator/health").permitAll()
              .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
              .requestMatchers("/api/admin/**").hasRole("ADMIN")
              .anyRequest().authenticated())
          .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)
          .exceptionHandling(e -> e
              .authenticationEntryPoint((req, res, ex) -> res.sendError(401))
              .accessDeniedHandler((req, res, ex) -> res.sendError(403)));
        return http.build();
    }

    @Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    AuthenticationManager authManager(AuthenticationConfiguration c) throws Exception {
        return c.getAuthenticationManager();
    }
}

The JWT filter — runs once per request

@Component
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwt;
    private final UserDetailsService users;
    JwtAuthFilter(JwtService jwt, UserDetailsService users) { this.jwt = jwt; this.users = users; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);                 // no token -> let authz reject it later
            return;
        }
        String token = header.substring(7);
        try {
            String username = jwt.extractUsername(token);   // parse + verify signature + exp
            if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
                UserDetails user = users.loadUserByUsername(username);
                if (jwt.isValid(token, user)) {
                    var authn = new UsernamePasswordAuthenticationToken(
                            user, null, user.getAuthorities());
                    authn.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                    SecurityContextHolder.getContext().setAuthentication(authn);
                }
            }
        } catch (JwtException invalid) {
            // leave context empty; ExceptionTranslationFilter -> 401
        }
        chain.doFilter(req, res);
    }
}
JWT request flow — login, then a protected call
#StepDetail
1POST /api/auth/login {email, password}permitAll. AuthController calls authenticationManager.authenticate(...).
2DaoAuthenticationProviderLoads the user via UserDetailsService, checks BCrypt.matches(raw, hash).
3Issue tokenJwtService.generate(user) — header {alg:HS256}, claims {sub:email, roles:[...], iat, exp:+15m}, HMAC signature with the server secret.
4Response{ "accessToken": "eyJ...", "refreshToken": "..." }. Client stores it (memory / httpOnly cookie).
5GET /api/orders/mine Authorization: Bearer eyJ...Enters the filter chain.
6JwtAuthFilterStrips Bearer , verifies signature with the secret, checks exp, loads UserDetails, builds an Authentication, puts it in SecurityContextHolder.
7AuthorizationFilteranyRequest().authenticated() — context has an Authentication ⇒ pass. (Admin URL would also check hasRole("ADMIN").)
8ControllerRuns. @AuthenticationPrincipal UserDetails me is injected; @PreAuthorize can do a finer check.
9Response sentSecurityContextHolder.clearContext() at end of request (it's a ThreadLocal; the thread returns to the pool).

Token expired at step 6 ⇒ filter leaves the context empty ⇒ step 7 sees no auth ⇒ ExceptionTranslationFilter invokes the entry point ⇒ 401. Client then calls POST /api/auth/refresh with the refresh token to get a new access token.

Common mistakes
  • Storing JWTs in localStorage. Any XSS steals them. Prefer an httpOnly, Secure, SameSite cookie, or keep the access token in memory only.
  • Long-lived access tokens. You can't revoke a stateless JWT — keep it short (5–15 min) and use a refresh token (revocable, stored server-side) for longevity.
  • ROLE_ prefix confusion. hasRole("ADMIN") checks the authority ROLE_ADMIN; hasAuthority("ADMIN") checks ADMIN. Pick one convention.
  • Not disabling CSRF for a stateless API (requests silently 403 on POST), or disabling it for a cookie-session app (now CSRF-vulnerable).
  • Putting the JWT filter after UsernamePasswordAuthenticationFilter — use addFilterBefore.
  • Trusting claims without verifying the signature, or accepting alg: none.
Interviewer probe

"Authentication vs authorization — where in the chain?" — authn in a dedicated filter early; authz in AuthorizationFilter last, plus @PreAuthorize at the method. "How does a stateless request stay authenticated with no session?" — it doesn't; every request re-authenticates from the token. "How do you log someone out of a JWT system?" — delete the client token + revoke/rotate the refresh token + optionally a short deny-list of access-token JTIs until they expire. "Where is the principal stored during the request?" — SecurityContextHolder, a ThreadLocal, cleared when the request ends.

Spring Boot Actuator

Actuator adds production-readiness endpoints under /actuator with almost no code: health, metrics, environment, loggers, thread dump, HTTP exchange history. It's how your app tells Kubernetes it's alive, and how Prometheus scrapes it.

Typical config

# build.gradle: implementation "org.springframework.boot:spring-boot-starter-actuator"

management.endpoints.web.exposure.include=health,info,metrics,prometheus
management.endpoint.health.show-details=when_authorized
management.endpoint.health.probes.enabled=true        # /actuator/health/liveness + /readiness
management.metrics.tags.application=${spring.application.name}
EndpointUse
/actuator/healthAggregated UP/DOWN from all HealthIndicators (DB, disk, Redis...). Wire to k8s liveness/readiness probes.
/actuator/health/readinessDOWN during startup and graceful shutdown ⇒ load balancer stops routing before the app dies.
/actuator/metrics/{name}Micrometer meters: http.server.requests, jvm.memory.used, hikaricp.connections.active.
/actuator/prometheusSame meters in Prometheus text format for scraping → Grafana dashboards.
/actuator/loggers/{logger}POST to change a log level at runtime without a redeploy.
/actuator/env, /actuator/threaddump, /actuator/heapdumpDebugging a running instance. Sensitive — lock down.

A custom health indicator + a business metric

@Component
class PaymentGatewayHealth implements HealthIndicator {
    private final PaymentGatewayClient client;
    PaymentGatewayHealth(PaymentGatewayClient client) { this.client = client; }

    public Health health() {
        return client.ping()
            ? Health.up().withDetail("latencyMs", client.lastLatencyMs()).build()
            : Health.down().withDetail("reason", "gateway timeout").build();
    }
}

@Service
class CheckoutService {
    private final Counter ordersPlaced;
    CheckoutService(MeterRegistry registry) {
        this.ordersPlaced = registry.counter("shop.orders.placed");
    }
    void placeOrder(Order o) { /* ... */ ordersPlaced.increment(); }

Common mistakes
  • Exposing all endpoints publicly (exposure.include=*) — /actuator/env and /heapdump leak secrets. Expose the minimum; put the rest behind auth or a separate management port (management.server.port).
  • Using /health as a deep check that pings every downstream — a slow dependency then flaps your pods. Keep liveness shallow; put dependency checks in readiness.
  • Not adding an application tag — metrics from every service collide in Prometheus.
Interviewer probe

"Liveness vs readiness?" — liveness failing ⇒ restart the pod; readiness failing ⇒ keep it running but stop sending traffic (startup, warmup, shutdown, transient dependency loss). "How would you expose a custom metric?" — inject MeterRegistry, create a Counter/Timer/Gauge. "How do you bump a log level in prod without redeploying?" — POST /actuator/loggers.

JUnit 5 + Mockito

Interviewers ask for a test to see whether you isolate the unit under test. The pattern: mock the collaborators, stub their behaviour, run the method, assert on the result and on the interactions. Use @ExtendWith(MockitoExtension.class) for a fast unit test with no Spring context; use @SpringBootTest / @DataJpaTest / @WebMvcTest only when you're testing the wiring.

Unit test — service logic, repository & gateway mocked

@ExtendWith(MockitoExtension.class)
class CheckoutServiceTest {

    @Mock  OrderRepository orders;
    @Mock  PaymentGateway  payments;
    @Mock  InventoryService inventory;
    @InjectMocks CheckoutService checkout;      // constructor-injected with the mocks

    @Test
    void placesOrder_whenPaymentSucceeds() {
        Cart cart = TestData.cartWith(2_000_00);                 // ₹2000
        given(inventory.reserve(cart.getItems())).willReturn(true);
        given(payments.charge("cust-1", 2_000_00))
                .willReturn(new PaymentResult("pay_123", true));
        given(orders.save(any(Order.class)))
                .willAnswer(inv -> { Order o = inv.getArgument(0); o.setId(42L); return o; });

        OrderResult result = checkout.placeOrder("cust-1", cart);

        assertThat(result.success()).isTrue();
        assertThat(result.orderId()).isEqualTo(42L);

        ArgumentCaptor<Order> saved = ArgumentCaptor.forClass(Order.class);
        verify(orders).save(saved.capture());
        assertThat(saved.getValue().getStatus()).isEqualTo("PAID");
        verify(inventory, never()).release(any());
    }

    @Test
    void releasesStock_andFails_whenPaymentDeclined() {
        Cart cart = TestData.cartWith(500_00);
        given(inventory.reserve(any())).willReturn(true);
        given(payments.charge(anyString(), anyLong()))
                .willReturn(new PaymentResult(null, false));

        OrderResult result = checkout.placeOrder("cust-1", cart);

        assertThat(result.success()).isFalse();
        verify(inventory).release(cart.getItems());   // compensating action ran
        verify(orders, never()).save(any());
    }

    @Test
    void propagates_whenGatewayThrows() {
        given(inventory.reserve(any())).willReturn(true);
        given(payments.charge(anyString(), anyLong()))
                .willThrow(new GatewayTimeoutException());

        assertThatThrownBy(() -> checkout.placeOrder("cust-1", TestData.cartWith(100_00)))
                .isInstanceOf(GatewayTimeoutException.class);
        verify(inventory).release(any());
    }
}

@WebMvcTest(ProductApiController.class)          // loads MVC infra + this controller, nothing else
class ProductApiControllerTest {

    @MockBean  ProductService products;           // the controller's dependency, mocked

    void returns404_whenProductMissing() throws Exception {
        given(products.require(99L)).willThrow(new NotFoundException("product 99"));

        mvc.perform(get("/api/products/99"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.message").value("product 99"));
    }
}
Core intuition

A unit test fails for exactly one reason: the code under test is wrong. Every dependency that could fail for its own reason is a mock with scripted behaviour. given(...).willReturn(...) sets up the world; verify(...) asserts your code drove the collaborators correctly (especially the compensating actions on the failure path).

Common mistakes
  • Reaching for @SpringBootTest for a logic test. It boots the whole context (seconds per test) to test a method that needs three mocks.
  • Mocking value objects / DTOs. Mock things with behaviour and side effects, not data holders — just new them.
  • Over-verifying. verify every getter call and the test breaks on every refactor. Assert outcomes; verify only the interactions that matter (saves, sends, compensations).
  • Stubbing what you don't call — MockitoExtension is strict and fails on unnecessary stubbing, which is a feature.
  • Testing Spring Data repository methods. Trust the framework; test your @Query methods with @DataJpaTest against an in-memory or Testcontainers DB.
Interviewer probe

"@Mock vs @MockBean?" — @Mock is plain Mockito (no Spring); @MockBean replaces a bean in the Spring context (use in slice/integration tests). "How do you test the failure path?" — stub the collaborator to throw/return failure, assert the compensating action via verify. "What's a test double that isn't a mock?" — a stub (canned answers), a fake (working lightweight impl, e.g. in-memory repo), a spy (real object, some methods stubbed).

Common mistakes
  • Hard-coding URLs instead of @{/path} — breaks under a context path; @{} also adds the CSRF token to form actions when using the Spring Security dialect.

Interviewer probe

"Thymeleaf vs a JS SPA?" — Thymeleaf for content sites, admin panels, forms, SEO-critical pages, small teams; a SPA when the UI is app-like and stateful. "How does the CSRF token get into the form?" — the Spring Security dialect injects a hidden field on th:action forms; a manual form needs ${_csrf}. "th:replace vs th:insert vs th:include?" — replace swaps the host tag, insert keeps it and nests the fragment inside.

REST API design + Postman workflow

A REST resource is a noun with a stable URL; HTTP verbs are the operations; status codes are the result. Design for the client: predictable URLs, consistent envelopes, meaningful errors, and no surprises on retries.

A well-formed controller

@RestController
@RequestMapping("/api/products")
class ProductApiController {
    private final ProductService products;
    ProductApiController(ProductService products) { this.products = products; }

    @GetMapping
    Page<ProductDto> list(@RequestParam(required = false) String category,
                          @PageableDefault(size = 20) Pageable pageable) {
        return products.search(category, pageable).map(ProductDto::from);
    }

    @GetMapping("/{id}")
    ProductDto get(@PathVariable long id) {
        return ProductDto.from(products.require(id));   // throws NotFoundException -> 404 via advice
    }

    @PostMapping
    ResponseEntity<ProductDto> create(@Valid @RequestBody CreateProductRequest body) {
        Product created = products.create(body);
        URI location = URI.create("/api/products/" + created.getId());
        return ResponseEntity.created(location).body(ProductDto.from(created));
    }

    @PutMapping("/{id}")
    ProductDto replace(@PathVariable long id, @Valid @RequestBody UpdateProductRequest body) {
        return ProductDto.from(products.replace(id, body));
    }

    @DeleteMapping("/{id}")
    ResponseEntity<Void> delete(@PathVariable long id) {
        products.delete(id);
        return ResponseEntity.noContent().build();
    }
}

Design checklist

  • Versioning: /api/v1/... or a header. Pick one before you ship.
  • Pagination: always paginate list endpoints; return {content, page, size, totalElements}.
  • Filtering/sorting via query params: ?status=PAID&sort=placedAt,desc.
  • Validation: @Valid + Bean Validation annotations on the request DTO ⇒ 400 with field errors.
  • Errors: one shape everywhere (see Exception handling) — {timestamp, status, error, message, path, fieldErrors}.
  • Idempotency for POST that must not double-charge: an Idempotency-Key header the server dedupes on.
  • HATEOAS only if a client actually consumes links; most don't.

Postman workflow

  1. Collection per service, folders per resource. Requests named by intent ("Create product — happy path", "Create product — missing name → 400").
  2. Environments (local, staging) holding {{baseUrl}} and secrets. Never hard-code hosts in requests.
  3. Auth once: a "Login" request whose Tests script saves the token — 
    const json = pm.response.json();
pm.environment.set("accessToken", json.accessToken);
pm.test("login 200", () => pm.response.to.have.status(200));
    then set collection-level auth to Bearer {{accessToken}}.
  4. Chain requests: "Create product" saves {{productId}} from the response; "Get product" uses it; "Delete product" cleans up.
  5. Tests tab on every request: status, schema, key fields. Run the whole collection with the Collection Runner or newman in CI.
  6. Export the collection to the repo (/postman/shop.postman_collection.json) so it's reviewed and versioned.
Common mistakes
  • Verbs in URLs — /getProduct, /api/createOrder. The verb is the HTTP method.
  • 200 for everything, with {"success": false} in the body. Use the status line; clients and proxies rely on it.
  • Returning 500 for client mistakes. Bad input is 400/422, missing is 404, conflict is 409, unauthenticated 401, forbidden 403.
  • Leaking stack traces in error responses.
  • Unbounded list endpoints that return 50k rows and OOM under load.
Interviewer probe

"PUT vs PATCH?" — PUT replaces the whole resource (idempotent), PATCH applies a partial change. "Is POST idempotent? How do you make it safe to retry?" — no; an idempotency key the server stores and returns the first result for. "201 vs 200 on create?" — 201 with a Location header pointing at the new resource. "How do you test this API without a UI?" — Postman collection with environments, a login request that captures the token, per-request test scripts, run in CI with newman.

Exception handling

Centralize it. Throw meaningful exceptions from the service layer; map them to HTTP once, in a @RestControllerAdvice. Controllers stay free of try/catch, and every error response has the same shape.

Domain exceptions + one advice

public class NotFoundException extends RuntimeException {
    public NotFoundException(String msg) { super(msg); }
}
public class BusinessRuleException extends RuntimeException {
    public BusinessRuleException(String msg) { super(msg); }
}

public record ApiError(Instant timestamp, int status, String error,
                       String message, String path,
                       Map<String, String> fieldErrors) {}

@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(NotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    ApiError handleNotFound(NotFoundException ex, HttpServletRequest req) {
        return build(HttpStatus.NOT_FOUND, ex.getMessage(), req, Map.of());
    }

    @ExceptionHandler(BusinessRuleException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    ApiError handleBusiness(BusinessRuleException ex, HttpServletRequest req) {
        return build(HttpStatus.CONFLICT, ex.getMessage(), req, Map.of());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid failures
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    ApiError handleValidation(MethodArgumentNotValidException ex, HttpServletRequest req) {
        Map<String, String> fields = ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(FieldError::getField,
                                      FieldError::getDefaultMessage, (a, b) -> a));
        return build(HttpStatus.BAD_REQUEST, "validation failed", req, fields);
    }

    @ExceptionHandler(Exception.class)                          // the catch-all
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    ApiError handleUnknown(Exception ex, HttpServletRequest req) {
        log.error("unhandled exception at {}", req.getRequestURI(), ex);  // log the trace
        return build(HttpStatus.INTERNAL_SERVER_ERROR,
                     "something went wrong", req, Map.of());              // don't leak it
    }

    private ApiError build(HttpStatus s, String msg, HttpServletRequest req,
                           Map<String, String> fields) {
        return new ApiError(Instant.now(), s.value(), s.getReasonPhrase(),
                            msg, req.getRequestURI(), fields);
    }
}
Core intuition

Exceptions are the return channel for "can't do that". The service says what went wrong in domain terms (NotFoundException); the advice translates how to report it in HTTP terms (404). One translation layer ⇒ one consistent error contract, and the mapping is visible in one file.

For server-rendered (Thymeleaf) apps, use @ControllerAdvice with methods that return a view name ("error/404") and add attributes to the Model, or drop templates in templates/error/404.html / 5xx.html for Boot's default resolver to pick up.

Common mistakes
  • try/catch in every controller method. Duplicated, inconsistent, easy to forget one.
  • Catching Exception and returning 200 with an error body.
  • Logging and rethrowing at every layer ⇒ the same stack trace five times in the logs. Log once, at the boundary.
  • Leaking internals — SQL errors, class names, stack traces in the response.
  • Swallowing InterruptedException without restoring the interrupt flag.
Interviewer probe

"Checked vs unchecked for domain errors?" — unchecked (RuntimeException) so the signature isn't polluted through every layer; the advice is the single handler. "Where do you log the stack trace?" — in the catch-all handler (or a filter) at the edge, once. "How does @RestControllerAdvice find the exception?" — it's a specialized HandlerExceptionResolver; Spring matches the thrown type to the most specific @ExceptionHandler.

File upload

A multipart/form-data request; Spring binds each part to a MultipartFile. The endpoint's job: validate (size, type), store somewhere durable (object storage, not the pod's disk), and persist a reference.

Config + endpoint

# application.yml
spring:
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 20MB        # several files per request

@RestController
@RequestMapping("/api/products/{id}/image")
class ProductImageController {

    private final ProductService products;
    private final FileStorage storage;         // wraps S3 / MinIO / local dir
    ProductImageController(ProductService products, FileStorage storage) {
        this.products = products; this.storage = storage;
    }

    private static final Set<String> ALLOWED = Set.of("image/png", "image/jpeg", "image/webp");

    @PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    ResponseEntity<ImageDto> upload(@PathVariable long id,
                                    @RequestParam("file") MultipartFile file) {
        if (file.isEmpty())
            throw new BusinessRuleException("empty file");
        if (!ALLOWED.contains(file.getContentType()))
            throw new BusinessRuleException("unsupported type: " + file.getContentType());

        String key = "products/%d/%s".formatted(id, UUID.randomUUID());
        String url;
        try (InputStream in = file.getInputStream()) {
            url = storage.put(key, in, file.getSize(), file.getContentType());
        } catch (IOException e) {
            throw new UncheckedIOException("upload failed", e);
        }
        products.attachImage(id, url);
        return ResponseEntity.status(HttpStatus.CREATED).body(new ImageDto(url));
    }
}
Common mistakes
  • Trusting the client's Content-Type / filename. Sniff the magic bytes for real validation; sanitize or discard the original filename (path-traversal via ../../).
  • Storing on the container filesystem. Gone on restart, not shared across replicas. Use object storage; keep only the key/URL in the DB.
  • file.getBytes() for large files — loads it all into heap. Stream via getInputStream().
  • No size cap ⇒ a 2GB upload OOMs the pod. Cap in config and at the ingress/LB.
  • Serving user uploads from your app's domain without Content-Disposition / a separate origin — stored-XSS risk for HTML/SVG.
Interviewer probe

"10,000 users uploading 5MB images — where does it go?" — object storage (S3/GCS), app returns a pre-signed URL so the browser uploads directly and never streams through your JVM. "How do you validate it's really a PNG?" — check the magic number, not the extension or header. "Big file, flaky network?" — multipart/resumable upload to the store, not one POST.

Git collaboration workflow

The expectation on a team: small branches, reviewed PRs, a green CI gate, a linear-ish history, and never a force-push to a shared branch. The exact model (trunk-based vs GitHub flow vs Gitflow) varies; the habits don't.

Day-to-day (GitHub / trunk-based flow)

git switch main && git pull --ff-only          # start from current main
git switch -c feat/order-idempotency-key        # short-lived topic branch

# ... work, committing in logical chunks ...
git add -p                                        # stage hunks deliberately
git commit -m "Add Idempotency-Key dedup to POST /orders"

git fetch origin
git rebase origin/main                            # keep history linear; resolve conflicts here
git push -u origin feat/order-idempotency-key

# open a Pull Request -> CI runs (build + tests + lint) -> review -> squash & merge
git switch main && git pull --ff-only
git branch -d feat/order-idempotency-key
SituationCommand
Pulled and got a merge commit you didn't wantgit config --global pull.ff only (then rebase manually)
Committed to main by mistakegit switch -c feat/x; git switch main; git reset --hard origin/main
Need one commit from another branchgit cherry-pick <sha>
Half-done work, must switch tasksgit stash push -m "wip" … git stash pop
Last commit message/content wrong (not pushed)git commit --amend
Undo a pushed commit safelygit revert <sha> (new inverse commit)
Find which commit broke a testgit bisect start / good / bad

Resolving a rebase conflict

git rebase origin/main
# CONFLICT in CheckoutService.java
#   <<<<<<< HEAD (their change from main)
#   ... incoming ...
#   =======
#   ... your change ...
#   >>>>>>> feat/order-idempotency-key
# edit the file to the correct combined result, then:
git add CheckoutService.java
git rebase --continue          # or: git rebase --abort to bail out
Common mistakes
  • git push --force to a shared branch. Use --force-with-lease, and only on your own topic branch.
  • Giant PRs. 2,000-line PRs get rubber-stamped. Keep them under ~400 lines; stack them if needed.
  • Committing secrets / target/ / IDE files. A real .gitignore from the start; git-secrets or a pre-commit hook.
  • Merge commits from git pull polluting history — configure pull.ff only or pull.rebase true.
  • Vague messages — "fix", "wip", "changes". Write the what and why; the diff shows the how.
Interviewer probe

"Merge vs rebase?" — merge preserves context and is safe on shared branches; rebase gives linear history and is for your own unpushed work. "You force-pushed and a teammate lost commits — recover?" — git reflog to find the lost SHA, git branch rescue <sha>. "How do you revert a bad deploy?" — git revert the merge commit (-m 1), or roll forward with a fix; never reset a shared branch.

Docker + basic deployment

Package the app as an image so it runs the same on your laptop, CI, and prod. For Spring Boot: a multi-stage build (build with the JDK, run on a slim JRE), layered so dependency layers cache across builds.

Multi-stage Dockerfile

# ---- build stage ----
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY gradlew settings.gradle build.gradle ./
COPY gradle ./gradle
RUN ./gradlew dependencies --no-daemon        # cached unless build files change
COPY src ./src
RUN ./gradlew bootJar --no-daemon

# ---- run stage ----
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
USER app                                       # don't run as root
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75 -XX:+UseZGC"
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

docker-compose for local dev (app + DB)

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: dev
    ports: ["5432:5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
  app:
    build: .
    depends_on:
      db: { condition: service_healthy }
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/shop
      SPRING_DATASOURCE_USERNAME: postgres
      SPRING_DATASOURCE_PASSWORD: dev
    ports: ["8080:8080"]

From image to running service

  1. docker build -t registry.example.com/shop:1.4.0 .
  2. docker push registry.example.com/shop:1.4.0 (CI does this on a tag / merge to main).
  3. Deploy target pulls the tag: a docker run on a VM, an ECS/Cloud Run service, or a Kubernetes Deployment whose image: is bumped and rolled out (readiness probe → /actuator/health/readiness).
  4. Config comes from environment variables / secrets, never baked into the image. Spring maps SPRING_DATASOURCE_URL → spring.datasource.url automatically.
  5. DB schema changes run as a Flyway/Liquibase migration on startup or as a separate job — never Hibernate ddl-auto=update in prod.
Common mistakes
  • Single-stage build shipping the whole JDK + Gradle cache + source — a 700MB image instead of ~180MB.
  • COPY . . before RUN ./gradlew dependencies — every source edit busts the dependency cache.
  • Running as root; no USER directive.
  • Fixed -Xmx that ignores the container limit. Use -XX:MaxRAMPercentage; modern JVMs are container-aware.
  • Secrets in ENV / the Dockerfile — they're in the image layers forever.
  • latest tag in prod — you can't tell what's running or roll back.
Interviewer probe

"Why multi-stage?" — build needs the JDK + build tool; runtime needs only a JRE + the jar. Smaller image, smaller attack surface, faster pulls. "How does the app get its DB password?" — injected env var / mounted secret at deploy time. "Container gets OOM-killed — why?" — JVM heap set without regard to the cgroup limit, or native memory (threads, metaspace, direct buffers) not accounted for.

Spring Cloud — a light intro (config server, Eureka)

Once you have several Spring Boot services, two problems appear: (1) where does configuration live, and (2) how do services find each other. Spring Cloud's answers are the Config Server and a service registry (Eureka). You won't build a full mesh in an interview — you should be able to explain the shape.

Config Server

A standalone service (@EnableConfigServer) that serves configuration from a backing store — usually a Git repo of {app}-{profile}.yml files. Each service, at startup, asks the config server for its config instead of reading a local file. 

// config-server: application.yml
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/acme/service-config
          default-label: main

// order-service: application.yml  (or spring.config.import)
spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config-server:8888"
// -> fetches order-service.yml + order-service-prod.yml from the git repo

Combined with /actuator/refresh (or Spring Cloud Bus), a config change in Git can propagate to running services without a redeploy. Secrets are usually kept out of Git and pulled from Vault or the platform's secret store.

Service discovery — Eureka

A registry where each service registers its host:port on startup and renews a lease (heartbeat) every 30s; instances that stop heartbeating are evicted. Callers ask the registry for "the instances of payment-service" and client-side load-balance across them — so you call http://payment-service/api/charge by name, and the IP is resolved at call time. 

// eureka-server: @EnableEurekaServer

// payment-service & order-service: just add the client starter
spring.application.name: payment-service
eureka.client.service-url.defaultZone: http://eureka:8761/eureka

// order-service calling payment-service, load-balanced by name:
@Bean @LoadBalanced RestClient.Builder restClientBuilder() { return RestClient.builder(); }

restClient.post()
    .uri("http://payment-service/api/charge")   // "payment-service" -> a live instance
    .body(chargeRequest)
    .retrieve()
    .body(ChargeResult.class);

  • Adding Spring Cloud on Kubernetes where DNS + Services already do discovery and ConfigMaps do config — you're duplicating the platform.
  • Config server as a hard startup dependency with no fallback — it goes down, nothing boots. Use optional: and sane local defaults.
  • Secrets in the config Git repo.
  • No circuit breaker on inter-service calls — one slow service cascades.
Interviewer probe

"How does order-service find payment-service?" — asks the registry by name, gets a list of healthy instances, client-side load-balances. "What happens when an instance dies?" — it stops heartbeating, the registry evicts it after a few missed leases, callers refresh their instance list. "Config server vs env vars?" — config server centralizes and versions config across many services and can refresh at runtime; env vars are simpler and enough for a few services or on a platform that already provides config.

Security config — form login for pages, JWT for /api

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
class SecurityConfig {

    // Chain 1: the JSON API — stateless, JWT
    @Bean @Order(1)
    SecurityFilterChain api(HttpSecurity http, JwtAuthFilter jwt) throws Exception {
        http.securityMatcher("/api/**")
            .csrf(c -> c.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwt, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    // Chain 2: the server-rendered site — session + form login
    @Bean @Order(2)
    SecurityFilterChain web(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(a -> a
                .requestMatchers("/", "/products/**", "/css/**", "/js/**", "/register").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .requestMatchers("/cart/**", "/checkout/**", "/orders/**").authenticated()
                .anyRequest().authenticated())
            .formLogin(f -> f.loginPage("/login").defaultSuccessUrl("/", false))
            .logout(l -> l.logoutSuccessUrl("/"));
        return http.build();
    }

    @Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }
}

Checkout — the transactional heart

@Service
class CheckoutService {
    private final CartRepository carts;
    private final ProductRepository products;
    private final OrderRepository orders;
    private final PaymentService payments;
    // constructor ...

    @Transactional
    public Order checkout(User user, Address shipTo, String idempotencyKey) {
        Cart cart = carts.findByUserIdWithItems(user.getId())
                         .orElseThrow(() -> new BusinessRuleException("empty cart"));
        if (cart.getItems().isEmpty()) throw new BusinessRuleException("empty cart");

        Order order = new Order(user, shipTo);
        for (CartItem ci : cart.getItems()) {
            Product p = products.findByIdForUpdate(ci.getProduct().getId())   // SELECT ... FOR UPDATE
                                .orElseThrow();
            if (p.getStock() < ci.getQty())
                throw new BusinessRuleException("out of stock: " + p.getName());
            p.setStock(p.getStock() - ci.getQty());                          // decrement under lock
            order.addLine(p, ci.getQty(), p.getPricePaise());                // copy price now
        }
        order.recalculateTotal();
        orders.save(order);

        PaymentResult pr = payments.charge(order, idempotencyKey);           // idempotent
        if (!pr.success()) throw new BusinessRuleException("payment declined"); // tx rolls back -> stock restored
        order.markPaid(pr.reference());
        cart.clear();
        return order;
    }
}

Likely interview questions about this project

Interviewer probe
  • "Why two security filter chains?" — the site is stateful (session cookie, CSRF, form login, redirects); the API is stateless (JWT, no CSRF, 401 not a redirect). securityMatcher + @Order routes each request to the right one.
  • "Two customers buy the last unit at the same time — what happens?" — SELECT ... FOR UPDATE on the product row inside the checkout transaction serializes them; the second sees stock < qty and gets a BusinessRuleException, its transaction rolls back. Alternative: optimistic locking with a @Version column and retry.
  • "Why copy the price into OrderItem?" — an order is a historical record; if the product price changes tomorrow, past orders must not.
  • "The payment webhook fires twice — double charge?" — no; Payment.idempotencyKey is unique and PaymentService returns the existing result for a repeat key.
  • "Where does LazyInitializationException bite you here?" — rendering orders/detail.html which walks order.items[].product; fixed with a JOIN FETCH query or an @EntityGraph, or a view-model assembled in the service.
  • "How do you test checkout?" — unit test with mocked repos/gateway for the stock and rollback logic; one @SpringBootTest + Testcontainers Postgres for the real transaction + FOR UPDATE behaviour.
  • "Scale it: 10k req/s on the product pages?" — cache the catalog (read-mostly) in Redis / CDN, paginate, add read replicas, keep checkout on the primary. See HLD.
  • "Admin uploads a product image — where does it go?" — object storage via a FileStorage abstraction; the DB stores the URL; validate magic bytes + size.
  • "How is config managed across dev/prod?" — application-{profile}.yml, secrets as env vars / mounted secrets, never in the image; Flyway for schema.
  • "One thing you'd refactor?" — have an honest answer ready (e.g. "move cart to Redis with a TTL instead of a DB table", "extract payment into its own service once a second provider is added").
