DSA — Non-linear Structures & Dynamic Programming

Phase 1, second half. Everything here branches: a node points at two or more others, and the work is defined by recursion on structure rather than a walk from index 0 to n−1. 1 · Trees & Traversals

A binary tree node holds a value and two child references, left and right, either of which may be null. There is no array backing it and no index arithmetic — the only way to reach a node is to follow references from the root. Because the structure is defined recursively (a tree is a node whose children are themselves trees), almost every tree algorithm is a three-line recursion: handle null, recurse left, recurse right, combine. The height h is the longest root-to-leaf path; it is O(log n) for a balanced tree and O(n) for a degenerate one, and it bounds both the recursion depth and the cost of a single root-to-leaf descent.

The four traversals differ only in when you process the current node relative to its subtrees. Pre-order (node, left, right) processes a parent before its children — use it to copy or serialise a tree. In-order (left, node, right) processes the left subtree, then the node, then the right — on a BST this yields values in sorted order. Post-order (left, right, node) processes both children before the node — use it when a node's answer depends on its children's answers (subtree sums, heights, deletion). Level-order (breadth-first) visits the tree row by row using a queue, and is the tool for "shortest path in the tree", "nodes at depth k", or anything phrased per level.

Recursive traversals are trivial to write but consume call-stack proportional to h, which overflows on a skewed tree of ~104–105 nodes. The iterative forms use an explicit Deque as a stack and give you the control some follow-ups demand (pause mid-traversal, bound memory, iterator API). Iterative in-order is the one worth memorising: push the entire left spine, then repeatedly pop, visit, and dive into the popped node's right child.

Core intuition

Ask one question of the current node: "can I answer for the whole subtree rooted here if someone hands me the answers for my left and right children?" If yes, it is a post-order recursion and the combine step is the whole problem. If the node's job is to pass information downward (a running path sum, a valid range), thread that as a parameter in a pre-order recursion.

Worked example — iterative in-order traversal with an explicit stack

import java.util.*;

class TreeNode { int val; TreeNode left, right; TreeNode(int v){ val = v; } }

public class IterativeInorder {
    static List<Integer> inorder(TreeNode root) {
        List<Integer> out = new ArrayList<>();
        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode curr = root;
        while (curr != null || !stack.isEmpty()) {
            while (curr != null) {        // push the whole left spine
                stack.push(curr);
                curr = curr.left;
            }
            curr = stack.pop();           // leftmost unvisited node
            out.add(curr.val);            // visit
            curr = curr.right;            // then explore its right subtree
        }
        return out;
    }

    public static void main(String[] args) {
        TreeNode root = new TreeNode(4);
        root.left = new TreeNode(2);
        root.right = new TreeNode(6);
        root.left.left = new TreeNode(1);
        root.left.right = new TreeNode(3);
        System.out.println(inorder(root));   // [1, 2, 3, 4, 6]
    }
}

How to recognise it in an unseen problem

Trigger signals
  • Input is a TreeNode root — the traversal choice is the algorithm design.
  • "Sum / height / diameter / count of a subtree", "is this subtree balanced / a BST" → post-order recursion returning a small struct or an int.
  • "Path from the root", "does a root-to-leaf path sum to target" → pre-order carrying an accumulator.
  • "Level by level", "right side view", "zigzag", "minimum depth", "nodes at distance k" → BFS with a per-level size snapshot.
  • "k-th smallest in a BST", "validate BST", "recover BST" → in-order traversal (recursive or the iterative form above).
  • "Serialize / deserialize", "clone" → pre-order with explicit null markers.
  • Recursion depth could hit 105 on a skewed tree → use the iterative traversal or BFS.
Common mistakes
  • No null base case, or checking node.left/node.right for null instead of node itself.
  • Level-order without snapshotting queue.size() before the inner loop → levels bleed together.
  • Returning early from a recursion and skipping the other subtree (e.g. path-sum stopping at the first hit when you need all paths).
  • Using a global mutable field for the answer and forgetting to reset it between test cases.
  • Confusing height (edges/nodes down to a leaf) with depth (down from the root) — off-by-one on the answer.
  • Deep recursion on a 105-node skewed tree → StackOverflowError.
  • Post-order iterative done with one stack and no "last visited" pointer → visiting a node before its right child.

2 · Binary Search Trees

A binary search tree adds one invariant to a binary tree: for every node, every value in its left subtree is smaller and every value in its right subtree is larger (assume distinct keys unless told otherwise). The invariant is recursive — it is not enough for a node to be larger than its immediate left child; it must be larger than the maximum of the whole left subtree. The single most useful consequence: an in-order traversal of a BST emits the keys in sorted order, so "k-th smallest", "next larger", "is this a valid BST", and "range sum" all reduce to a controlled in-order walk.

Search, insert, and delete all cost O(h): you compare the target with the current node and descend left or right, halving the problem only if the tree is balanced. A plain BST built from sorted input degenerates into a linked list with h = n; self-balancing variants (red-black, AVL) keep h = O(log n), and Java's TreeMap / TreeSet are red-black trees you should reach for when you need an ordered structure with ceiling/floor/higher/lower in logarithmic time.

Deletion is the one fiddly operation. If the node is a leaf, detach it. If it has one child, splice that child into its place. If it has two children, replace the node's value with its in-order successor (the minimum of the right subtree — the leftmost node reachable by going right once then left as far as possible), then delete that successor from the right subtree, which is now an easy one-or-zero-child case.

Core intuition

"BST" means "sorted array you can insert into in O(log n)." Whenever a problem wants order statistics and mutation, that is the trade a BST buys. To check validity, don't compare a node to its parent — pass an allowed open interval (low, high) down the recursion and tighten it: everything left of a node must be below its value, everything right must be above it.

Worked example — validate a BST by carrying a (low, high) bound downward

class TreeNode { int val; TreeNode left, right; TreeNode(int v){ val = v; } }

public class ValidateBST {
    static boolean isValid(TreeNode node, Long low, Long high) {
        if (node == null) return true;
        if (node.val <= low || node.val >= high) return false;   // outside the allowed open interval
        return isValid(node.left,  low, (long) node.val)          // left subtree must stay below node.val
            && isValid(node.right, (long) node.val, high);        // right subtree must stay above node.val
    }
    static boolean isValidBST(TreeNode root) {
        return isValid(root, Long.MIN_VALUE, Long.MAX_VALUE);
    }

    public static void main(String[] args) {
        TreeNode root = new TreeNode(5);
        root.left  = new TreeNode(3);
        root.right = new TreeNode(8);
        root.right.left  = new TreeNode(4);   // 4 sits in 5's right subtree but 4 < 5 → invalid
        root.right.right = new TreeNode(9);
        System.out.println(isValidBST(root)); // false
    }
}

How to recognise it in an unseen problem

Trigger signals
  • The prompt literally says "binary search tree", or the tree is stated to be sorted-by-structure.
  • "k-th smallest / largest", "in-order successor / predecessor", "closest value to x" → in-order walk, stop when the count or the target is reached.
  • "Validate", "recover two swapped nodes" → in-order should be strictly increasing; find where it isn't.
  • "Insert / delete and keep it a BST", "trim to a range [lo, hi]" → recurse on the one side the comparison allows.
  • "Lowest common ancestor" in a BST → walk down from the root; the first node that splits the two targets (or equals one) is the LCA — O(h), no recursion into both subtrees.
  • "Build a balanced BST from a sorted array" → recurse on the middle element.
Common mistakes
  • Validating with a parent comparison instead of an inherited interval.
  • Bounds as Integer.MIN_VALUE/MAX_VALUE then a node actually holds that value → false negative; use Long or nullable Integer.
  • <= vs <: decide up front whether duplicates are allowed and on which side.
  • Deletion with two children: forgetting to then remove the successor from the right subtree, leaving it duplicated.
  • Assuming O(log n) — an adversarial/sorted insertion order gives O(n) height.
  • LCA in a BST written as the general-tree LCA (recurse both subtrees) — correct but wastes the ordering; O(h) is available.

3 · Tries (Prefix Trees)

A trie stores a set of strings as a tree of characters: the root is the empty prefix, and each edge is labelled with one character, so the path from the root to a node spells that node's prefix. A boolean flag on a node marks whether that prefix is also a complete stored word. Children are held either in a fixed array (size 26 for lowercase English — fastest, simplest indexing with c - 'a') or in a HashMap<Character, Node> when the alphabet is large or unknown.

The payoff is that insert, exact search, and startsWith (prefix query) all run in O(L) where L is the length of the query string — completely independent of how many words the trie holds. A HashSet<String> also gives O(L) exact lookup, but it cannot answer "how many stored words begin with cat" without scanning every key. Tries also let you walk a candidate string and a dictionary in lock-step, which is what makes them the backbone of "word search on a board", wildcard matching, and autocomplete.

The cost is memory: each node reserves space for its whole child set (26 references even if one is used), and there is one node per distinct prefix character across all words. When strings share long prefixes this is a win; when they don't, a trie can use far more memory than a plain list, and a compressed/radix trie (edges labelled with substrings) is the usual fix.

Core intuition

A trie turns "search a dictionary" into "walk a single path, one character per step." If a problem repeatedly asks about prefixes, or needs to try many dictionary words against the same text position, the trie lets every one of those queries share the work of matching their common prefix once.

Worked example — insert, exact search, and prefix query

class Trie {
    private final Trie[] next = new Trie[26];
    private boolean end;

    public void insert(String word) {
        Trie node = this;
        for (char c : word.toCharArray()) {
            int i = c - 'a';
            if (node.next[i] == null) node.next[i] = new Trie();
            node = node.next[i];
        }
        node.end = true;
    }

    public boolean search(String word)      { Trie n = walk(word);   return n != null && n.end; }
    public boolean startsWith(String prefix) { return walk(prefix) != null; }

    private Trie walk(String s) {
        Trie node = this;
        for (char c : s.toCharArray()) {
            node = node.next[c - 'a'];
            if (node == null) return null;
        }
        return node;
    }
}

How to recognise it in an unseen problem

Trigger signals
  • "Implement autocomplete / search suggestions", "words that start with a prefix".
  • A dictionary of words plus a grid or a text, and you must match many words at once ("Word Search II", "Concatenated Words").
  • Wildcard or "." matches-any-character search over a word set → trie with a branching DFS on ..
  • "Maximum XOR of two numbers in an array" and other bitwise-greedy problems → a binary trie on the 32 bits of each number.
  • "Replace words with their shortest root", "longest word buildable one character at a time".
  • Repeated prefix membership tests where a HashSet would re-scan keys.
Common mistakes
  • Treating "walk succeeded" as "word found" — you must also check the end flag.
  • Array children for a large or mixed-case alphabet (wasted memory) or a HashMap for plain lowercase (slower, boxing overhead).
  • Not handling the empty string, or an off-alphabet character crashing c - 'a'.
  • Word Search II: not pruning trie branches after a word is found, or not deleting exhausted leaves → revisits and TLE.
  • Rebuilding the trie inside a loop instead of once up front.
  • Recursion over the trie deep enough to overflow when word length is large — iterate where you can.

4 · Heaps & Priority Queues

A binary heap is a complete binary tree (every level full except possibly the last, which fills left to right) stored implicitly in an array: the children of index i are 2i+1 and 2i+2, the parent is (i-1)/2. A min-heap maintains the property that every parent is ≤ both children, so the smallest element is always at index 0. Reading that minimum is O(1); inserting (append, then "sift up" while smaller than the parent) and removing the min (move the last element to the root, then "sift down" toward the smaller child) are both O(log n). Building a heap from an existing array is O(n).

Java's PriorityQueue is a min-heap by default; new PriorityQueue<>(Comparator.reverseOrder()) or a custom comparator gives a max-heap or priority-by-field. Use a heap whenever you need repeated access to the current extreme of a changing set but not full sorted order: "k largest / smallest", "k-th element", "merge k sorted lists", "schedule the highest-priority task", and Dijkstra's shortest path. The two-heap trick (a max-heap of the lower half, a min-heap of the upper half) maintains a running median in O(log n) per insert.

For "k-th largest", the efficient shape is a size-k min-heap: push every element, and whenever the heap exceeds k entries, poll the smallest. What remains are the k largest seen, and the root is the k-th largest. This is O(n log k) time and O(k) space — better than sorting (O(n log n)) when k ≪ n.

Core intuition

A heap is the right structure when you keep asking "what's the smallest/largest right now?" while the set keeps changing. It gives you that one element cheaply and nothing else — no search, no ordered iteration. If you need the top k and k is small, hold a heap of size k of the opposite polarity so the element you might evict is the one at the root.

Worked example — k-th largest element via a size-k min-heap

import java.util.PriorityQueue;

public class KthLargest {
    static int findKthLargest(int[] nums, int k) {
        PriorityQueue<Integer> pq = new PriorityQueue<>();   // min-heap
        for (int x : nums) {
            pq.offer(x);
            if (pq.size() > k) pq.poll();                    // drop the current smallest
        }
        return pq.peek();                                     // root = k-th largest overall
    }

    public static void main(String[] args) {
        System.out.println(findKthLargest(new int[]{3, 2, 1, 5, 6, 4}, 2)); // 5
    }
}

How to recognise it in an unseen problem

Trigger signals
  • "k largest / smallest / most frequent / closest", "k-th largest" — especially as a stream.
  • "Merge k sorted lists / arrays" → min-heap of the current head of each list.
  • "Median of a data stream", "sliding window median" → two heaps.
  • "Always process the item with the highest priority / earliest deadline / smallest cost next" → Dijkstra, task scheduler, meeting rooms.
  • "Minimum cost to connect / combine" repeatedly merging the two cheapest → heap (Huffman-style).
  • You need the extreme repeatedly and the set changes — if it never changes, just sort once.
Common mistakes
  • Forgetting Java's PriorityQueue is a min-heap — max-heap needs an explicit comparator.
  • Iterating a PriorityQueue and expecting sorted order — only poll() gives that.
  • Using a size-n heap when a size-k heap of opposite polarity suffices — O(n log n) instead of O(n log k).
  • Comparator written as a - b on values that can overflow — use Integer.compare.
  • Mutating an object's key after it is in the heap — the heap order is now silently wrong; remove and re-insert instead.
  • Reaching for a heap when a full sort is simpler and k ≈ n, or when counting-sort bounds apply.

5 · Graphs — BFS, DFS, Topological Sort, Union-Find

A graph is a set of vertices and edges; edges may be directed or undirected, weighted or not. Two representations dominate. An adjacency list (List<List<Integer>> or a map) stores, per vertex, the vertices it connects to — O(V + E) space, and iterating a vertex's neighbours is proportional to its degree. An adjacency matrix (boolean[V][V]) answers "is there an edge u→v" in O(1) but costs O(V²) space and makes neighbour iteration O(V) regardless of how sparse the graph is. Interview graphs are almost always sparse, so default to the adjacency list; use a matrix only for dense graphs or when you constantly test specific edges.

BFS explores outward in layers from the source using a FIFO queue, marking each vertex visited as it is enqueued. In an unweighted graph the layer number is the shortest-path distance, so BFS is the tool for "fewest steps / moves / edges". It runs in O(V + E) but its frontier can hold O(V) vertices at once. DFS goes as deep as possible before backtracking, via recursion or an explicit stack, also O(V + E); its memory is the current path length, O(V) worst case but typically much less. DFS is natural for connectivity, cycle detection, enumerating paths, and topological sort; it does not give shortest paths, and deep recursion on a 105-vertex graph can overflow the call stack — switch to an explicit stack or BFS there.

Topological sort orders the vertices of a directed acyclic graph so that every edge u → v points forward in the order — the classic "which order can I take these prerequisite-linked courses" question. Kahn's algorithm does it with BFS: compute every vertex's in-degree, start a queue with the in-degree-0 vertices, and repeatedly remove one, appending it to the order and decrementing its neighbours' in-degrees, enqueuing any that hit zero. If the final order is missing vertices, the graph had a cycle and no topological order exists.

Union-Find (disjoint-set union) tracks a partition of vertices into connected components under a stream of "connect u and v" operations. find(x) returns the representative of x's component; union(a, b) merges two components. Two optimisations make it near-constant time: union by size/rank always hangs the smaller tree under the larger root, and path compression flattens the path to the root every time you call find. Together they give O(α(n)) amortised per operation, where α is the inverse-Ackermann function — effectively ≤ 4 for any real input. Use it for "number of connected components", cycle detection in an undirected graph, Kruskal's minimum spanning tree, and dynamic connectivity.

Core intuition

Pick the traversal by what the answer is: shortest / fewest → BFS; exists a path / all paths / is there a cycle / ordering → DFS or Kahn. Pick the data structure by what changes: the graph is fixed and you explore it → adjacency list + BFS/DFS; edges are added one at a time and you keep asking "are these two connected yet" → union-find. Union-find answers connectivity without ever materialising the components.

Worked example A — topological sort (Kahn's algorithm)

import java.util.*;

public class TopoSort {
    static int[] topoSort(int n, int[][] edges) {   // edges: [from, to], meaning from must precede to
        List<List<Integer>> adj = new ArrayList<>();
        for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
        int[] indeg = new int[n];
        for (int[] e : edges) { adj.get(e[0]).add(e[1]); indeg[e[1]]++; }

        Deque<Integer> q = new ArrayDeque<>();
        for (int i = 0; i < n; i++) if (indeg[i] == 0) q.offer(i);

        int[] order = new int[n];
        int idx = 0;
        while (!q.isEmpty()) {
            int u = q.poll();
            order[idx++] = u;
            for (int v : adj.get(u))
                if (--indeg[v] == 0) q.offer(v);
        }
        return idx == n ? order : new int[0];   // fewer than n emitted ⇒ cycle ⇒ no valid order
    }

    public static void main(String[] args) {
        int[][] edges = {{0,1},{0,2},{1,3},{2,3}};
        System.out.println(Arrays.toString(topoSort(4, edges))); // [0, 1, 2, 3]
    }
}

Worked example B — union-find with path compression and union by size

class DSU {
    private final int[] parent, size;

    DSU(int n) {
        parent = new int[n];
        size   = new int[n];
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }
    }

    int find(int x) {
        while (parent[x] != x) {
            parent[x] = parent[parent[x]];   // path compression (halving): point x at its grandparent
            x = parent[x];
        }
        return x;
    }

    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;          // already in one component ⇒ this edge would close a cycle
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }   // attach smaller under larger
        parent[rb] = ra;
        size[ra] += size[rb];
        return true;
    }
}

How to recognise it in an unseen problem

Trigger signals
  • A grid where you move between adjacent cells ("islands", "rotting oranges", "walls and gates") — it's a graph; BFS for shortest, DFS/union-find for connectivity.
  • "Fewest moves / steps / transformations", "shortest path" in an unweighted graph → BFS.
  • "Can all nodes be reached", "detect a cycle", "all paths from s to t", "clone the graph" → DFS.
  • "Course prerequisites", "build order", "alien dictionary", "task scheduling with dependencies" → topological sort.
  • "Number of connected components / provinces / friend circles", "redundant connection", "accounts merge", "is this a valid tree" → union-find.
  • "Minimum spanning tree", "connect all points at minimum cost" → Kruskal (union-find) or Prim (heap).
  • Weighted edges, non-negative, single-source shortest path → Dijkstra (BFS with a min-heap).
Common mistakes
  • BFS marking visited at dequeue instead of enqueue → the same vertex is queued many times, blowing up memory and time.
  • No visited set at all on a graph with cycles → infinite loop.
  • Recursive DFS on a 105-node graph → StackOverflowError; use an explicit stack or BFS.
  • Adding an undirected edge only one way, or a directed edge both ways.
  • Topological sort: not checking that all n vertices were emitted → silently returning a partial order for a cyclic graph.
  • Union-Find with neither path compression nor union by size → find degrades to O(n), whole algorithm O(n²).
  • Comparing x == root or parent[a] == parent[b] instead of find(a) == find(b).
  • Using BFS for shortest path on a weighted graph — you need Dijkstra / Bellman-Ford.

6 · Greedy Algorithms

A greedy algorithm builds an answer in steps, and at each step takes the choice that looks best right now, never revisiting it. When it works it is wonderfully cheap — usually a sort plus one linear pass, O(n log n), and a few lines of code. The catch is that "looks best now" is only safe when the problem has the greedy-choice property: there exists an optimal solution that agrees with the greedy first choice. If a locally worse move now can unlock a much better outcome later, greedy fails, and the honest way to know is to try to build a small counterexample.

You prove a greedy correct with an exchange argument: take any optimal solution, and show that you can swap in the greedy choice without making it worse (and without breaking feasibility). Repeat, and the optimal solution is transformed step by step into the greedy one, so the greedy one is also optimal. The canonical case is interval scheduling — to fit the most non-overlapping intervals, always take the one that finishes earliest among those still compatible: it leaves the most room for everything after it.

Greedy is provably correct for interval scheduling and interval "point cover" (arrows/balloons), for Huffman coding, for Dijkstra with non-negative weights, for minimum spanning trees (Kruskal, Prim), for the fractional knapsack (take the highest value-per-weight until full), and for reachability problems like Jump Game. It is a trap for the 0/1 knapsack (you cannot take a fraction of an item — that needs DP), for coin change with arbitrary denominations (with coins {1, 3, 4} making 6, greedy takes 4 + 1 + 1 = three coins, but 3 + 3 = two is optimal), for longest-path problems, and for most partitioning problems.

Core intuition

Before you commit to greedy, ask: "if I make the locally optimal move now, can an adversary arrange the rest so I regret it?" If you can't construct that regret and you can sketch an exchange argument, greedy is safe. If you find even one small case where a worse-looking early move wins, you are in DP territory — the difference is exactly whether future choices depend on which option you took now.

Worked example — maximum number of non-overlapping intervals (sort by finish time)

import java.util.*;

public class IntervalScheduling {
    static int maxNonOverlapping(int[][] intervals) {
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));  // by finish time, ascending
        int count = 0, lastEnd = Integer.MIN_VALUE;
        for (int[] iv : intervals) {
            if (iv[0] >= lastEnd) {   // starts at or after the last kept interval finished
                count++;
                lastEnd = iv[1];
            }
        }
        return count;
    }

    public static void main(String[] args) {
        int[][] iv = {{1,3},{2,4},{3,5},{7,9}};
        System.out.println(maxNonOverlapping(iv)); // 3  → [1,3], [3,5], [7,9]
    }
}

Why earliest-finish is optimal (exchange argument). Let greedy's first pick be g, the interval that finishes earliest. Take any optimal set and let its earliest-finishing interval be o. Since g finishes no later than o, replacing o with g still overlaps nothing that came after o — the set stays valid and the same size. Now recurse on the intervals starting after g. So greedy matches an optimal solution at every step.

How to recognise it in an unseen problem

Trigger signals
  • "Maximum number of / minimum number of" over intervals, and a sort by one endpoint makes the choice obvious.
  • "Can you reach the end", "minimum jumps" → track the furthest reachable index.
  • "Assign / match to maximise pairs" with two sorted lists → two pointers, take the smallest feasible.
  • Repeatedly "merge the two cheapest / smallest" → greedy with a heap.
  • A proof by exchange argument is easy to sketch, and you cannot find a counterexample after honestly trying.
  • Not greedy: choosing item i changes what is optimal for the rest (0/1 knapsack, general coin change, most "count the ways" / "best partition" problems) → dynamic programming.
Common mistakes
  • Sorting by start time or by length when the correct key is finish time (or vice versa for a different problem).
  • Assuming greedy works because it passed the examples — always attempt a counterexample first.
  • Applying greedy to the 0/1 knapsack or arbitrary-denomination coin change.
  • Comparator (a, b) -> a[1] - b[1] overflowing for large coordinates — use Integer.compare.
  • Boundary confusion: do touching intervals [1,3] and [3,5] count as overlapping? Decide, then use >= or > consistently.
  • Greedy that needs a tie-break rule (e.g. equal finish times) and doesn't specify one.

7 · Dynamic Programming

Dynamic programming is brute-force recursion with a memory: you write down the answer to every subproblem the first time you compute it, so you never recompute it. It applies when a problem has optimal substructure (the optimal answer is built from optimal answers to smaller subproblems) and overlapping subproblems (a naive recursion would solve the same subproblem many times). If subproblems don't overlap, it's plain divide-and-conquer; if there's no real choice at each step, it's ordinary recursion; if a local choice is provably safe, it's greedy. DP is what's left: several choices per step, and which one is best depends on subproblems you'll reuse.

7.1 · How to recognise a DP problem

The reliable tells: the problem asks for an optimum (longest / shortest / min / max), a count of ways, or a yes/no feasibility — usually not the actual arrangement. You can describe the solution as a sequence of decisions, each choosing among a few options ("take this item or don't", "match these characters or skip one"). And the brute-force recursion visibly recomputes states. The practical recipe is always the same four steps:

The recipe
  • State. Write the recursion first: "at position i with situation s, the answer is…". The parameters that change become your DP dimensions / memo key.
  • Choices. At each state, enumerate the handful of moves. They must be mutually exclusive and cover every possibility.
  • Recurrence. Combine the choices — max / min / sum of the sub-results, plus any immediate cost or gain.
  • Base cases & order. The smallest states (empty string, zero capacity, single cell) get direct answers; then fill larger states in an order where every dependency is already known.

7.2 · Top-down (memoization) vs bottom-up (tabulation)

Top-down keeps the recursion and caches each result in an array or map keyed by the state. It only ever computes states you actually reach, it follows the recurrence directly so it's easy to write, and it handles awkward or sparse state spaces without you working out an iteration order. The costs are recursion overhead and stack-depth limits. Bottom-up fills a table iteratively in dependency order. It has no recursion, predictable performance, and makes space optimisation (keep only the last row/column) straightforward — but you must find a valid fill order, and you may compute states you never needed. They have identical asymptotic complexity; converting one to the other is mechanical once you have the recurrence.

Core intuition

Find the recursion and the state; the table is just bookkeeping. If you can write solve(state) as "the best over a few solve(smaller state) calls plus a local term", you have a DP — memoise it, then (optionally) rewrite the memo as a loop that fills the same values in order.

7.3 · 0/1 Knapsack — deriving the recurrence

n items; item i has weight w[i] and value v[i]; a bag of capacity W; each item taken zero or one times; maximise total value.

  1. Subproblem. Let dp[i][c] = the maximum value achievable using only items 1..i with capacity c.
  2. Choices for item i. Exactly two, and they're exhaustive:
    • Skip it. Value = dp[i-1][c] — same capacity, one fewer item to consider.
    • Take it (only possible if w[i] ≤ c). Value = v[i] + dp[i-1][c - w[i]] — gain v[i], spend w[i] of capacity, move on to items 1..i-1 (it's i-1, not i, because the item is used up).
  3. Recurrence. dp[i][c] = max( dp[i-1][c], w[i] ≤ c ? v[i] + dp[i-1][c - w[i]] : −∞ )
  4. Base case. dp[0][c] = 0 for every c (no items → no value).
  5. Answer. dp[n][W]. Time and space O(nW); space drops to O(W) with a 1-D array iterated right-to-left, so that dp[c - w[i]] still holds the previous row's value.

Worked example — 0/1 knapsack, space-optimised to one row

public class Knapsack01 {
    static int knapsack(int[] w, int[] v, int W) {
        int[] dp = new int[W + 1];
        for (int i = 0; i < w.length; i++)
            for (int c = W; c >= w[i]; c--)                 // right-to-left ⇒ dp[c - w[i]] is still "row i-1"
                dp[c] = Math.max(dp[c], v[i] + dp[c - w[i]]);
        return dp[W];
    }

    public static void main(String[] args) {
        int[] w = {2, 3, 4, 5}, v = {3, 4, 5, 6};
        System.out.println(knapsack(w, v, 5));   // 7  → items (2,3) + (3,4)
    }
}

7.4 · Unbounded Knapsack — deriving the recurrence

Same setup, but each item may be taken any number of times (rod cutting, coin change).

  1. Subproblem. dp[c] = best value for capacity c. The item index drops out of the state — because items are reusable, "which items remain" is always "all of them".
  2. Choice. For capacity c, either stop, or take one more copy of some item i with w[i] ≤ c, leaving sub-state dp[c - w[i]] — and note it's dp[c - w[i]], not a smaller item set, because item i is still available afterwards.
  3. Recurrence. dp[c] = max over all i with w[i] ≤ c of ( v[i] + dp[c - w[i]] ), with dp[0] = 0.
  4. Order. Iterate capacity left-to-right — the opposite of 0/1 — so that dp[c - w[i]] already reflects having used item i.
static int knapsackUnbounded(int[] w, int[] v, int W) {
    int[] dp = new int[W + 1];
    for (int c = 1; c <= W; c++)
        for (int i = 0; i < w.length; i++)
            if (w[i] <= c) dp[c] = Math.max(dp[c], v[i] + dp[c - w[i]]);
    return dp[W];
}

dp[6] = min(1 + dp[5], 1 + dp[3], 1 + dp[2]) = min(3, 2, 3) = 2 (two 3-coins). A greedy "take the largest coin ≤ remaining" would pick 4 + 1 + 1 = three coins — this is the counterexample that shows coin change needs DP, not greedy. (For the min-coins version, initialise dp[1..W] to a large sentinel and take min.)

7.5 · LCS & Edit Distance — deriving the recurrence

Longest common subsequence. Strings A (length m) and B (length n); find the longest sequence of characters appearing in both in the same relative order (not necessarily contiguous).

  1. Subproblem. dp[i][j] = LCS length of the prefixes A[0..i) and B[0..j).
  2. Choice — look at the last characters A[i-1] and B[j-1].
    • If they're equal, that character can end the LCS, and removing it from both prefixes is a strictly smaller subproblem: dp[i][j] = 1 + dp[i-1][j-1].
    • If they differ, at least one of them is not in the LCS, so try dropping each: dp[i][j] = max( dp[i-1][j], dp[i][j-1] ).
  3. Base case. dp[0][j] = dp[i][0] = 0 (an empty prefix shares nothing).
  4. Answer. dp[m][n], in O(mn) time and space (reducible to O(min(m,n))).

Edit distance is the same skeleton with three edit operations and unit costs. If A[i-1] == B[j-1], no work: dp[i][j] = dp[i-1][j-1]. Otherwise pay 1 for the cheapest fix: dp[i][j] = 1 + min( dp[i-1][j-1] (replace), dp[i-1][j] (delete from A), dp[i][j-1] (insert into A) ). Base cases dp[i][0] = i (delete everything) and dp[0][j] = j (insert everything). 

static int lcs(String a, String b) {
    int m = a.length(), n = b.length();
    int[][] dp = new int[m + 1][n + 1];
    for (int i = 1; i <= m; i++)
        for (int j = 1; j <= n; j++)
            dp[i][j] = a.charAt(i - 1) == b.charAt(j - 1)
                     ? 1 + dp[i - 1][j - 1]
                     : Math.max(dp[i - 1][j], dp[i][j - 1]);
    return dp[m][n];
}

7.6 · Palindromic Subsequence — deriving the recurrence

Longest palindromic subsequence of a string s of length n. This is an interval DP: the state is a range of s, not a prefix.

  1. Subproblem. dp[i][j] = length of the longest palindromic subsequence within s[i..j] (inclusive).
  2. Choice — compare the two ends s[i] and s[j].
    • If s[i] == s[j], both ends wrap around the best palindrome strictly inside: dp[i][j] = 2 + dp[i+1][j-1] (treat dp[i+1][j-1] as 0 when i+1 > j-1).
    • Otherwise at least one end is unused: dp[i][j] = max( dp[i+1][j], dp[i][j-1] ).
  3. Base case. dp[i][i] = 1 (one character is a palindrome).
  4. Order. Fill by increasing range length (equivalently: i from n-1 down to 0, j from i+1 up to n-1), so dp[i+1][j-1], dp[i+1][j], dp[i][j-1] are ready. Answer: dp[0][n-1]. (Equivalent shortcut: LPS(s) = LCS(s, reverse(s)).)

7.7 · Grid DP — deriving the recurrence

An m × n grid; you move only right or down from the top-left to the bottom-right.

  1. Subproblem. dp[i][j] = the answer for reaching cell (i, j).
  2. Choice — you entered (i, j) from above or from the left. Those are the only two predecessors, so:
    • Count of paths: dp[i][j] = dp[i-1][j] + dp[i][j-1] (an obstacle forces dp[i][j] = 0).
    • Minimum path sum: dp[i][j] = g[i][j] + min( dp[i-1][j], dp[i][j-1] ).
  3. Base case. dp[0][0] is the start cell's own value (or 1 path). The first row and first column have only one predecessor each, so they accumulate in a single direction.
  4. Order. Row by row, left to right — both dependencies are already filled. Space reduces to O(n): one row updated left-to-right, where dp[j] is "from above" (old value) and dp[j-1] is "from the left" (just updated).
static int minPathSum(int[][] g) {
    int m = g.length, n = g[0].length;
    int[] dp = new int[n];
    dp[0] = g[0][0];
    for (int j = 1; j < n; j++) dp[j] = dp[j - 1] + g[0][j];   // first row
    for (int i = 1; i < m; i++) {
        dp[0] += g[i][0];                                       // first column
        for (int j = 1; j < n; j++)
            dp[j] = g[i][j] + Math.min(dp[j], dp[j - 1]);
    }
    return dp[n - 1];
}

How to recognise it in an unseen problem

Trigger signals
  • "Maximum / minimum / longest / shortest" over a sequence of decisions, or "how many ways", or "is it possible to reach exactly".
  • "Choose a subset with sum / count property" → knapsack family (0/1 if each item once, unbounded if reusable).
  • Two strings and an alignment / similarity / transformation → LCS / edit-distance grid.
  • One string and a question about palindromes, or about splitting it → interval DP on [i, j].
  • A grid with restricted moves and a cost or a count → grid DP.
  • The brute-force recursion has 2 or 3 branches and obviously revisits the same (i, state) pairs.
  • You catch yourself wanting greedy but can build a small case where a worse move now wins → it's DP.
Common mistakes
  • State missing a parameter that actually varies (a running remainder, "is item i still available", a parity/flag).
  • 0/1 vs unbounded knapsack: iterating the 1-D capacity loop in the wrong direction.
  • Off-by-one between "first i items" / "index i" and "prefix of length i".
  • Base cases unset, or using 0 where the identity should be +∞ / −∞ (min/max problems).
  • Top-down memo not keyed on the full state, or a "0 = not computed" sentinel colliding with a real answer of 0.
  • Tabulation filled in an order where a needed cell isn't ready yet — especially interval DP.
  • Returning dp[n] when the answer is a max over all states (longest increasing subsequence, maximum subarray, longest palindromic substring).
  • Space-optimising to a rolling array before the plain 2-D version is verified correct.
