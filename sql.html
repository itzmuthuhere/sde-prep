The sample schema

A tiny e-commerce model: customers place orders, each order has one or more order_items pointing at products. A separate employees table (self-referencing via manager_id) exists only for the recursive-CTE section. The data is deliberately small — 6 customers, 10 orders, 14 line items — so every query result on this page can be verified by counting rows yourself.

Two rows are placed on purpose: customer Frank Li has no orders (so LEFT JOIN and "never ordered" queries have something to find), and product Legacy Adapter has no sales (so anti-joins have something to find). Order 1004 is cancelled and 1006 is only shipped, so "delivered revenue" differs from "gross revenue".

1 · Advanced SELECT

Everything before FROM is a projection: you choose columns, compute new ones, rename them with AS, and reshape values. The workhorses are CASE (an inline if/else that returns a value), the null-handlers COALESCE (first non-null argument) and NULLIF (null when two values are equal — handy to dodge divide-by-zero), and scalar functions like EXTRACT, ROUND, CAST / ::.

DISTINCT removes duplicate rows after projection; PostgreSQL also has DISTINCT ON (col) to keep the first row per group under an ORDER BY. LIMIT with OFFSET paginates — but only meaningfully when paired with a deterministic ORDER BY, otherwise "page 2" is undefined. Remember the logical evaluation order: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. That is why you can't reference a SELECT alias in WHERE (it doesn't exist yet) but you can in ORDER BY.

Core intuition

SELECT is a per-row transform: given one row's columns, what do I output? If the answer needs other rows, that is not a SELECT job — it's a join, an aggregate, or a window. Reach for CASE the moment you hear "bucket", "label", "flag as", or "otherwise".

Worked query — computed columns, CASE, EXTRACT, filtered + paginated

SELECT
    c.name,
    c.city,
    c.segment,
    EXTRACT(YEAR FROM c.signup_date)        AS signup_year,
    CASE WHEN c.segment = 'business'
         THEN 'priority' ELSE 'standard' END AS support_tier
FROM customers c
WHERE c.city IN ('Seattle', 'Austin')
ORDER BY c.signup_date
LIMIT 4;

When this comes up in interviews

Always. Screening rounds are almost entirely SELECT + WHERE + CASE. Expected fluency: bucketing with CASE, null-safety with COALESCE, cheap date parts with EXTRACT. Overkill: DISTINCT ON and clever CASE nesting when a small join or a window would read more clearly — reviewers dislike "surprising" SQL more than long SQL.

2 · Joins — every type

A join pairs each row of one table with matching rows of another on a predicate. INNER JOIN keeps only pairs that match. LEFT JOIN keeps every left row, filling NULLs where the right side has no match (RIGHT JOIN is the mirror; FULL OUTER JOIN keeps unmatched rows from both sides). CROSS JOIN is every combination — the Cartesian product, no predicate. A self join is just a table joined to itself under two aliases, for "compare a row to other rows in the same table".

The anti-join deserves its own name: LEFT JOIN … WHERE right.key IS NULL finds left rows with no match ("customers who never ordered", "products never sold"). It is the single most common "medium" SQL question. Its partner, the semi-join, asks only "does a match exist" and is usually written with EXISTS (see §6).

The one trap that sinks people: putting a filter on the right table of a LEFT JOIN in the WHERE clause silently turns it back into an inner join (because NULL = 'x' is false). Filters on the outer table must live in the ON clause.

Core intuition

Ask two questions. "Do I need rows that have no partner?" — yes ⇒ outer join. "Which side must always survive?" — that side is LEFT. Then decide where each filter goes: conditions on the always-survive table go in ON, not WHERE.

SELECT o.order_id, c.name, o.order_date, o.status
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'delivered'
ORDER BY o.order_id
LIMIT 5;

Self join — pairs of customers in the same city

SELECT a.name AS customer_a, b.name AS customer_b, a.city
FROM customers a
JOIN customers b
  ON a.city = b.city
 AND a.customer_id < b.customer_id      -- each pair once, no self-pairing
ORDER BY a.city;
Result
customer_acustomer_bcity
Bob MartinEve ParkAustin
Alice NguyenCarla ReyesSeattle

The a.customer_id < b.customer_id condition is the whole trick: = would return every customer paired with themselves, <> would return each pair twice (A–B and B–A).

RIGHT JOIN is just LEFT JOIN with the tables swapped — most teams ban it for readability. FULL OUTER JOIN shows up when reconciling two lists ("rows in yesterday's snapshot vs today's"); MySQL lacks it, so you emulate with LEFT JOIN … UNION … RIGHT JOIN. CROSS JOIN is for generating a grid to fill — e.g. every (customer, month) cell before LEFT JOINing actual orders so months with no orders still appear as zero.

Common mistakes
  • Filtering the right table of a LEFT JOIN in WHERE — it collapses to an inner join. Move it to ON.
  • Join predicate too loose (missing a key column) → row explosion; the result has more rows than either table.
  • COUNT(*) after a LEFT JOIN counting 1 for unmatched rows — use COUNT(right.key).
  • Joining on a nullable column and forgetting NULL = NULL is unknown, not true.
  • Summing a parent column after joining to children — the parent value is duplicated per child and the sum is inflated.
  • Self join without an inequality → duplicate/self pairs.
When this comes up in interviews

Every SQL interview, usually the first real question. "Combine two tables", "customers who never ordered", "employees earning more than their manager" are all just joins. Be instant on INNER vs LEFT and the anti-join pattern. Overkill: reaching for FULL OUTER JOIN or multi-way self joins when the question is really a GROUP BY or a window function.

3 · Sorting & Grouping

GROUP BY collapses rows that share the grouping key into one row per group; every column in SELECT must then be either a grouping key or wrapped in an aggregate. HAVING filters groups after aggregation, the way WHERE filters rows before it — "departments with more than 5 people" is HAVING COUNT(*) > 5, and it cannot be done in WHERE.

ORDER BY takes multiple keys (each ASC/DESC independently), can sort by an expression or a SELECT alias, and controls null placement with NULLS FIRST / NULLS LAST (Postgres defaults nulls to last for ASC, MySQL to first). GROUP BY extensions — ROLLUP, CUBE, GROUPING SETS — produce subtotal rows in one pass, useful for report-style "total per category and a grand total".

Core intuition

"Per X" in the question ⇒ GROUP BY X. A condition on the aggregated number ("more than", "at least", "average above") ⇒ HAVING. A condition on raw rows ("only delivered orders") ⇒ WHERE, and it runs first, so it shrinks the work.

Worked query — customers per city and segment, ranked

SELECT c.city, c.segment, COUNT(*) AS customer_count
FROM customers c
GROUP BY c.city, c.segment
ORDER BY customer_count DESC, c.city ASC;
Result

Denverconsumer1

Five groups from six customers — only Austin/consumer (Bob + Eve) has two. Ties on customer_count are broken by city ASC.

Common mistakes
  • Selecting a non-aggregated, non-grouped column — Postgres errors; MySQL (old mode) returns an arbitrary value.
  • Putting an aggregate condition in WHERE (WHERE COUNT(*) > 5) — it belongs in HAVING.
  • Filtering rows in HAVING that could have been in WHERE — correct, but slower (you aggregated rows you then threw away).
  • COUNT(col) skips NULLs; COUNT(*) counts rows. Different answers.
  • Relying on GROUP BY to also sort the output — it does not; add ORDER BY.
  • ORDER BY a column not in SELECT DISTINCT — not allowed.
When this comes up in interviews

Constantly — "top N per group", "count per day", "categories with more than K items" are the bread and butter of the medium tier. Know WHERE vs HAVING cold. Overkill: ROLLUP/CUBE/ GROUPING SETS are almost never asked; mentioning them is a nice bonus, leading with them is a red flag.

4 · Aggregation

The five standard aggregates — COUNT, SUM, AVG, MIN, MAX — all ignore NULL (except COUNT(*)). COUNT(DISTINCT col) counts unique non-null values. Used without GROUP BY, an aggregate collapses the whole result to a single row.

Conditional aggregation is the technique that carries most interview answers: aggregate over a subset within the same scan. PostgreSQL's SUM(x) FILTER (WHERE cond) is the clean form; the portable form is SUM(CASE WHEN cond THEN x END) and COUNT(CASE WHEN cond THEN 1 END). This is how you get "delivered revenue and total revenue side by side", or pivot rows into columns ("count of each status per day").

Watch precision: AVG of integers may do integer division in some engines (cast one operand to numeric); SUM over many big rows can overflow a narrow integer type; and AVG silently drops NULLs from the denominator, which is sometimes right and sometimes a bug ("average score" — do missing scores count as zero?).

Core intuition

If you're about to run two near-identical queries that differ only by a WHERE filter and then compare the numbers, stop — that's one query with two FILTER/CASE aggregates.

Worked query — one scan, several headline numbers

SELECT
    COUNT(*)                             AS line_rows,
    COUNT(DISTINCT o.customer_id)        AS buying_customers,
    SUM(oi.quantity * oi.unit_price)     AS gross_revenue,
    ROUND(AVG(oi.quantity * oi.unit_price), 2) AS avg_line_value,
    MAX(oi.quantity * oi.unit_price)     AS biggest_line
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id;
Result
line_rowsbuying_customersgross_revenueavg_line_valuebiggest_line

14 line items across 10 orders from 5 distinct customers (Frank never ordered). 1675 / 14 = 119.64; the biggest single line is 10×Widget = 250.00 in order 1003.

Conditional aggregation — delivered vs all revenue in one pass

SELECT
    SUM(oi.quantity * oi.unit_price)                                       AS all_revenue,
    SUM(oi.quantity * oi.unit_price) FILTER (WHERE o.status = 'delivered') AS delivered_revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id;
-- MySQL: SUM(CASE WHEN o.status = 'delivered'
--                 THEN oi.quantity * oi.unit_price END)

Common mistakes
  • Assuming COUNT(col) and COUNT(*) are the same — they differ whenever col has NULLs.
  • AVG(int_col) doing integer division (some engines) — AVG(col::numeric).
  • Averaging over a join that duplicated the base row — the average is weighted by child count.
  • SUM returning NULL (not 0) when no rows match — wrap in COALESCE(SUM(...), 0).
  • Counting after a LEFT JOIN and getting 1 for the no-match rows.
  • Mixing an aggregate and a bare column with no GROUP BY.
When this comes up in interviews

In every question that has a "how many" or "how much". Conditional aggregation (SUM(CASE …)) is a genuine differentiator — it separates people who write three queries from people who write one. Overkill: hand-rolling a pivot with a dozen CASE columns when the interviewer would accept "…and I'd pivot this in the BI layer".

5 · CTEs (Common Table Expressions)

A CTE is a named subquery declared up front with WITH, then referenced by name in the main query (or in later CTEs). It doesn't make the query more powerful than nested subqueries — it makes it readable: you name each intermediate result, and you read the query top-to-bottom instead of inside-out.

The typical shape is a pipeline: CTE 1 shapes the base rows, CTE 2 aggregates CTE 1, the final SELECT joins that back to a dimension table. A CTE can be referenced multiple times without repeating its text. In modern PostgreSQL CTEs are not an optimization fence by default (they can be inlined); if you rely on materialization, say WITH x AS MATERIALIZED (…).

Core intuition

If you catch yourself writing a subquery inside a subquery inside a FROM, stop and give each layer a name with WITH. Same result, and the interviewer can now follow your logic — which is half of what they're grading.

Worked query — two-stage pipeline: order totals → customer revenue

WITH order_totals AS (
    SELECT o.order_id, o.customer_id,
           SUM(oi.quantity * oi.unit_price) AS order_value
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'delivered'
    GROUP BY o.order_id, o.customer_id
),
customer_revenue AS (
    SELECT customer_id,
           SUM(order_value) AS revenue,
           COUNT(*)         AS delivered_orders
    FROM order_totals
    GROUP BY customer_id
)
SELECT c.name, r.revenue, r.delivered_orders
FROM customer_revenue r
JOIN customers c ON c.customer_id = r.customer_id
ORDER BY r.revenue DESC;
Result
namerevenuedelivered_orders
Bob Martin600.002
Alice Nguyen360.003
Carla Reyes275.002
Eve Park40.001

Dan and Frank don't appear — Dan's only order is shipped, Frank has none, so neither survives the WHERE o.status = 'delivered' in the first CTE. Alice has more orders but lower total than Bob.

Common mistakes
  • Expecting a CTE to be evaluated once and reused — before PG 12 it was; now it may be inlined and run per reference.
  • Trying to reference a CTE defined later in the same WITH list (only recursive CTEs self-reference).
  • A trailing comma after the last CTE, or forgetting the comma between CTEs.
  • Putting ORDER BY inside a non-recursive CTE and assuming the outer query preserves it — it doesn't.
  • Very long CTE chains that would be clearer as a view or a temp table.
When this comes up in interviews

Whenever the answer has more than one step — which is most medium/hard questions. Using a CTE instead of nested subqueries is a readability signal reviewers actively look for. Overkill: a CTE for a single trivial subquery, or five CTEs where two would do. It's a clarity tool, not a checkbox.

6 · Subqueries

A subquery is a SELECT nested inside another statement. Four positions: scalar (returns one row/one column — usable anywhere a value is, e.g. WHERE x > (SELECT AVG(x) …)); IN / NOT IN (a value against a column list); EXISTS / NOT EXISTS (a correlated existence test); and derived table (a subquery in FROM, which must be aliased).

A correlated subquery references a column from the outer query, so it conceptually re-runs per outer row — EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id). EXISTS short-circuits on the first match and handles NULLs safely, which is why it's preferred over IN for "has any" / "has none" questions. NOT IN with a subquery that can produce a NULL is a classic bug: the whole predicate becomes unknown and you get zero rows.

Core intuition

"Compared to an overall number" ⇒ scalar subquery. "Is in / not in a set" ⇒ IN for a static-ish list, EXISTS for "does a related row exist". "Not in a set" and the set might contain NULL ⇒ NOT EXISTS, never NOT IN.

Scalar + derived table — customers above the average customer's revenue

SELECT c.name, rev.revenue
FROM customers c
JOIN (
    SELECT o.customer_id,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'delivered'
    GROUP BY o.customer_id
) AS rev ON rev.customer_id = c.customer_id
WHERE rev.revenue > (
    SELECT AVG(t.revenue)
    FROM (
        SELECT SUM(oi.quantity * oi.unit_price) AS revenue
        FROM orders o
        JOIN order_items oi ON oi.order_id = o.order_id
        WHERE o.status = 'delivered'
        GROUP BY o.customer_id
    ) AS t
);
Result
namerevenue
Alice Nguyen360.00
Bob Martin600.00

Delivered revenues are 600 / 360 / 275 / 40; their average is 1275 / 4 = 318.75. Only Bob and Alice clear it. (A CTE would let you write that subquery once — this is exactly the case §5 is for.)

    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p     ON p.product_id = oi.product_id
    WHERE o.customer_id = c.customer_id
      AND p.category = 'Software'

ORDER BY c.name;

Common mistakes
  • NOT IN (subquery with NULLs) → zero rows. Use NOT EXISTS or add WHERE col IS NOT NULL.
  • A scalar subquery that returns more than one row → runtime error.
  • Derived table without an alias → syntax error.
  • Repeating a big subquery verbatim in two places instead of using a CTE.
  • Correlated subquery in SELECT that runs per row when a join would do it once — a real performance trap on big tables.
  • Assuming IN and EXISTS always plan the same — usually similar, but not guaranteed.
When this comes up in interviews

"Second highest salary", "customers who bought all products", "managers with ≥5 reports" — these are subquery questions, and they're extremely common. NOT EXISTS for "bought all / missing none" is a pattern worth drilling. Overkill: deeply nested correlated subqueries where a JOIN + GROUP BY or a window function is both faster and clearer.

Practice problems

7 · Window Functions (the deep one)

A window function computes a value for each row using a window of related rows — without collapsing the result. That is the whole point: GROUP BY gives you one row per group; OVER (PARTITION BY …) gives you every original row plus the group-level number. The clause has three parts: PARTITION BY (which rows share a window), ORDER BY (order within the window — required for ranking and offset functions), and the frame (ROWS/RANGE BETWEEN … AND … — which slice of the ordered partition to aggregate).

They run after WHERE/GROUP BY/ HAVING and before ORDER BY/ LIMIT, so you cannot filter on a window result in the same SELECT — you wrap it in a CTE or subquery and filter outside. "Top 3 per group", "latest row per group", "running total", "compare to previous row", "percent of total" are all window-function questions, and this is the single highest-leverage SQL topic for product-company interviews.

Core intuition

Hear "per group but keep the detail rows", or "compared to the previous / next / first", or "running / cumulative / rolling", or "Nth highest per" → window function. If you need to filter on that computed number, you'll need two query levels.

7a · ROW_NUMBER vs RANK vs DENSE_RANK

All three number rows within a partition by an ORDER BY. ROW_NUMBER is always 1, 2, 3, 4 — arbitrary among ties. RANK gives ties the same number then skips (1, 1, 3). DENSE_RANK ties without skipping (1, 1, 2). Use ROW_NUMBER for "exactly one row per group" (dedupe, latest-per-key); RANK/DENSE_RANK for "top N including ties".

Cities ranked by customer count — all three functions

SELECT
    city,
    COUNT(*) AS customers,
    ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC) AS row_number,
    RANK()       OVER (ORDER BY COUNT(*) DESC) AS rank,
    DENSE_RANK() OVER (ORDER BY COUNT(*) DESC) AS dense_rank
FROM customers
GROUP BY city;
Result
citycustomersrow_numberrankdense_rank
Austin2111
Seattle2211
Chicago1332
Denver1432

Austin and Seattle both have 2 customers. ROW_NUMBER still forces 1 and 2 (which one gets 1 is engine-dependent without a tie-breaker in the OVER … ORDER BY). RANK gives both 1 then jumps to 3; DENSE_RANK gives both 1 then 2.

7b · Top-N per group

The canonical pattern: number rows within each partition, then filter in an outer query.

Each customer's two highest-value orders

WITH ranked AS (
    SELECT
        o.customer_id,
        o.order_id,
        SUM(oi.quantity * oi.unit_price) AS order_value,
        ROW_NUMBER() OVER (
            PARTITION BY o.customer_id
            ORDER BY SUM(oi.quantity * oi.unit_price) DESC
        ) AS rn
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    GROUP BY o.customer_id, o.order_id
)
SELECT customer_id, order_id, order_value
FROM ranked
WHERE rn <= 2

7c · LAG / LEAD — reach across rows

LAG(col, n, default) reads n rows back in the ordered partition; LEAD reads forward. This is "difference from previous row", "days since last order", "did the value change" — without a self join.

Gap between each customer's consecutive orders

SELECT
    o.customer_id,
    o.order_id,
    o.order_date,
    LAG(o.order_date) OVER w AS prev_order_date,
    o.order_date
      - LAG(o.order_date) OVER w AS days_since_prev
FROM orders o
WINDOW w AS (PARTITION BY o.customer_id ORDER BY o.order_date)
ORDER BY o.customer_id, o.order_date;

7d · Running totals, moving averages & the frame

With an ORDER BY in OVER but no explicit frame, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which means all rows with an order-key ≤ the current row's, so ties are lumped together. For a true row-by-row running total, say ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. A rolling window of the last 3 rows is ROWS BETWEEN 2 PRECEDING AND CURRENT ROW. This distinction is a favourite interview follow-up.

Cumulative delivered revenue + 3-order moving average

WITH daily AS (
    SELECT o.order_id, o.order_date,
           SUM(oi.quantity * oi.unit_price) AS order_value
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'delivered'
    GROUP BY o.order_id, o.order_date
)
SELECT
    order_date,
    order_value,
    SUM(order_value) OVER (ORDER BY order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
    ROUND(AVG(order_value) OVER (ORDER BY order_date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2)     AS moving_avg_3
FROM daily
ORDER BY order_date;

7e · Share of total, NTILE, FIRST_VALUE

An OVER () with no PARTITION and no ORDER BY aggregates the whole result — perfect for "percent of grand total". NTILE(k) splits the ordered partition into k roughly equal buckets (quartiles, deciles). FIRST_VALUE/LAST_VALUE/NTH_VALUE pull a specific row's value into every row.

Each customer's delivered revenue, its share, and which half they're in

SELECT
    c.name,
    SUM(oi.quantity * oi.unit_price) AS revenue,
    ROUND(100.0 * SUM(oi.quantity * oi.unit_price)
          / SUM(SUM(oi.quantity * oi.unit_price)) OVER (), 1) AS pct_of_total,
    NTILE(2) OVER (ORDER BY SUM(oi.quantity * oi.unit_price) DESC) AS revenue_half
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN customers c    ON c.customer_id = o.customer_id
WHERE o.status = 'delivered'
GROUP BY c.name
ORDER BY revenue DESC;
Result

SUM(SUM(...)) OVER () is a window over the grouped rows: the inner SUM is the per-customer total, the outer sums those four totals to 1275. NTILE(2) over 4 rows → two buckets of two.

Common mistakes
  • Filtering on a window result in the same SELECT (WHERE rn = 1) — wrap it in a CTE/subquery first.
  • LAST_VALUE returning the current row because the default frame ends at CURRENT ROW — add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.
  • Running total that jumps on tied ORDER BY values — that's the default RANGE frame; switch to ROWS.
  • ROW_NUMBER where ties must share a rank — use RANK/DENSE_RANK.
  • Mixing a window function into GROUP BY as if it were an aggregate — it runs after grouping, over the grouped rows.
  • Forgetting PARTITION BY resets every function (rank, running total, lag) at each partition boundary.
When this comes up in interviews

The defining topic of a product-company SQL round. "Top 3 salaries per department", "consecutive login streak", "month-over- month growth", "latest event per user", "median / percentile" — all window functions. If you're weak on one thing, make it this. Overkill: a window function for a plain "one number per group" (that's GROUP BY), or NTILE/ NTH_VALUE when a simple RANK filter is what's asked. Also overkill in OLTP code paths where the sort is expensive at scale — fine in interviews, flag it in real design.

8 · Recursive CTEs

A recursive CTE walks a graph or generates a sequence. It has two halves joined by UNION ALL: the anchor (a normal query — the starting rows) and the recursive member (a query that joins the CTE to itself, producing the next layer from the previous one). It repeats the recursive member until it yields no new rows. PostgreSQL requires the keyword WITH RECURSIVE; MySQL 8+ too.

The two things it's for: hierarchies — org charts, category trees, bill-of-materials, "all reports under a manager", "all ancestors of a comment" — and series generation — a row per day/month to left-join sparse data onto, or filling an ID gap. Use UNION (not ALL) to auto-dedupe if the graph has diamonds, carry a depth column and cap it as a safety net, and know PG's CYCLE clause exists for genuinely cyclic graphs.

Core intuition

"All descendants / ancestors", "explode the tree", "traverse until", "every date between" ⇒ recursive CTE. Anchor = where you start. Recursive member = given a row I already have, what's the next one? Termination = when the join finds nothing.

Worked query — the full org tree with depth and path

WITH RECURSIVE org AS (
    SELECT employee_id, name, manager_id, title,
           1 AS depth,
           name AS path
    FROM employees
    WHERE manager_id IS NULL              -- anchor: the CEO

    UNION ALL

    SELECT e.employee_id, e.name, e.manager_id, e.title,
           o.depth + 1,
           o.path || ' > ' || e.name     -- recursive: attach each report
    FROM employees e
    JOIN org o ON e.manager_id = o.employee_id
)
SELECT depth, name, title, path
FROM org
ORDER BY path;

Series generation — one row per month, to fill gaps

WITH RECURSIVE months AS (
    SELECT DATE '2024-01-01' AS month
    UNION ALL
    SELECT (month + INTERVAL '1 month')::date
    FROM months
    WHERE month < DATE '2024-06-01'
)
SELECT m.month, COUNT(o.order_id) AS orders_placed
FROM months m
LEFT JOIN orders o
       ON date_trunc('month', o.order_date) = m.month
GROUP BY m.month
ORDER BY m.month;

Common mistakes
  • Omitting RECURSIVE (required in PG/MySQL even though some engines infer it).
  • No terminating condition in the recursive member → runs to the engine's recursion cap and errors.
  • UNION ALL on a cyclic graph → infinite rows; use UNION, a depth cap, or the CYCLE clause.
  • Referencing the CTE twice in the recursive member — most engines allow it exactly once.
  • SELECT * in the recursive member when column types don't line up with the anchor.
  • Recursing when a plain self-join to a fixed depth (e.g. "manager and skip-manager only") would do.
When this comes up in interviews

Sometimes — and it's a screening filter. Org-hierarchy and "all subtasks / all reports" questions are the common form; a chunk of candidates freeze on them, so being fluent is a real edge. Series generation for gap-filling shows up in analytics-heavy roles. Overkill: a recursive CTE for a fixed 2–3 level lookup, or when the platform has a native path/ltree/array type. If the hierarchy is deep and hot, real systems store a materialized path or closure table instead — worth saying out loud.

9 · Advanced String Functions

Concatenate with || (Postgres/standard) or CONCAT(...) (also MySQL; CONCAT treats NULL as empty, whereas || propagates NULL — use CONCAT_WS for null-safe joining with a separator). Case: UPPER/LOWER, and INITCAP (Postgres only) for Title Case. Slice with SUBSTRING(s FROM p FOR n), LEFT/RIGHT, and SPLIT_PART(s, delim, k) to grab the k-th token. Find with POSITION(sub IN s) / STRPOS. Clean with TRIM/LTRIM/ RTRIM, REPLACE, LPAD/RPAD. Measure with LENGTH.

For pattern work: LIKE (%, _), ILIKE for case-insensitive (PG), and full regex via ~ / regexp_replace / regexp_matches (PG) or REGEXP_REPLACE/REGEXP_LIKE (MySQL 8). To roll many rows into one string, use STRING_AGG(expr, delim ORDER BY …) in Postgres — MySQL's equivalent is GROUP_CONCAT(expr ORDER BY … SEPARATOR delim).

Core intuition

String questions are usually "parse a field that should have been three columns" (split), "normalize for comparison" (lower + trim), "validate a format" (regex / LIKE), or "collapse a group into a list" (STRING_AGG). Identify which before reaching for functions.

Worked query — derive codes, emails and cleaned forms from a name

SELECT
    name,
    UPPER(LEFT(SPLIT_PART(name, ' ', 2), 3))                       AS surname_code,
    LOWER(SPLIT_PART(name, ' ', 1) || '.' ||
          SPLIT_PART(name, ' ', 2)) || '@corp.com'                 AS email,
    LENGTH(name)                                                   AS name_len,
    REGEXP_REPLACE(name, '[aeiou]', '', 'gi')                      AS no_vowels,
    LPAD(customer_id::text, 4, '0')                                AS padded_id
FROM customers
ORDER BY customer_id;

Common mistakes
  • SQL string positions are 1-based, not 0-based — SUBSTRING(s, 1, 3) is the first three chars.
  • x || NULL is NULL in Postgres; use CONCAT/CONCAT_WS or COALESCE.
  • INITCAP doesn't exist in MySQL; || concatenation doesn't (by default) either.
  • LIKE is case-sensitive in Postgres — use ILIKE or LOWER(col) LIKE.
  • Un-anchored regex validation (~ 'abc' matches anywhere) — anchor with ^…$.
  • GROUP_CONCAT silently truncates at group_concat_max_len (default 1024 in MySQL).
  • Leading/trailing whitespace defeating a join or GROUP BY — TRIM first.
When this comes up in interviews

Light but real — "fix the capitalization of names", "valid-email filter", "patients whose conditions contain DIAB1", "comma-separate the products sold each day". Know SPLIT_PART, LIKE/regex, and STRING_AGG/GROUP_CONCAT. Overkill: elaborate regex when a LIKE would pass, or parsing structured text in SQL that should be parsed in the application. Heavy string munging in queries is a smell worth naming.
