1. Amazon-style order management ⭐

⭐ Build fully & push to GitHub

Your core transactional-backend story. Small enough to finish, deep enough to talk about for an hour.

Problem statement

Manage an order's whole lifecycle — from cart checkout through payment, inventory reservation, fulfilment, shipping, and returns — with correct state transitions, idempotent checkout, and no overselling when many customers race for the last unit.

Functional requirements

  • Create an order from a cart: validate items, re-price server-side, validate the address.
  • Reserve inventory atomically; release it on cancel or on a payment timeout.
  • Authorize payment at checkout, capture on ship.
  • Order state machine: CREATED → PAYMENT_PENDING → CONFIRMED → PACKED → SHIPPED → DELIVERED, with CANCELLED and RETURNED branches.
  • Split shipments when items ship from different warehouses.
  • Idempotent checkout keyed by a client-supplied token.
  • Order history + tracking for the customer; admin can cancel, refund, and re-drive stuck orders.

Architecture

Service view 
client ─▶ API gateway ─▶ Order Service (Spring Boot) ──▶ Postgres (orders, items, outbox)
                              │  reserve/release        ▲
                              ├──────────────▶ Inventory Service ─▶ Postgres (stock, reservations)
                              ├──────────────▶ Payment Service   ─▶ gateway adapter (auth/capture)
                              │
                     outbox poller ─▶ Kafka ─▶ Fulfilment consumer ─▶ advances state, writes shipments
                                            └─▶ Notification Service (email/SMS)

Outbox pattern: the order row and an outbox_events row are written in one local transaction; a poller publishes to Kafka. This removes the dual-write problem (DB commit + broker publish can't be atomic).

Tech stack

Java 21, Spring Boot 3 (Web, Validation, Data JPA), PostgreSQL, Flyway, Kafka (or RabbitMQ), Redis for idempotency keys, Resilience4j, Testcontainers for integration tests, Docker Compose to run the lot. OpenAPI via springdoc.

Build-order milestones

  1. orders + order_items entities, POST/GET endpoints, Flyway migrations, Testcontainers Postgres test.
  2. Idempotency-Key handling — return the same order for a repeated key.
  3. Inventory reservation with SELECT … FOR UPDATE (or optimistic version); a scheduled job releases expired holds.
  4. Payment Service stub with authorize/capture; wire the state machine (guard illegal transitions).

What to say about this in an interview
  • State machine — enumerate the states and legal transitions; illegal transitions return 409, not 500.
  • Dual-write problem & the outbox — why you can't atomically commit to Postgres and publish to Kafka, and how the outbox fixes it.
  • Oversell prevention — pessimistic lock vs optimistic version vs reservation-with-TTL; you chose reservations so the cart hold doesn't block other buyers.
  • Idempotent checkout — client token → unique constraint; a retried request never creates a second order.
  • Saga / compensation — cancellation isn't a rollback, it's forward-recovery actions.
  • At-least-once + idempotent consumers — the fulfilment consumer must tolerate duplicate events.

2. Scalable notification service ⭐

⭐ Build fully & push to GitHub

The cleanest way to show you understand queues, retries, and back-pressure.

Problem statement

One internal API that any service calls to notify a user. It delivers across channels (email, SMS, push, in-app) reliably — with retries, rate limiting, deduplication, user preferences, and delivery tracking — while shielding the caller from provider latency and outages.

Functional requirements

  • Accept a request: template id + recipient + data + one or more channels.
  • Resolve the user's contact details, channel preferences, and quiet hours.
  • Render the template; enqueue one job per channel.
  • Deliver via provider adapters (SES / Twilio / FCM) behind a common interface, with a fake adapter for local dev.
  • Retry failed sends with exponential backoff + jitter; dead-letter after N attempts.
  • Deduplicate by idempotency key; enforce per-user and global rate limits.
  • Track per-channel delivery status; accept provider webhooks (delivered / bounced).
  • Channel fallback (push fails → email); expose an in-app notification feed.

Architecture

Flow 
caller ─▶ Notification API ─▶ Postgres (notification + per-channel deliveries)
                │
                └─▶ exchange ─┬─▶ email.q  ─▶ Email worker  ─▶ SES adapter ─┐
                              ├─▶ sms.q    ─▶ SMS worker    ─▶ Twilio       │ update status
                              └─▶ push.q   ─▶ Push worker   ─▶ FCM          │
                                                   │ fail                  ▼
                                          retry.q (TTL delay) ──▶ back to channel queue
                                                   │ attempts exhausted
                                                   ▼
                                                 DLQ  ──▶ alert + manual redrive

Redis: idempotency SETNX, token-bucket rate limits.   Provider webhook ─▶ API ─▶ status = DELIVERED/BOUNCED

Tech stack

Java 21, Spring Boot 3, Spring AMQP + RabbitMQ (delayed/TTL queues give you backoff for free; Kafka + a scheduler is the alternative), PostgreSQL, Flyway, Redis with Bucket4j for rate limiting, Resilience4j for retry / circuit-breaking, Micrometer + Prometheus for metrics, Testcontainers, Docker Compose.

Build-order milestones

  1. API + persistence + POST/GET, Flyway, Testcontainers.
  2. Template rendering (Handlebars/Thymeleaf) + request validation.
  3. Publish per-channel messages to RabbitMQ; a console/fake worker "delivers".
  4. Retry with exponential backoff + jitter via TTL/delayed queues; DLQ + a redrive endpoint.
  5. Idempotency + dedupe (Redis SETNX); per-user token-bucket rate limit (Bucket4j).
  6. User preferences + quiet hours + channel fallback ordering.
  7. Provider webhooks update delivery status; add a real SES or Twilio adapter.
  8. In-app feed endpoint; Micrometer metrics (queue depth, delivery latency, failure rate); README + diagram.
What to say about this in an interview
  • Why a queue — decouples the caller's latency from the provider's; absorbs spikes; lets you retry without blocking anyone.
  • At-least-once + idempotent consumers — "exactly-once delivery" is a myth; you dedupe with an idempotency key and a time window.
  • Backoff + jitter — why plain exponential backoff causes retry storms (thundering herd) and jitter spreads them.
  • DLQ — poison messages must leave the main flow; you alert and redrive manually.
  • Queue-per-channel — isolates a slow/broken provider so SMS problems don't stall email.
  • Rate limiting — token bucket, per-user and global, to respect provider quotas and protect users from spam.

3. Payments quoting & settlement service ⭐

⭐ Build fully & push to GitHub — this is your ACID showcase

Pricing, tax calculation, route quoting, and money movement with real financial-correctness guarantees.

Problem statement

Given a shipment request (origin, destination, weight, service level), produce a firm, immutable price quote — base rate + surcharges + tax — with an expiry. Later, convert a quote to a booking, authorize payment, and on delivery settle the actual charge against that quote, writing balanced double-entry ledger records so the books always reconcile and no customer is ever double-charged.

Functional requirements

  • Quote: compute route distance → apply a versioned rate card → add surcharges (fuel, remote-area) → compute tax by jurisdiction → return an immutable quote with line items and expiresAt.
  • Booking: convert a non-expired quote to a booking; authorize payment; idempotent.
  • Settlement: on delivery, capture the final amount (may differ from quote within a tolerance); post an adjustment; write ledger entries.
  • Refunds and adjustments as forward ledger transactions, never row edits.
  • Double-entry ledger: every transaction's debits equal its credits.
  • Daily reconciliation: ledger totals vs the payment gateway; a report endpoint.
  • Idempotency on every state-changing call.

Architecture

Two services, one ledger 
            ┌───────────────── Quote Service (stateless) ─────────────────┐
request ─▶  │ route/distance ─▶ rate card (v) ─▶ surcharges ─▶ tax rules(v) │ ─▶ immutable quote
            └────────────────────────────────────────────────────────────┘
                         │ quoteId
                         ▼
   ┌──────────────── Settlement Service (stateful, owns the ledger) ───────────────┐
   │ booking: quote ─▶ payment.authorize()   (Idempotency-Key)                     │
   │ settle:  payment.capture() ─▶ ONE serializable txn:                           │
   │            debit  customer_ar        credit revenue                           │
   │            debit  tax_expense/holding credit tax_payable                      │
   │          (sum of entries in the txn == 0 — asserted)                          │
   │ outbox ─▶ Kafka (SettlementPosted)                                            │
   └──────────────────────────────────────────────────────────────────────────────┘
        nightly: reconciliation job  →  ledger vs gateway  →  report

Tech stack

Java 21, Spring Boot 3, Spring Data JPA, PostgreSQL, Flyway. Money as BigDecimal in minor units (or Moneta / JSR-354) — never double. Explicit transaction isolation (SERIALIZABLE for ledger posts, with retry-on-conflict), optimistic version on accounts. Resilience4j for the gateway adapter, Kafka + outbox for events, Testcontainers, jqwik for property-based money-math tests, Docker Compose.

Build-order milestones

  1. Decide the money type; build the pricing engine (rate-card lookup, distance stub, surcharges) as a pure, unit-tested module.
  2. Tax module: rule table by jurisdiction + per-rule rounding; unit-tested against known cases.
  3. Quote persistence with expiry; line items immutable once written.
  4. Booking = quote → payment.authorize() via a fake adapter; idempotency keys store-and-replay the response.
  5. Double-entry ledger: accounts + balanced entries inside one SERIALIZABLE transaction; a test asserts sum(D) = sum(C) per txn.
  6. Settlement: capture, handle final ≠ quoted within tolerance, post the adjustment entry.
  7. Refund / void flows as forward transactions; outbox events.
  8. Nightly reconciliation job (ledger vs gateway) + report endpoint; property-based tests on rounding & associativity; README with an "ACID guarantees" section.
What to say about this in an interview
  • Never float/double for money — BigDecimal or integer minor units; state your rounding mode and where you round.
  • Double-entry ledger — every transaction balances; you never UPDATE a balance, you append entries and derive the balance. Corrections are new transactions.
  • Isolation levels — a read-modify-write on an account balance under READ COMMITTED is a lost-update bug; you use SELECT … FOR UPDATE or SERIALIZABLE + retry. Reference the traced race on the HLD page.
  • Idempotency keys — store the first response and replay it; a retried settle never double-captures.
  • Quote immutability + versioning — the rate card and tax rules are versioned; a quote records which versions priced it, so it's reproducible and auditable.
  • Auth vs capture, tolerance on the final amount, and reconciliation as the safety net that catches anything the code missed.

4. RAG-based internal support assistant ⭐

⭐ Build fully & push to GitHub — your GenAI project

Spring Boot + Spring AI + pgvector. Pairs directly with the GenAI page.

Problem statement

An assistant that answers support questions from the company's own documents (wiki, runbooks, policies, resolved tickets) with citations — instead of hallucinating. It must say "I don't know" when the retrieved context is weak, and you must be able to measure how good it is.

Functional requirements

  • Ingest documents from sources (Markdown, PDF, Confluence export); chunk, embed, store in a vector store.
  • On a question: retrieve top-k relevant chunks (vector similarity, optionally + keyword), assemble a grounded prompt, call the LLM, return an answer with source citations.
  • Conversation memory for follow-ups.
  • Confidence gate: if the best retrieval score is below a threshold, return "I don't know / ask this team" instead of guessing.
  • Thumbs up/down feedback; admin re-index; basic PII / prompt-injection filtering.
  • Per-source access control (a user only retrieves from spaces they can see).

Architecture

Ingest path and query path 
INGEST:  loaders (md/pdf/html) ─▶ token-aware chunker (size + overlap)
         ─▶ embedding model (API) ─▶ Postgres + pgvector (document_chunks.embedding)

QUERY:   question ─▶ embed ─▶ pgvector top-k (cosine)  ─┐
                     └─▶ (optional) BM25 keyword search ─┴─▶ merge + re-rank
         ─▶ prompt = system + retrieved chunks + history + question
         ─▶ LLM (Claude via Spring AI) ─▶ answer + citations
         ─▶ grounding gate: max_score < τ  ⇒  "I don't know"
         ─▶ log(question, chunk_ids, scores, tokens, cost)

Redis: chat session memory + embedding cache.

Tech stack

Java 21, Spring Boot 3, Spring AI (chat + embedding clients), PostgreSQL + pgvector (HNSW index), Flyway, Redis, Testcontainers, Docker Compose. LLM: Claude (Anthropic API). Optional Elasticsearch/Postgres full-text for the keyword half of hybrid search. Small labelled Q&A set for evaluation.

Build-order milestones

  1. Schema + CREATE EXTENSION vector + Flyway; document / chunk entities.
  2. Ingestion: Markdown + PDF loader → token-aware chunker (with overlap) → embed → store; job status endpoint.
  3. Retriever: top-k cosine query; tune k and chunk size; write retrieval_logs.
  4. Chat endpoint: prompt template (system + context + question), Spring AI call to Claude, parse out citations.
  5. Grounding gate: if max_score < τ → "I don't know"; enforce that every claim maps to a citation.
  6. Conversation memory (last N turns, older turns summarized) in Redis; follow-up questions resolve pronouns from history.
  7. Add keyword search + merge (hybrid); optional re-rank. Evaluate on the labelled set: retrieval precision@k, answer relevance, citation precision.
  8. Feedback loop + admin re-index + PII / prompt-injection filter; metrics (retrieval latency, tokens & cost per query); README with the diagram and your eval numbers.
What to say about this in an interview
  • Full RAG architecture — ingest (load → chunk → embed → index) and query (embed → retrieve → assemble → generate) as two separate pipelines.
  • Chunking trade-offs — small chunks = precise but lose context; large = context-rich but dilute the embedding; overlap preserves boundaries. You tuned this against recall.
  • Hybrid retrieval — vector catches paraphrase, keyword catches exact terms (error codes, config keys); merge both.
  • pgvector + HNSW — approximate nearest neighbour; why you didn't need a dedicated vector DB at this scale.
  • Grounding & anti-hallucination — the confidence gate and mandatory citations; "I don't know" is a feature.
  • Evaluation — you measured retrieval precision and answer relevance on a labelled set, not "it looked good in a demo".
  • Cost / latency — cache embeddings, cap context size, use a cheaper model for routing/summarizing memory.

5. Hotstar-style streaming platform

Design & write-up only. See the fuller worked HLD on the Electives page.

Problem statement

Deliver live and on-demand video to millions of concurrent viewers with adaptive quality, low rebuffering, and tolerance for enormous spikes (a cricket match final).

Functional requirements

  • Upload / ingest VOD; ingest a live RTMP/SRT feed.
  • Transcode to an adaptive-bitrate ladder; segment into HLS/DASH chunks + a rolling manifest.
  • Serve segments via CDN; the client player picks bitrate by measured bandwidth.

  6. WebSocket live tracking.
  7. Delivery-fee / surge engine.
  8. Ratings + wire in the notification service.
What to say about this in an interview
  • It's a composition — geo search (project 6), a fan-out dispatch/matching (project 6), a notification service (project 2), an order state machine (project 1). Say that explicitly; it shows you see the building blocks.
  • Three-sided coordination — the state machine spans customer, restaurant, and partner; each transition is an event.

14. AI agent for workflow automation (human-in-the-loop)

Design & write-up only — though the milestone plan is buildable if you want a second GenAI project. See the GenAI page on agents.

Problem statement

An agent that executes multi-step internal workflows ("onboard this vendor": create records, request approvals, send emails, schedule tasks) by planning and calling tools — pausing for a human on risky or irreversible steps.

Functional requirements

  • Accept a goal in natural language + context.
  • The agent plans and executes via a registered, typed tool set (createTicket, sendEmail, updateCRM, scheduleMeeting).
  • Classify each step by risk; pause and request approval for high-risk / irreversible ones.
  • Resume on approve / reject, feeding the human's note back into context.
  • Full audit trail of every thought, tool call, and result.
  • Per-tool timeout + retry; a tool allow-list and spend caps as guardrails.
  • Inspect / replay a run.

Architecture

A durable workflow engine with an LLM planner 
Orchestrator (Spring Boot) run loop:
  state = { goal, history[], pendingApproval? }   ── persisted every step in Postgres
  iterate:
    LLM(history, toolSchemas) ─▶ one of:
        • tool call      ─▶ risk check ─▶ if low: execute adapter, append result
                                        ─▶ if high: persist "AWAIT_APPROVAL", notify, STOP
        • final answer   ─▶ mark DONE
  resume(approvalId, decision) ─▶ rehydrate state ─▶ continue loop

tools = Spring beans + JSON-schema descriptors    Redis lock: one active step per run
Kafka: run events     idempotency: each tool call keyed so resume never re-fires a side effect

Tech stack

Java 21, Spring Boot 3, Spring AI function/tool calling with Claude, PostgreSQL (durable, resumable run + step state), Redis, Kafka, Testcontainers. Tools are Spring beans exposing a JSON-schema descriptor.

Sample REST API

POST /api/v1/runs
{ "goal": "Onboard vendor Acme Corp", "context": { "vendorEmail": "ops@acme.com" },
  "toolAllowList": ["createTicket", "sendEmail", "updateCRM"] }
  ──▶ 201 { "runId": "run_5", "status": "PLANNING" }

GET  /api/v1/runs/run_5
  ──▶ 200 {
    "status": "AWAIT_APPROVAL",
    "steps": [
      { "n": 1, "kind": "tool", "toolName": "createTicket", "state": "DONE" },
      { "n": 2, "kind": "tool", "toolName": "sendEmail", "risk": "HIGH", "state": "PENDING_APPROVAL",
        "input": { "to": "ops@acme.com", "subject": "Welcome" } }
    ]
  }

POST /api/v1/runs/run_5/approvals/2   { "decision": "approve", "note": "looks good" }
  ──▶ 200 { "status": "RUNNING" }

Sample database schema

agent_runs(id text primary key, goal text, status text, state_json jsonb,
           created_at, updated_at)
agent_steps(run_id text, idx int, kind text, tool_name text,
            input_json jsonb, output_json jsonb, risk text, approval_state text,
            primary key (run_id, idx))
tool_registry(name text primary key, schema_json jsonb, risk_default text, enabled bool)
approvals(id bigserial primary key, run_id text, step_idx int, decision text,
          note text, decided_by bigint, decided_at timestamptz)
run_events(id bigserial primary key, run_id text, type text, payload jsonb, at)

Build-order milestones

  1. Tool interface + 2–3 fake tools + their JSON-schema descriptors.
  2. Agent loop (LLM ↔ tool calls) end-to-end for a low-risk goal.
  3. Durable run / step state in Postgres — kill the process mid-run and resume.
  4. Risk classification + the "AWAIT_APPROVAL" pause (persist & stop).
  5. Approval endpoint + resume, injecting the human's note into context.
  6. Per-tool retry / timeout + tool allow-list + a spend-cap guardrail.
  7. Full audit trail + a run-inspector endpoint.
  8. Idempotent tool execution — a resume must never re-send an email — + an eval over sample workflows.
What to say about this in an interview
  • The agent loop — ReAct-style: observe → think → act → repeat, with tool schemas given to the model.
  • Durable, resumable state is the hard part — this is really a workflow engine; the LLM is just the planner. State lives in Postgres, not in memory.
  • Human-in-the-loop as a first-class state, not a callback — the run genuinely stops and is rehydrated later.
  • Idempotency on resume — the single most important correctness property; every side-effecting tool call is keyed so it never double-fires.
  • Guardrails — allow-list, spend caps, risk gates; you never let the model free-run irreversible actions.
  • Auditability — every thought and tool result is logged for replay and debugging.

15. AI-augmented code review assistant

Design & write-up only.

Problem statement

A bot that comments on pull requests — flagging likely bugs, security issues, convention violations, and missing tests — as a useful first-pass reviewer that saves humans time without being noisy.

Functional requirements

  • Receive a PR webhook (GitHub / GitLab); fetch the diff + changed files + surrounding context.
  • Run deterministic checks (linters, static analysis, coverage delta) and LLM checks (per-hunk bug/risk reasoning).
  • Dedupe and rank findings by severity × confidence; drop anything below a threshold.
  • Post inline comments + one summary comment.
  • Respect a repo config (.reviewbot.yml — rules, ignored paths, threshold).
  • Don't re-comment on unchanged code across force-pushes.
  • Token / cost budget per PR; learn from resolved vs dismissed comments.

Architecture

Deterministic tools + LLM judgment 
GitHub ──webhook──▶ Webhook Service (verify signature) ─▶ enqueue review job (Kafka)
                                                              │
  Review Worker:  fetch diff ─▶ parse hunks
     ├─ deterministic: checkstyle / spotbugs / semgrep  (shelled out in a sandbox) ─▶ findings
     └─ LLM: per hunk + file context ─▶ Claude ─▶ structured findings (JSON schema)
  Aggregator: dedupe by (file,line,rule) ─▶ rank severity×confidence ─▶ apply repo threshold
  VCS adapter: post inline comments + summary
  Redis: per-PR dedupe hashes (skip lines already commented on an earlier push)
  Postgres: review_runs, findings, feedback

Tech stack

Java 21, Spring Boot 3, Spring AI + Claude, PostgreSQL, Kafka, Redis, Docker (a sandbox to run the linters), GitHub / GitLab REST adapters. The LLM is prompted per hunk and must return findings matching a strict JSON schema.

Sample REST / webhook API

POST /api/v1/webhooks/github        (PR opened / synchronize)
  ──▶ 202 { "reviewRunId": "rr_9" }

GET  /api/v1/reviews/rr_9
  ──▶ 200 {
    "status": "COMPLETED",
    "findings": [
      { "file": "OrderService.java", "line": 88, "severity": "HIGH", "category": "bug",
        "message": "Possible NPE: `payment` may be null when status == FAILED",
        "confidence": 0.72, "source": "llm" },
      { "file": "OrderService.java", "line": 12, "severity": "LOW", "category": "style",
        "message": "Unused import", "confidence": 1.0, "source": "checkstyle" }
    ]
  }

POST /api/v1/findings/f_3/feedback   { "resolution": "dismissed", "reason": "false positive" }  ──▶ 202

Sample database schema

review_runs(id text primary key, repo text, pr_number int, head_sha text,
            status text, prompt_tokens int, cost_usd numeric(8,4), created_at)
findings(id text primary key, run_id text, file text, line int,
         severity text, category text, message text, confidence numeric(4,2),
         source text, dedupe_key text, posted bool)
repo_configs(repo text primary key, yaml jsonb, updated_at)
feedback_events(id bigserial primary key, finding_id text, resolution text,
                reason text, at timestamptz)

Build-order milestones

  1. Webhook intake — verify the signature, enqueue a job.
  2. Diff fetch + hunk parsing.
  3. Deterministic analyzers (checkstyle / spotbugs / semgrep) → findings.
  4. LLM analyzer per hunk with file context → schema-validated findings.
  5. Aggregator: dedupe by dedupe_key, rank by severity × confidence, apply the repo threshold.
  6. VCS adapter: post inline + summary comments.
  7. Cross-push dedupe (skip unchanged lines) + a per-PR cost cap.
  8. Feedback capture + a precision metric (accepted / total) to tune the prompt and threshold.
What to say about this in an interview
  • Hybrid by design — rules where rules are exact (unused import), the LLM only for judgment calls (this null path looks reachable).
  • The noise problem — precision over recall; a noisy bot gets muted. Confidence thresholds and severity gating exist for this.
  • Dedupe across force-pushes — comment once; track a dedupe_key so a rebase doesn't repeat 30 comments.
  • Per-hunk context windows — you feed the hunk + surrounding lines + the file's imports, not the whole repo.
  • Structured LLM output — a strict JSON schema with retry-on-invalid, so the aggregator can trust the shape.
  • Cost control — a token budget per PR; skip generated files and vendored code.
  • Feedback loop — dismissed/accepted rates are how you measure the bot, and they feed prompt + threshold tuning.
