React fundamentals + hooks

React is a library for building UIs as a tree of components — functions that take props (inputs from the parent) and return JSX describing what to render. When a component's state or props change, React re-runs the function, diffs the new element tree against the old one (the "virtual DOM"), and applies the minimal set of real DOM changes. You describe what the UI should look like for a given state; React figures out the DOM mutations.

JSX is syntax sugar for React.createElement. {expr} embeds a JS expression; attributes are camelCase (onClick, className); lists render via .map() and each item needs a stable key so the diff can track it across renders.

A component with state, effect, and a child

function ProductList({ category }) {          // prop from the parent
  const [products, setProducts] = useState([]);   // state: [value, setter]
  const [loading, setLoading]   = useState(true);
  const [error, setError]       = useState(null);

  useEffect(() => {                            // run after render, when deps change
    let cancelled = false;
    setLoading(true);
    fetch(`/api/products?category=${category}`)
      .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); })
      .then(data => { if (!cancelled) { setProducts(data.content); setLoading(false); } })
      .catch(e  => { if (!cancelled) { setError(e); setLoading(false); } });
    return () => { cancelled = true; };        // cleanup: ignore a stale response
  }, [category]);                              // dependency array

  if (loading) return <Spinner />;
  if (error)   return <p role="alert">Failed to load.</p>;

  return (
    <ul>
      {products.map(p => (
        <ProductCard key={p.id} product={p} />   // stable key per item
      ))}
    </ul>
  );
}

The hooks you actually use

HookPurposeGotcha
useStateLocal component state. Setter triggers a re-render.Updates are batched & async; use the updater form setN(n => n + 1) when the next value depends on the previous.
useEffectSide effects after render: data fetch, subscriptions, timers.Missing deps ⇒ stale closures; return a cleanup fn; runs twice in dev StrictMode (by design).
useContextRead a value from a Context.Provider ancestor without prop-drilling.Every consumer re-renders when the context value changes — memoize the value.
useRefMutable box that survives renders without causing one; also holds DOM nodes.Changing .current does not re-render.
useMemo / useCallbackCache an expensive value / a stable function identity across renders.Premature use adds noise; measure first.
useReducerState with complex transitions — a local Redux.Reach for it when useState calls cluster together.
Core intuition

A component is a pure function of (props, state) → UI. "Rendering" just calls that function; it should have no side effects. Anything that touches the outside world (network, DOM, timers, subscriptions) goes in useEffect, with a dependency array saying when to re-run it and a cleanup function saying how to undo it.

Rules of hooks

  • Only call hooks at the top level of a component or another hook — never in a condition, loop, or nested function. React tracks them by call order.
  • Only call them from React functions (components or custom useX hooks).
  • State is immutable — never mutate it; create a new object/array (setItems([...items, x])).
Common mistakes
  • Missing/wrong useEffect deps. The lint rule react-hooks/exhaustive-deps is right almost always — listen to it.
  • Mutating state: items.push(x); setItems(items) — same reference, no re-render.
  • Index as key in a reorderable/filterable list — breaks the diff and loses input focus/state.
  • Fetching without cleanup — a slow response for the old category lands after you've switched, and overwrites the new data.
  • Derived state in useState — if it can be computed from props/state during render, just compute it; don't copy it into state.
Interviewer probe

"What triggers a re-render?" — a state setter, a new prop, or a parent re-rendering. "Why does the dependency array matter?" — it's how the effect knows when to re-run and which values it closes over; omit a dep and you read a stale value. "Controlled vs uncontrolled input?" — controlled: value lives in React state (value + onChange); uncontrolled: the DOM holds it, read via a ref. "useRef vs useState?" — ref for values that change without needing a re-render (a timer id, a previous value).

Redux concepts

Redux is a predictable state container for state that many far-apart components need (the logged-in user, a cart, cached server data). One store holds the whole app state as a single immutable object. You never mutate it; you dispatch an action (a plain object describing what happened), and a pure reducer (state, action) => newState computes the next state. Components select the slices they need and re-render when those slices change.

The one-way data flow 
UI event ──dispatch(action)──▶ store ──▶ reducer(state, action) ──▶ new state
   ▲                                                                   │
   └───────────────── components re-render via useSelector ◀───────────┘

Unidirectional: the only way to change state is an action, so every change is describable, loggable, and replayable (time-travel debugging).

Redux Toolkit — the modern, non-boilerplate way

// cartSlice.js
import { createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] },        // { productId, name, qty, pricePaise }[]
  reducers: {
    // Immer lets you "mutate" a draft; it produces a new immutable state
    addItem(state, action) {
      const line = state.items.find(i => i.productId === action.payload.productId);
      if (line) line.qty += 1;
      else state.items.push({ ...action.payload, qty: 1 });
    },
    removeItem(state, action) {
      state.items = state.items.filter(i => i.productId !== action.payload);
    },
    clear(state) { state.items = []; },
  },
});

export const { addItem, removeItem, clear } = cartSlice.actions;
export default cartSlice.reducer;

// selectors — derive, don't store
export const selectCartCount = (s) => s.cart.items.reduce((n, i) => n + i.qty, 0);
export const selectCartTotal = (s) => s.cart.items.reduce((t, i) => t + i.qty * i.pricePaise, 0);

// store.js
import { configureStore } from "@reduxjs/toolkit";
import cart from "./cartSlice";
export const store = configureStore({ reducer: { cart } });

Using it in a component

import { useSelector, useDispatch } from "react-redux";
import { addItem, selectCartCount } from "./cartSlice";

function AddToCartButton({ product }) {
  const dispatch = useDispatch();
  const count = useSelector(selectCartCount);   // re-renders only when the count changes
  return (
    <button onClick={() => dispatch(addItem({
      productId: product.id, name: product.name, pricePaise: product.pricePaise,
    }))}>
      Add to cart ({count})
    </button>
  );
}

Async (calling an API) doesn't belong in a reducer — reducers are pure. Use createAsyncThunk (or RTK Query for server-cache) which dispatches pending / fulfilled / rejected actions you handle in extraReducers.

Common mistakes
  • Putting everything in Redux. Form field state, "is this dropdown open" — that's local useState. Redux is for shared, app-wide state.
  • Storing derived data (cart total) in the store instead of computing it in a selector — now it can drift out of sync.
  • Mutating state outside Immer (plain Redux, or a selector) — breaks change detection and time-travel.
  • Selecting a new object each render (useSelector(s => ({a: s.a}))) — always "changed", re-renders every time. Select primitives, or use createSelector / shallowEqual.
  • Reaching for Redux before you need it — Context + useReducer, or a server-cache lib (React Query), covers many apps.
Interviewer probe

"Why not just Context?" — Context is a transport, not a state manager; every consumer re-renders on any change, and there's no dev-tools, middleware, or structured updates. "What makes a reducer a reducer?" — pure, synchronous, (state, action) => newState, no side effects, no mutation. "Where does the API call go?" — a thunk / RTK Query, which dispatches lifecycle actions the reducer handles. "How does a component avoid needless re-renders?" — select the narrowest slice possible, memoize derived selectors.

Node / Express basics

Node runs JavaScript on the server on a single-threaded event loop with non-blocking I/O: instead of a thread per request, one thread juggles thousands of connections, parking each while it waits on I/O and resuming it via callbacks/promises. Great for I/O-bound APIs; a CPU-bound task blocks everyone (offload to a worker thread or another service). This is the opposite of the Spring/Tomcat thread-per-request model — the mental adjustment for a Java dev.

A small Express REST API

import express from "express";
import { z } from "zod";

const app = express();
app.use(express.json());                       // body parser -> req.body

// middleware: runs in order, calls next() to continue (like a filter chain)
app.use((req, res, next) => {
  req.id = crypto.randomUUID();
  console.log(`${req.id} ${req.method} ${req.path}`);
  next();
});

const CreateProduct = z.object({
  name: z.string().min(1),
  pricePaise: z.number().int().positive(),
});

app.get("/api/products", async (req, res, next) => {
  try {
    const items = await productRepo.search(req.query.category, req.query.page ?? 0);
    res.json({ content: items });
  } catch (err) { next(err); }                 // forward to the error handler
});

app.post("/api/products", requireAuth, requireRole("admin"), async (req, res, next) => {
  try {
    const body = CreateProduct.parse(req.body); // throws on invalid -> 400 below
    const created = await productRepo.create(body);
    res.status(201).location(`/api/products/${created.id}`).json(created);
  } catch (err) { next(err); }
});

// central error handler — 4 args marks it as such
app.use((err, req, res, next) => {
  if (err instanceof z.ZodError)
    return res.status(400).json({ message: "validation failed", issues: err.issues });
  console.error(req.id, err);
  res.status(err.status ?? 500).json({ message: err.expose ? err.message : "server error" });
});

app.listen(3000);

Auth middleware (JWT) — mirrors the Spring filter

import jwt from "jsonwebtoken";

export function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer ")) return res.status(401).json({ message: "no token" });
  try {
    req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET); // { sub, roles }
    next();
  } catch {
    res.status(401).json({ message: "invalid token" });
  }
}
export const requireRole = (role) => (req, res, next) =>
  req.user?.roles?.includes(role) ? next() : res.status(403).json({ message: "forbidden" });
Core intuition

Express is a chain of middleware functions (req, res, next). Each does its bit and calls next() to pass control on, or ends the response. It's the same "chain of responsibility" as the Spring Security filter chain, just explicit and in one file. async/await over promises is how you write non-blocking I/O that reads sequentially.

Common mistakes
  • Blocking the event loop — a synchronous loop over 100k items, JSON.parse of a huge payload, bcrypt in a tight loop. Every other request stalls.
  • Unhandled promise rejections — forgetting try/catch in an async route (or not calling next(err)) crashes or hangs the request.
  • Not validating req.body — trusting client JSON straight into the DB.
  • Secrets / config from anywhere but process.env; committing .env.
  • One process, one core. Use the platform's replica count, or the cluster module / PM2, to use all cores.
Interviewer probe

"Node is single-threaded — how does it handle concurrency?" — non-blocking I/O + event loop; the OS/libuv thread pool does the actual I/O, JS resumes via callbacks. "What breaks that model?" — CPU-bound work; it blocks the loop, so offload it. "Express middleware order — does it matter?" — yes, it's sequential; auth before the handler, error handler last. "How is this different from Spring MVC?" — thread-per-request vs one loop; blocking JDBC is fine in Spring, a blocking call is poison in Node.

MongoDB schema basics

MongoDB stores documents (BSON, JSON-like) in collections. No fixed schema is enforced by default, no joins in the SQL sense, no multi-collection transactions you'd lean on. The design question is always: embed related data in one document, or reference it by id in another collection?

EmbedReference
When"contains" / "belongs to one" — read together, bounded sizeMany-to-many, large/unbounded, or edited independently
ReadOne query gets everythingMultiple queries or a $lookup
WriteUpdate the whole subtree together (atomic per doc)Update pieces independently
ExampleOrder → its line items & shipping addressOrder → the customer; product catalog

The eCommerce model, Mongo-style (Mongoose)

import { Schema, model, Types } from "mongoose";

const productSchema = new Schema({
  name:        { type: String, required: true },
  slug:        { type: String, required: true, unique: true },
  pricePaise:  { type: Number, required: true, min: 0 },
  stock:       { type: Number, default: 0 },
  category:    { type: String, index: true },          // denormalized: just the name
  createdAt:   { type: Date, default: Date.now },
});

const orderSchema = new Schema({
  user:   { type: Types.ObjectId, ref: "User", required: true, index: true }, // reference
  status: { type: String, enum: ["PENDING", "PAID", "SHIPPED", "CANCELLED"], default: "PENDING" },
  // embed the lines — always read with the order, bounded, and price is snapshotted
  items: [{
    productId:      { type: Types.ObjectId, ref: "Product" },
    name:           String,        // copied at purchase time
    qty:            { type: Number, min: 1 },
    unitPricePaise: Number,
  }],
  shippingAddress: {               // embedded sub-document, not its own collection
    line1: String, city: String, pincode: String,
  },
  totalPaise: Number,
  placedAt:   { type: Date, default: Date.now },
});
orderSchema.index({ user: 1, placedAt: -1 });          // "my orders, newest first"

export const Product = model("Product", productSchema);
export const Order   = model("Order", orderSchema);

Querying

// list a user's recent orders (uses the compound index)
const orders = await Order.find({ user: userId }).sort({ placedAt: -1 }).limit(20).lean();

// join to the customer only when you need it
const withUser = await Order.findById(id).populate("user", "email name");

// aggregation: revenue per day
const revenue = await Order.aggregate([
  { $match: { status: "PAID" } },
  { $group: { _id: { $dateToString: { format: "%Y-%m-%d", date: "$placedAt" } },
              total: { $sum: "$totalPaise" } } },
  { $sort: { _id: 1 } },
]);
Core intuition

Model around how the app reads the data, not around normalized entities. If a screen always shows an order with its lines, store them in one document so one query serves the screen. Duplication (the product name copied into the order line) is fine and often correct — it's a historical snapshot, and there's no join to keep it live anyway.

Common mistakes
  • Modeling like SQL — a collection per entity, everything referenced, $lookup everywhere. You lose Mongo's main advantage and gain slow queries.
  • Unbounded embedded arrays — embedding "all comments" in a post; the 16MB document limit and rewrite cost eventually bite. Reference when the child set grows without limit.
  • No indexes — every query is a collection scan. Index your filter + sort fields; check with .explain().
  • Assuming ACID across documents — single-document writes are atomic; multi-document needs an explicit transaction (replica set) and costs more.
  • Storing money as a float. Use integer minor units (paise/cents) or Decimal128.
Interviewer probe

"Embed or reference the order lines?" — embed: bounded, always read with the order, price snapshotted. "Embed or reference the customer?" — reference: shared across many orders, edited independently. "How do you make find({user, sort: placedAt}) fast?" — a compound index { user: 1, placedAt: -1 }. "SQL vs Mongo for this shop?" — a relational DB is the safer default for orders/payments (transactions, constraints); Mongo shines for catalog, sessions, event logs, flexible content.
