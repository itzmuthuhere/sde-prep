LLMs & Transformers

A large language model is a function that takes a sequence of tokens (word-ish chunks — "tokenization" splits "unhappiness" into ["un", "happiness"] or similar) and predicts a probability distribution over the next token. That's the whole objective: given everything so far, what comes next. Text generation is just running that prediction in a loop, appending each sampled token and feeding the result back in (autoregressive decoding). Everything that feels intelligent — following instructions, writing code, summarizing — is an emergent consequence of getting very good at that one prediction task over a large chunk of the internet, then being nudged with instruction tuning and RLHF to prefer helpful, well-formatted answers.

The transformer is the architecture that made this scale. Its key move is self-attention. For each token, the model computes three vectors: a query ("what am I looking for?"), a key ("what do I offer?"), and a value ("what I'll contribute if selected"). Every token's query is compared against every other token's key (a dot product → a relevance score), the scores are softmax-normalized into weights, and each token's new representation becomes the weighted sum of all the values. In plain terms: every token gets to look at every other token and pull in the information that's relevant to it. "The animal didn't cross the street because it was too tired" — attention is how "it" binds to "animal" and not "street". Stack ~30–100 of these layers (with "heads" doing this in parallel on different subspaces, plus feed-forward layers in between) and the model builds progressively richer, more contextual representations.

Why this beat RNNs: an RNN processes tokens one at a time, threading a hidden state forward, so training can't parallelize across the sequence and long-range dependencies decay. Attention looks at the whole sequence at once — fully parallel on a GPU during training, and any token can directly influence any other regardless of distance. The cost is that attention is O(n²) in sequence length (every token vs every token), which is why context windows are a scaling battle and why long prompts get expensive fast. At inference the model caches the keys and values of tokens it's already seen (the KV cache), so generating token n+1 doesn't reprocess the whole prompt — but that cache grows with context length and dominates memory for long conversations.

The generation loop, conceptually

tokens = tokenize(prompt)
while not done:
    logits = model(tokens)          # distribution over the vocabulary, for the *next* token
    next_id = sample(logits,         # temperature: 0 = argmax (deterministic-ish),
                     temperature=0.7, #   higher = flatter distribution = more variety
                     top_p=0.9)       # nucleus: sample only from the smallest set summing to 0.9
    tokens.append(next_id)
    if next_id == EOS or len(tokens) > max_tokens:
        done = True
return detokenize(tokens)
Core intuition

An LLM is a next-token predictor with no memory beyond its context window and no ability to "look things up" unless you put the information in the prompt. Attention is content-based routing: it lets each position gather exactly the earlier context it needs. Two consequences you'll rely on constantly — (1) whatever the model knows about your domain has to be in the context (that's why RAG exists), and (2) output is sampled, so the same prompt can give different answers; set temperature=0 when you need repeatability.

Terms worth being able to define
  • Parameters / weights — the learned numbers (7B, 70B, …). More ≈ more capable and more expensive per token.
  • Context window — max tokens (prompt + output) the model can attend to at once (e.g. 8K, 128K, 1M).
  • Embedding — a vector representation of a token or a whole text; nearby vectors ≈ similar meaning. Used for retrieval (next section).
  • Pre-training vs instruction tuning vs RLHF — learn language → learn to follow instructions → learn to prefer human-preferred answers.
  • Hallucination — confident, fluent, wrong. It's not a bug in the usual sense; the model optimizes plausibility, not truth.
Common mistakes
  • Treating the model as a database. It has no rows; it has a compressed, lossy statistical picture of its training data with a knowledge cutoff.
  • Assuming determinism. Non-zero temperature, load-balanced backends, and model updates all make output drift. Pin versions; test with temperature=0.
  • Ignoring tokenization. Costs, limits, and truncation are all in tokens, not characters (~4 chars/token for English, worse for code and other languages).
  • "Just increase the context window." Cost and latency scale with tokens, and models attend unevenly — facts buried mid-context get missed ("lost in the middle").

Vector DBs & Semantic Search

Keyword search matches strings; semantic search matches meaning. An embedding model maps a piece of text to a fixed-length vector (say 768 or 1536 floats) such that texts with similar meaning land near each other in that space. "How do I reset my password?" and "I forgot my login credentials" share no keywords but sit close as vectors. So the retrieval recipe is: embed every document chunk once at ingest time, store the vectors; at query time embed the query and find the nearest stored vectors. "Nearest" is usually cosine similarity (angle between vectors) or dot product.

Doing that exactly means comparing the query against every vector — fine for 10K chunks, hopeless for 50M. A vector database (Pinecone, Weaviate, Qdrant, Milvus, pgvector on Postgres, Elasticsearch's dense_vector) builds an approximate nearest neighbor (ANN) index — most commonly HNSW, a navigable small-world graph you greedily walk toward the query. You trade a small amount of recall (you might miss a true top-10 result occasionally) for 100–1000× faster queries. Knobs like ef_search / ef_construction tune that recall-vs-latency trade-off.

For a backend engineer the practical questions are: Do I even need a dedicated vector DB? If you're on Postgres already and have < ~1M chunks, pgvector keeps everything in one system, one backup story, one transaction boundary — start there. Reach for a dedicated store when you need scale, high write throughput, metadata filtering at speed, or managed ops. Metadata filtering matters more than people expect: you almost always want "nearest chunks where tenant_id = X and doc_type = 'policy' and not archived", and doing the filter pre-ANN vs post-ANN changes both correctness and performance.

pgvector — the "it's just a table" option

CREATE EXTENSION vector;

CREATE TABLE doc_chunks (
  id          bigserial PRIMARY KEY,
  document_id bigint NOT NULL REFERENCES documents(id),
  tenant_id   bigint NOT NULL,
  content     text   NOT NULL,
  embedding   vector(1536) NOT NULL          -- from your embedding model
);

-- ANN index (HNSW). Without it, queries are exact but do a full scan.
CREATE INDEX ON doc_chunks USING hnsw (embedding vector_cosine_ops);

-- retrieval: 8 nearest chunks for this tenant, cosine distance
SELECT id, document_id, content,
       1 - (embedding <=> $1) AS similarity   -- <=> is cosine distance
FROM   doc_chunks
WHERE  tenant_id = $2                          -- metadata filter
ORDER  BY embedding <=> $1
LIMIT  8;
Core intuition

A vector DB is a nearest-neighbor index over embeddings, nothing more mystical. The embedding model defines the meaning space; the DB just makes "find the closest N" fast and filterable. Two hard rules: (1) the same embedding model must embed both documents and queries — mixing models gives garbage; (2) changing the embedding model later means re-embedding your entire corpus.

When it comes up in interviews vs overkill

Right call: search over support tickets, docs, code, or product catalog descriptions where users phrase things differently than the source. Overkill: exact lookups (order by ID), structured filtering ("orders > $100 last week" — that's SQL), small fixed FAQ (just put all 20 Q&As in the prompt). Often the best answer is hybrid: BM25 keyword score + vector score, combined (e.g. Reciprocal Rank Fusion) — keyword catches exact names, IDs, and rare terms that embeddings smear together.

Common mistakes
  • Different embedding models for index and query — or silently upgrading the model and not re-indexing.
  • No metadata filtering plan — multi-tenant data with no tenant_id filter is a data-leak incident waiting to happen.
  • Treating similarity score as a probability — 0.82 cosine isn't "82% relevant"; calibrate a threshold against your own data, and expect the top result to sometimes be irrelevant.
  • Embedding huge chunks — a 4,000-token chunk produces a mushy "average" vector that matches everything weakly. See chunking under RAG.
  • Forgetting it's eventually consistent — a freshly written doc isn't retrievable until it's embedded and indexed.

LLM APIs & Fine-Tuning

Calling a hosted LLM is a plain HTTPS request: you send a list of messages with roles (system, user, assistant), some parameters (model, temperature, max_tokens, optionally tools and a response schema), and you get back generated text plus a usage block counting input and output tokens — which is exactly what you're billed on, output tokens usually 3–5× the price of input. You'll almost always want streaming (server-sent events, token by token) so the user sees output in ~300 ms instead of waiting 8 s for the full response. The system message is where durable instructions, persona, and rules go; it's not magic, but models are tuned to weight it heavily.

The judgment call interviewers love: you need the model to behave differently than it does out of the box — do you prompt, retrieve (RAG), or fine-tune? These solve different problems and stack:

Prompting / few-shotRAGFine-tuning
FixesFormat, tone, task framing, simple rulesMissing knowledge — private, fresh, or too large for contextMissing behavior / style / implicit task skill the model can't be instructed into
Data needed0–20 examples in the promptA corpus + retrieval pipelineHundreds–thousands of clean input→output pairs
Iteration speedSecondsMinutes–hours (re-index)Hours–days per run; a real ML loop
Keeps facts current?Only if you paste them inYes — swap the document, doneNo — knowledge is frozen at training time
Cost shapeLonger prompts = more tokens/callRetrieval infra + more input tokensTraining cost up front; often shorter prompts after
Main riskPrompt gets huge and brittleRetrieval quality is now your ceilingOverfitting, catastrophic forgetting, stale, hard to debug

Default order: prompt first, add RAG when it's a knowledge gap, fine-tune last and only when you have evidence prompting can't get there and you have the data. Classic fine-tune wins: enforcing a rigid output style across thousands of calls (and cutting the giant instruction prompt), a narrow classification/extraction task where you have labeled data, matching a very specific domain voice. Classic mistake: fine-tuning to "teach it our product docs" — that's a retrieval problem, and the fine-tuned model will still hallucinate and now can't be updated without retraining. Modern fine-tuning is usually LoRA / PEFT (train a small adapter, not all the weights) — cheaper, and you can host many adapters over one base model.

A typical call with tools + structured output (shape, provider-agnostic)

POST /v1/chat/completions
{
  "model": "some-capable-model",
  "temperature": 0,
  "messages": [
    { "role": "system", "content": "You are a support triage assistant. Be terse." },
    { "role": "user",   "content": "My invoice #4491 is wrong, I was double charged." }
  ],
  "tools": [{
    "type": "function",
    "function": {
      "name": "lookup_invoice",
      "description": "Fetch an invoice by number",
      "parameters": { "type": "object", "properties": { "number": { "type": "string" } },
                      "required": ["number"] }
    }
  }],
  "response_format": { "type": "json_schema", "json_schema": { /* force valid JSON out */ } }
}

// -> model responds with tool_calls: [{ name: "lookup_invoice", arguments: {"number":"4491"} }]
// your code runs it, appends a role:"tool" message with the result, calls again -> final answer
Core intuition

Prompting changes the instructions. RAG changes the knowledge. Fine-tuning changes the model. The further down that list, the more it costs to build and change, and the more it can go wrong silently. Reach for the cheapest lever that could plausibly work, measure, then escalate.

Common mistakes
  • Fine-tuning for knowledge. It bakes in facts you can't update and doesn't stop hallucination. Use RAG.
  • No eval set. You cannot tell if a prompt change or a fine-tune helped without a held-out set of cases and a scoring method. Build the eval before the fix.
  • Not pinning the model version — a provider's "latest" pointer moves and your carefully-tuned prompt regresses overnight.
  • Ignoring token budgets in the response — no max_tokens cap means a runaway generation and a surprise bill; too low means truncated JSON.
  • Sending PII to a third-party API without checking the data-processing terms / retention. This is a real compliance question in interviews now.

RAG Systems

Retrieval-Augmented Generation: before answering, fetch relevant text from your own data and put it in the prompt, then ask the model to answer using only that. It's how you get an LLM to answer questions about private, large, or fresh information without fine-tuning and with a citation trail. Architecturally it's two pipelines:

RAG architecture 
INGEST (offline, on document change)
  source docs ─▶ parse/clean ─▶ chunk ─▶ embed each chunk ─▶ upsert {vector, text, metadata}

QUERY (per request)
  user question
     ├─▶ (optional) rewrite / expand the query
     ├─▶ embed ─▶ vector search (+ keyword search) ─▶ top-K chunks
     ├─▶ (optional) rerank K chunks with a cross-encoder ─▶ top-N
     ├─▶ build prompt:  system rules + N chunks (with source IDs) + question
     └─▶ LLM ─▶ answer + citations ─▶ (optional) verify answer is grounded in chunks

Chunking is the highest-leverage design decision and it's all trade-offs. Chunks that are too large dilute the embedding (one vector trying to represent many ideas) and waste context tokens on irrelevant text; chunks too small lose the context needed to be understood ("It must be renewed every 90 days" — what must?) and fragment answers across many retrievals. Fixed-size chunking (e.g. 500 tokens, 50-token overlap) is the simple baseline; structure-aware chunking (split on headings, code blocks, table rows) is usually better because it respects natural boundaries. The overlap exists so a sentence split across a boundary still appears whole somewhere. A common upgrade: embed small chunks for precise matching but retrieve the surrounding parent section for context ("small-to-big").

Retrieval failure modes — most "the LLM is dumb" complaints are actually retrieval bugs:

FailureLooks likeUsual cause / fix
Missing content"I don't have information on that" for something that is in the docsBad chunking, doc never ingested, query/doc vocabulary mismatch → add keyword/hybrid search, query rewriting
Retrieved but not in top-KRight doc exists, wrong ones ranked above itK too small, no reranker → add a cross-encoder reranker, raise K then rerank down
Retrieved but ignoredAnswer contradicts a chunk that was in the promptToo many chunks / lost-in-the-middle, weak prompt → fewer, better chunks; instruct "answer only from context"
Wrong extractionChunk is right, answer misreads itConflicting chunks, table flattened to mush → dedupe, better parsing, ask for quotes
Stale answerCites an old policyIngest lag, no versioning, old + new both retrieved → recency filter, delete superseded docs
No-answer not handledConfidently makes something up when nothing relevant was foundNo similarity floor → if best score < threshold, return "not found" instead of calling the LLM

Query pipeline, sketched

def answer(question, tenant_id):
    chunks = hybrid_search(question, tenant_id, k=20)      # vector + BM25, fused
    if not chunks or chunks[0].score < MIN_SCORE:
        return NoAnswer("Nothing relevant in the knowledge base.")

    chunks = rerank(question, chunks)[:6]                  # cross-encoder, keep best 6
    context = "\n\n".join(f"[{c.doc_id}#{c.idx}] {c.text}" for c in chunks)

    prompt = [
      {"role": "system", "content":
        "Answer ONLY from the context. Cite sources as [doc#chunk]. "
        "If the context doesn't contain the answer, say so."},
      {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
    ]
    ans = llm(prompt, temperature=0)
    return ans  # optionally: a second call to check every claim is supported by context
Core intuition

RAG turns "what does the model know?" into "what can my search find and fit in the context?" — so your retrieval quality is the ceiling on your answer quality. A better model can't fix a chunk that was never retrieved. Debug RAG by first checking what got retrieved, not what the LLM said.

Common mistakes
  • No evaluation of retrieval separately from generation. Track retrieval recall/precision (did the right chunk come back?) apart from answer quality.
  • One giant K. Stuffing 30 chunks in raises cost, latency, and "lost in the middle" — retrieve wide, rerank, keep few.
  • Ignoring document structure — PDFs with tables/multi-column layouts parsed to flat text destroy meaning before you even chunk.
  • No "I don't know" path — a similarity floor and a grounded-ness check are what keep RAG honest.
  • Never re-indexing after an embedding model change, or mixing chunk versions in the same index.
  • Putting access control only in the prompt ("don't show HR docs to non-HR") — filter at the query, not with a plea to the model.

Agentic AI Workflows

An agent is an LLM in a loop with tools. Instead of one prompt → one answer, the model is given a goal and a set of tools (functions it can call — search, DB query, HTTP request, code execution), and on each turn it decides: call a tool, or finish. Your code executes the tool, feeds the result back, and the model goes again. This is the ReAct pattern — reason, act, observe, repeat — and it's what lets an LLM do multi-step work: "find the customer's last order, check if it shipped, draft a reply."

The design spectrum, cheapest and most reliable first:

PatternWhat it isUse when
Single callOne prompt, one responseThe task fits in one shot. Most tasks.
Chain / pipelineFixed sequence of calls, output → input (extract → classify → draft)You know the steps ahead of time
RouterOne call picks a branch; each branch is its own prompt/chainDistinct request types needing different handling
Tool-use loop (agent)Model chooses tools and when to stopSteps depend on intermediate results; genuinely dynamic
Multi-agentSpecialized agents (planner, researcher, critic) coordinateRarely worth it — coordination overhead is real; try one good agent first

The engineering hard parts are not the prompt. They are: loop control (max iterations, cost/time budget, detecting "stuck in a loop"), error handling (a tool 500s — retry? tell the model? abort?), state (what's carried between turns; the context window fills up fast), determinism & testing (the path varies run to run), and safety — an agent with a delete_file or send_email tool and a prompt-injected document is a genuine hazard. Give agents the narrowest tools that work, make destructive actions require confirmation, and log every tool call.

The agent loop, unrolled

messages = [system_prompt, user_goal]
for step in range(MAX_STEPS):                 # hard cap — non-negotiable
    resp = llm(messages, tools=TOOLS, temperature=0)
    if resp.tool_calls:
        for call in resp.tool_calls:
            try:
                result = TOOLS[call.name](**call.args)   # you run it, with your own authz checks
            except Exception as e:
                result = {"error": str(e)}               # let the model react, don't crash the loop
            messages.append(tool_result_message(call.id, result))
    else:
        return resp.content                   # model decided it's done
    if cost_so_far > BUDGET or time_so_far > DEADLINE:
        return "Stopping: budget exceeded. Partial progress: ..."
return "Stopping: hit step limit."
Core intuition

An agent is a while loop where an LLM picks the next function call. That's powerful and inherently less predictable than a fixed pipeline. Prefer the most constrained pattern that solves the task — a chain you can test beats an agent you can only hope about. Add autonomy only where the steps truly can't be known in advance.

Common mistakes
  • No iteration cap or budget — one bad run burns $40 and 5 minutes.
  • Too many tools — 30 tools in the prompt and the model picks wrong; group them or use a router.
  • Broad, powerful tools — run_sql(query) instead of get_order(id). Least privilege applies to tools.
  • Trusting tool output / retrieved docs as instructions — prompt injection. Keep a boundary: data is data, only the system prompt gives orders.
  • Building multi-agent systems first — the demo impresses, the reliability doesn't. Start with one agent.
  • No observability — you can't debug an agent without a trace of every prompt, tool call, and result.

LangChain & LangGraph Basics

LangChain is a toolkit that wraps the common pieces — model clients, prompt templates, output parsers, vector-store connectors, document loaders, retrievers, tool/agent scaffolding — behind uniform interfaces, so swapping an OpenAI model for an Anthropic one, or Pinecone for pgvector, is a config change. Its composition style is LCEL (LangChain Expression Language): you pipe components with |, and the resulting chain gets streaming, batching, and async for free. It's genuinely useful for getting a RAG prototype running in an afternoon; the criticism is that the abstractions can obscure what prompt is actually being sent, so know how to drop to the raw SDK when debugging.

LangGraph is the same team's answer to "agents need real control flow." You model the workflow as a graph: nodes are functions (call the model, run a tool, check a condition), edges are transitions, and a shared state object is threaded through. Conditional edges let you branch ("if the model asked for a tool, go to the tool node; else go to END"), and cycles are first-class (that's the agent loop). It adds persistence / checkpointing (pause a run, resume it, time-travel), human-in-the-loop (interrupt before a risky node for approval), and a clear place to enforce the caps and budgets from the last section. Think of it as a state machine for LLM workflows.

LCEL RAG chain (LangChain) — the whole thing

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt            # ChatPromptTemplate with {context} and {question}
    | model             # ChatOpenAI / ChatAnthropic / ...
    | StrOutputParser()
)
chain.invoke("What's our refund window?")     # also .stream(), .batch(), .ainvoke()

LangGraph — an agent as a graph

graph = StateGraph(AgentState)                 # state = {messages: [...], steps: int}
graph.add_node("model", call_model)
graph.add_node("tools", run_tools)
graph.set_entry_point("model")
graph.add_conditional_edges("model", lambda s:
    "tools" if s["messages"][-1].tool_calls else END)
graph.add_edge("tools", "model")              # loop back
app = graph.compile(checkpointer=SqliteSaver(...))   # persistence + resumability
Core intuition

LangChain = batteries-included wiring for the common LLM-app pieces. LangGraph = when your app has branches, loops, retries, pauses, and approvals, model it explicitly as a graph instead of burying control flow in prompt logic. Neither is required — a plain HTTP client and a for loop is a legitimate choice, especially for one well-defined workflow.

Common mistakes
  • Cargo-culting LangChain for a single simple call — you've added a dependency and a layer of indirection for a 10-line request.
  • Not logging the rendered prompt — when a chain misbehaves, the first question is "what exactly did we send?" Turn on tracing (LangSmith or callbacks).
  • Version churn — the library moves fast; pin versions and read the migration notes.
  • Using LangGraph state as a dumping ground — unbounded message history blows the context window; prune or summarize.

Prompt Engineering Techniques

Prompt engineering is specifying the task precisely enough that a next-token predictor produces what you want, reliably, across inputs. For production the goal isn't a clever one-off prompt — it's a robust template that holds up over thousands of varied inputs and is versioned like code.

TechniqueWhat / why
Role + explicit taskSystem message sets persona and hard rules; be concrete about the exact output wanted ("Return a JSON array of {name, amount}").
Few-shot examples2–5 input→output pairs. The single most effective lever for format and edge-case handling. Cover the tricky cases, not just the happy path.
Chain-of-thought"Think step by step" / "reason before answering" — improves multi-step reasoning and math. For structured output, have it reason in a scratchpad field, then a final field.
Structured outputAsk for JSON and use the API's schema/JSON-mode to enforce it. Parse and validate; retry on failure.
DelimitersWrap user content in <doc>...</doc> or triple backticks so the model (and you) can tell instructions from data — also a first line of defense against injection.
Give an out"If you're not sure, say 'I don't know'." Reduces confident fabrication.
DecompositionSplit a complex ask into chained smaller prompts — each is testable and cheaper to fix.
Prefilling / output primingStart the assistant turn with {" or Here is the summary: to lock format.

Structure that works well: role → task → rules/constraints → examples → the input (delimited) → output format reminder. Put the most important instruction near the start and restate the output format at the end (models weight both ends). Iterate against a fixed set of test inputs, not vibes — change one thing, re-run the set, compare.

Core intuition

The model does what's statistically implied by your prompt, not what you meant. Structure, examples, and explicit constraints narrow the distribution toward the answer you want. If it's getting something wrong, show it a correct example of exactly that case — that beats another paragraph of instructions almost every time.

Common mistakes
  • Negation-only instructions ("don't be verbose", "never mention X") — weak. Say what to do instead.
  • One mega-prompt doing five jobs — decompose; each piece becomes testable.
  • No delimiters around user input — the model can't tell your instructions from the user's text, and neither can an attacker's payload.
  • Tuning on one example — you fix that case and silently break three others. Keep a regression set.
  • Prompts as string literals scattered in code — version them, review changes, and log which version ran.
  • Asking for JSON without schema enforcement or a retry path — you'll get ```json fences, trailing prose, and the occasional invalid doc.

MCP — Model Context Protocol

MCP is an open protocol (introduced by Anthropic, now broadly adopted) that standardizes how an LLM application connects to external tools and data. The problem it solves: every AI app was re-implementing bespoke integrations for GitHub, Slack, Postgres, the filesystem, Jira… an N×M mess of clients and connectors. MCP makes it N+M — a tool provider writes one MCP server, and any MCP client (an IDE assistant, a chat app, your own agent) can use it. It's deliberately analogous to the Language Server Protocol, which did the same for editors and language tooling.

The architecture is client–server over JSON-RPC 2.0, either over stdio (local subprocess) or HTTP/SSE (remote). An MCP server exposes three things: tools (functions the model can call — create_issue, run_query), resources (readable data the client can pull into context — a file, a table schema, a wiki page), and prompts (reusable templated instructions the user can invoke). The host app discovers what a server offers at connect time and presents the tools to the model. For a backend engineer, "write an MCP server" is essentially "write a small adapter that exposes your internal API as a set of typed tool definitions" — plus auth, and being careful about what you expose.

An MCP server exposing one tool (TypeScript SDK, abridged)

const server = new McpServer({ name: "orders", version: "1.0.0" });

server.tool(
  "get_order",
  "Fetch an order by its ID",
  { orderId: z.string() },
  async ({ orderId }) => {
    const order = await db.orders.findById(orderId);      // your existing service
    if (!order) return { content: [{ type: "text", text: "Not found" }], isError: true };
    return { content: [{ type: "text", text: JSON.stringify(order) }] };
  }
);

await server.connect(new StdioServerTransport());        // or an HTTP transport
Core intuition

MCP is a USB-C port for LLM tools: one standard socket so integrations are built once and reused everywhere, instead of every app inventing its own plug. You'll either consume MCP servers (point your agent at an existing one) or publish one (wrap your service so assistants can use it) — usually the former.

Common mistakes / things to raise
  • Over-exposing. An MCP server is an API surface reachable by an LLM that may be steered by untrusted input — expose narrow, least-privilege tools, not execute_sql.
  • Auth as an afterthought — remote MCP servers need real authn/authz (OAuth is the direction); a tool call should run with the user's permissions, not the server's.
  • Prompt injection via resources — content pulled in as a "resource" can contain instructions; the client must keep the data/instruction boundary.
  • Assuming it replaces your API layer — it's an adapter for AI clients, sitting in front of the same services your normal API uses.
  • No rate limiting / auditing on tool calls — an agent can hammer a tool in a loop.

Production Trade-offs — Cost, Latency, Accuracy, Safety

This is where backend-engineer interviews for AI-adjacent roles spend the most time, because it's the part that's actually engineering. The four concerns trade against each other and you're expected to reason about the dials.

Cost

You pay per token, input + output, and output is the expensive half. Levers: pick the smallest model that passes your eval (route easy requests to a cheap model, hard ones to a strong one — "model cascade"); trim the prompt (few-shot examples and giant system prompts add up over millions of calls — this is a real reason to fine-tune); cache — exact-match response cache for repeated queries, semantic cache for near-duplicates, and prompt caching (providers discount the unchanged prefix of your prompt — put the static system prompt and few-shot block first); cap max_tokens; batch offline work at a discount. Always log per-request token counts and set per-user / per-tenant budgets and alerts.

Latency

A strong model's first token can be 500 ms–2 s; full responses several seconds. Stream so perceived latency is time-to-first-token, not total. Every extra chain step, tool call, or reranker is serial latency — parallelize independent retrievals, and use a small fast model for cheap sub-steps (query rewriting, routing, classification). Long context = slower and pricier, so retrieve few good chunks rather than many. Set aggressive timeouts and have a fallback (cached answer, cheaper model, "try again"). Speculative / predicted outputs and shorter outputs also help.

Accuracy

You cannot manage what you don't measure. Build an eval set of real inputs with expected outputs or a rubric; score with exact-match, or an LLM-as-judge for open-ended answers (cheaper than humans, needs its own validation), plus task metrics (retrieval recall, JSON-valid rate, citation-correct rate). Run it in CI on every prompt or model change. In production, sample and review, collect thumbs-up/down, watch for drift. Reduce errors with grounding (RAG + "answer only from context"), self-check passes, structured output + validation, and constraining the task. Accept that ~100% is not on the table — design the product to degrade gracefully (show sources, allow correction, keep a human in the loop for high-stakes actions).

Safety

Distinct risks, distinct mitigations: prompt injection (untrusted text — a retrieved doc, a web page, a tool result — carrying instructions the model follows) → keep the data/instruction boundary, least-privilege tools, confirm destructive actions, don't feed raw untrusted output into another privileged call; jailbreaks / harmful content → provider safety filters plus your own input/output moderation classifier; PII & data leakage → redact before sending, check the provider's retention/training terms, enforce tenant isolation in retrieval (filter, don't ask); hallucination in high-stakes paths → grounding, citations, human review; abuse & cost-DoS → rate limits, budgets, auth. Log prompts, responses, and tool calls for audit.

Worked trade-off: a customer-support answer bot

Requirement: answer from the help center, < 3 s perceived, cheap at 100K/day, must not invent policy.
Design: hybrid retrieval over chunked help docs → rerank to 5 chunks → small model with "answer only from context, cite, else escalate" → stream. Similarity floor routes no-match straight to a human. Prompt-cache the system + format block. Nightly eval set of 200 real tickets scored by an LLM judge + citation check; block deploys on regression.
Why: RAG (not fine-tune) because policies change weekly; small model because retrieval does the heavy lifting and eval passes; streaming for the latency budget; the floor + escalation is the safety net against confident wrong answers.

Core intuition

There's no "best" config — there's the cheapest, fastest setup that passes your eval and your safety bar. So the first move on any LLM feature is: define the eval and the failure budget. Everything after is turning dials (model size, K, context length, caching, routing) against that fixed target.

Common mistakes
  • Shipping without an eval set — every later change is a guess, and regressions are invisible.
  • Biggest model by default — often 5–20× the cost for accuracy your task doesn't need; benchmark the small one.
  • No streaming — users stare at a spinner for 6 seconds.
  • No cost guardrails — no max_tokens, no per-tenant budget, no alert; the bill teaches you.
  • Access control in the prompt instead of in the retrieval query / tool authz.
  • Treating prompt injection as theoretical — any agent with tools + untrusted input has a real attack surface.
  • No fallback path when the provider is slow or down.
