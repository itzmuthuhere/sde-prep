Low-Level Design — SOLID, Patterns & Class Modelling

Phase 2. An LLD round gives you a fuzzy prompt ("design a parking lot") and 45 minutes. The interviewer is watching one thing: can you turn requirements into a small set of classes with clear responsibilities, name the pattern that fits, and defend the trade-off when they push back. This page is the three things you get tested on — the SOLID principles as before/after code, the ten patterns that actually show up, and ten classic problems worked as design walkthroughs.

How to use this page. For SOLID, read the "bad" snippet and try to name the smell before scrolling to the fix. For each pattern, the trigger scenario box is the most important part — patterns are answers to specific problems, and quoting the trigger in an interview is what separates "I memorised the GoF book" from "I know when to reach for this". For the problems, sketch your own class list first, then compare. Tick items off to feed the home dashboard — aim for SOLID + 3 patterns a week, one problem per weekend.

How to run an LLD round

The failure mode is jumping straight to classes. Spend the first 5–10 minutes pinning down scope out loud: clarify requirements ("multiple floors? electric vehicles? monthly passes?"), then state the core use cases you will support and explicitly park the rest. Interviewers almost always want you to cut scope — a tight design of three use cases beats a sprawling one that never compiles.

Then work outside-in: identify the nouns (they become classes or enums), assign each one responsibility (if you can't say what a class is responsible for in one sentence, it's wrong), and define the relationships (has-a vs is-a — prefer composition). Only then write code, and only for the interesting parts: the pricing logic, the state machine, the concurrency point. Nobody wants to watch you type getters.

Keep the API-first habit: sketch the key method signatures (Ticket park(Vehicle v), boolean book(Show s, List<Seat> seats)) before their bodies. That surfaces the design decisions early and gives the interviewer something concrete to push on.

Core intuition

A class should have one reason to change, depend on abstractions, and be open for extension without editing its source. Every pattern below is just a disciplined way to get one of those three properties in a situation where the naive code loses it.

Common mistakes
  • Designing for requirements nobody asked for. "What if we add helicopters" — only if the interviewer says so.
  • Anemic domain model: all data in classes, all behaviour in one giant Service. Put behaviour next to the data it uses.
  • Pattern name-dropping. Saying "I'll use a Factory" without a creation problem to solve reads as cargo-culting.
  • Ignoring concurrency until asked. For parking / booking / ATM, name the race condition yourself.
  • One enum with a giant switch that you edit for every new type — the exact thing OCP and Strategy exist to prevent.

SOLID principles (bad → good)

Five heuristics for where to draw class boundaries. Each one below is a concrete smell and its fix — that's how they come up in interviews ("what's wrong with this class?"), not as definitions to recite.

S — Single Responsibility Principle

A class should have one reason to change. The classic violation is a domain object that also formats itself and persists itself: a change to the report layout, the database, or the tax rules all force edits to the same file, and the three concerns can't be tested or reused independently.

❌ Bad — Invoice does maths, formatting, and persistence

class Invoice {
    private List<LineItem> items;
    private Customer customer;

    double total() {
        return items.stream().mapToDouble(LineItem::amount).sum();
    }

    // reason to change #2: the print format
    void printInvoice() {
        System.out.println("INVOICE for " + customer.getName());
        items.forEach(i -> System.out.println(i.getName() + "  " + i.amount()));
        System.out.println("TOTAL: " + total());
    }

    // reason to change #3: the storage technology
    void saveToDatabase() {
        Connection c = DriverManager.getConnection("jdbc:...");
        // ... INSERT INTO invoices ...
    }
}

✅ Good — one responsibility per class

class Invoice {                       // domain + business rules only
    private final List<LineItem> items;
    private final Customer customer;
    Invoice(Customer c, List<LineItem> items) { this.customer = c; this.items = items; }
    double total() { return items.stream().mapToDouble(LineItem::amount).sum(); }
    List<LineItem> getItems() { return items; }
    Customer getCustomer() { return customer; }
}

class InvoicePrinter {               // changes only when the layout changes
    String format(Invoice inv) { /* build the text / PDF */ return "..."; }
}

interface InvoiceRepository { void save(Invoice inv); }

class JdbcInvoiceRepository implements InvoiceRepository {
    public void save(Invoice inv) { /* INSERT ... */ }
}

O — Open/Closed Principle

Software entities should be open for extension, closed for modification. If adding a new shape, payment type, or export format means editing an existing switch, that switch is a magnet for bugs and merge conflicts. Push the varying behaviour behind an interface so new cases are new classes.

❌ Bad — every new shape edits AreaCalculator

class AreaCalculator {
    double area(Object shape) {
        if (shape instanceof Circle c)       return Math.PI * c.r * c.r;
        else if (shape instanceof Square s)  return s.side * s.side;
        // add Triangle? edit this method, re-test everything here
        throw new IllegalArgumentException("unknown shape");
    }
}

✅ Good — new shape = new class, calculator untouched

interface Shape { double area(); }

record Circle(double r) implements Shape {
    public double area() { return Math.PI * r * r; }
}
record Square(double side) implements Shape {
    public double area() { return side * side; }
}
record Triangle(double b, double h) implements Shape {   // added later, nothing else changes
    public double area() { return 0.5 * b * h; }
}

class AreaCalculator {
    double totalArea(List<Shape> shapes) {
        return shapes.stream().mapToDouble(Shape::area).sum();
    }
}

L — Liskov Substitution Principle

A subtype must be usable anywhere its supertype is expected, without surprising the caller. The famous violation: Square extends Rectangle. A square must keep width == height, so it has to override the setters — and now code that "sets width to 5, height to 4, expects area 20" breaks when handed a Square. The inheritance models "is-a" in English but not in behaviour.

❌ Bad — Square breaks Rectangle's contract

class Rectangle {
    protected int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(int w)  { this.width = w; this.height = w; }
    @Override void setHeight(int h) { this.width = h; this.height = h; }
}

void resizeAndCheck(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;      // passes for Rectangle, FAILS for Square (gives 16)
}

✅ Good — no false is-a; share the abstraction, not the setters

interface Shape { int area(); }

final class Rectangle implements Shape {
    private final int width, height;
    Rectangle(int w, int h) { this.width = w; this.height = h; }
    public int area() { return width * height; }
}

final class Square implements Shape {
    private final int side;
    Square(int side) { this.side = side; }
    public int area() { return side * side; }
}
// Immutable + no inheritance between them => no contract to violate.

I — Interface Segregation Principle

No client should be forced to depend on methods it doesn't use. A fat interface makes every implementer carry stubs that throw UnsupportedOperationException — and callers can't tell from the type which methods are real. Split it along the lines of who calls what.

❌ Bad — an old printer forced to implement scan/fax

interface MultiFunctionDevice {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
}

class OldPrinter implements MultiFunctionDevice {
    public void print(Document d) { /* real */ }
    public void scan(Document d)  { throw new UnsupportedOperationException(); }
    public void fax(Document d)   { throw new UnsupportedOperationException(); }
}

✅ Good — small role interfaces, compose as needed

interface Printer { void print(Document d); }
interface Scanner { void scan(Document d); }
interface Fax     { void fax(Document d); }

class OldPrinter implements Printer {
    public void print(Document d) { /* real */ }
}

class WorkgroupMFD implements Printer, Scanner, Fax {
    public void print(Document d) { /* ... */ }
    public void scan(Document d)  { /* ... */ }
    public void fax(Document d)   { /* ... */ }
}

D — Dependency Inversion Principle

High-level policy should not depend on low-level details; both depend on an abstraction. When a service news its collaborators directly, you can't swap the transport, can't unit-test without hitting the network, and a change to the low-level class ripples upward. Depend on an interface and inject the implementation.

❌ Bad — policy welded to a concrete sender

class OrderService {
    private final SmtpEmailClient email = new SmtpEmailClient();  // hard-wired

    void placeOrder(Order o) {
        // ... save order ...
        email.sendSmtp(o.getCustomerEmail(), "Order confirmed #" + o.getId());
    }
}

✅ Good — depend on an abstraction, inject it

interface NotificationSender { void send(String to, String message); }

class EmailSender implements NotificationSender {
    public void send(String to, String msg) { /* SMTP */ }
}
class SmsSender implements NotificationSender {
    public void send(String to, String msg) { /* provider API */ }
}

class OrderService {
    private final NotificationSender sender;
    OrderService(NotificationSender sender) { this.sender = sender; }   // injected

    void placeOrder(Order o) {
        // ... save order ...
        sender.send(o.getContact(), "Order confirmed #" + o.getId());
    }
}
// Tests pass a FakeNotificationSender; prod wires EmailSender or a composite.

Design patterns

Ten patterns cover the vast majority of LLD rounds. For each: what it is in two lines, a trigger scenario (the concrete situation that should make you reach for it), a compact Java example, and the probe an interviewer uses to check you actually understand the trade-off rather than the name.

Singleton — Creational

Guarantees a class has exactly one instance and gives a global access point to it. Use sparingly: it's a global variable with a nicer name, and it makes testing harder because callers can't substitute a fake.

Trigger scenario

You have exactly one of something physical or expensive and everyone must share it: an in-memory app config, a connection pool, a metrics registry, a hardware driver handle. Creating a second one would be wrong, not just wasteful.

Java — enum singleton (thread-safe, serialization-safe, no reflection attack)

enum ConfigManager {
    INSTANCE;

    private final Map<String, String> settings = new ConcurrentHashMap<>();

    public String get(String key)            { return settings.get(key); }
    public void   set(String key, String v)  { settings.put(key, v); }
}

// usage
ConfigManager.INSTANCE.set("region", "ap-south-1");

// If you need lazy init with a class: double-checked locking
class ConnectionPool {
    private static volatile ConnectionPool instance;
    private ConnectionPool() { /* open sockets */ }

    static ConnectionPool getInstance() {
        if (instance == null) {                       // 1st check (no lock)
            synchronized (ConnectionPool.class) {
                if (instance == null)                 // 2nd check (with lock)
                    instance = new ConnectionPool();
            }
        }
        return instance;
    }
}
Interviewer probe

"Is your version thread-safe?" (eager holder / enum yes; naive lazy no). "Why volatile in double-checked locking?" (stop other threads seeing a half-constructed object). "How do you test a class that calls this?" — the honest answer is you inject it as a dependency instead of calling getInstance() everywhere, which is why many teams avoid the pattern and let a DI container manage the single instance.

Factory — Creational

Moves the new decision into one place so callers ask for what they want, not how it's built. "Simple factory" is a static method with a switch; "Factory Method" defers the choice to a subclass; "Abstract Factory" produces families of related objects.

Trigger scenario

Which concrete class to instantiate depends on runtime input — a "UPI" / "CARD" string from a request, a file extension, an OS — and that if/switch would otherwise be copy-pasted at every call site.

Java — simple factory for payment processors

interface PaymentProcessor { void pay(long amountPaise); }

class UpiProcessor  implements PaymentProcessor { public void pay(long a) { /* ... */ } }
class CardProcessor implements PaymentProcessor { public void pay(long a) { /* ... */ } }
class WalletProcessor implements PaymentProcessor { public void pay(long a) { /* ... */ } }

class PaymentProcessorFactory {
    static PaymentProcessor create(PaymentMethod method) {
        return switch (method) {
            case UPI    -> new UpiProcessor();
            case CARD   -> new CardProcessor();
            case WALLET -> new WalletProcessor();
        };
    }
}

// caller
PaymentProcessor p = PaymentProcessorFactory.create(request.getMethod());
p.pay(request.getAmount());
Interviewer probe

"Doesn't the switch still violate OCP?" — yes, the factory is the one place that changes; alternatively register suppliers in a Map<PaymentMethod, Supplier<PaymentProcessor>> so adding a type is a map entry. "Factory Method vs Abstract Factory?" — Factory Method = one product, chosen by subclass; Abstract Factory = a set of products that must be consistent (e.g. all "dark theme" widgets).

Builder — Creational

Constructs a complex object step by step, then hands back an immutable result. Replaces telescoping constructors (new Pizza(12, true, false, true, 2, ...)) and half-initialised objects from a pile of setters.

Trigger scenario

An object has many fields, several optional, some with defaults, and you want it immutable and validated once it's built — HTTP requests, DB queries, config objects, a Notification with optional cc / attachments / priority.

Java — nested static Builder

class HttpRequest {
    private final String url;            // required
    private final String method;         // required
    private final Map<String, String> headers;
    private final String body;           // optional
    private final int timeoutMs;         // optional, defaulted

    private HttpRequest(Builder b) {
        this.url = b.url; this.method = b.method;
        this.headers = b.headers; this.body = b.body; this.timeoutMs = b.timeoutMs;
    }

    static class Builder {
        private final String url;
        private final String method;
        private Map<String, String> headers = new HashMap<>();
        private String body = null;
        private int timeoutMs = 5000;

        Builder(String url, String method) { this.url = url; this.method = method; }

        Builder header(String k, String v) { headers.put(k, v); return this; }
        Builder body(String b)             { this.body = b; return this; }
        Builder timeoutMs(int t)           { this.timeoutMs = t; return this; }

        HttpRequest build() {
            if (url == null || method == null) throw new IllegalStateException("url/method required");
            return new HttpRequest(this);
        }
    }
}

HttpRequest r = new HttpRequest.Builder("https://api.example.com/orders", "POST")
        .header("Content-Type", "application/json")
        .body("{\"id\":42}")
        .timeoutMs(2000)
        .build();
Interviewer probe

"Why not just setters?" — the object is never in a partially-built, mutable state; required fields are enforced by the builder constructor; the result can be final and thread-safe. "When is it overkill?" — 2–3 fields, all required: just use a constructor or a record.

Adapter — Structural

Wraps a class so its interface matches what your code expects. The classic "translate between two incompatible APIs" move.

Trigger scenario

You designed to an interface (PaymentGateway) and now must plug in a third-party SDK whose method names and types are completely different, and you can't (or don't want to) change either side.

Java — adapting a third-party SDK to your interface

// your app's expectation
interface PaymentGateway { PaymentResult charge(String customerId, long amountPaise); }

// the vendor SDK you can't modify
class StripeClient {
    Charge createCharge(int amountCents, String currency, String source) { /* ... */ }
}

class StripeGatewayAdapter implements PaymentGateway {
    private final StripeClient stripe;
    StripeGatewayAdapter(StripeClient stripe) { this.stripe = stripe; }

    public PaymentResult charge(String customerId, long amountPaise) {
        int cents = (int) (amountPaise / 100 * 100);          // translate units
        Charge c = stripe.createCharge(cents, "inr", customerId);
        return new PaymentResult(c.getId(), c.getStatus().equals("succeeded"));
    }
}
Interviewer probe

"Adapter vs Facade?" — Adapter changes an interface to match an existing expectation (1:1, no new behaviour); Facade invents a new simpler interface over many classes. "Object adapter vs class adapter?" — object adapter holds a reference (composition, flexible); class adapter extends the adaptee (needs multiple inheritance, rare in Java).

Decorator — Structural

Wraps an object to add behaviour at runtime without touching the class or exploding the subclass count. Each decorator implements the same interface and delegates to the thing it wraps.

Trigger scenario

You need combinations of optional features — a coffee with milk + caramel + extra shot, a data stream that is buffered + compressed + encrypted — and one subclass per combination would be dozens of classes. java.io (new BufferedReader(new InputStreamReader(...))) is the canonical example.

Java — beverage cost with stackable add-ons

interface Beverage { String description(); int costPaise(); }

class Espresso implements Beverage {
    public String description() { return "Espresso"; }
    public int costPaise() { return 15000; }
}

abstract class AddOn implements Beverage {
    protected final Beverage base;
    AddOn(Beverage base) { this.base = base; }
}

class Milk extends AddOn {
    Milk(Beverage b) { super(b); }
    public String description() { return base.description() + " + Milk"; }
    public int costPaise() { return base.costPaise() + 2000; }
}

class Caramel extends AddOn {
    Caramel(Beverage b) { super(b); }
    public String description() { return base.description() + " + Caramel"; }
    public int costPaise() { return base.costPaise() + 3000; }
}

Beverage order = new Caramel(new Milk(new Espresso()));
// "Espresso + Milk + Caramel", 20000 paise
Interviewer probe

"Decorator vs inheritance?" — inheritance fixes the combination at compile time; decorators compose at runtime and in any order. "Decorator vs Strategy?" — Strategy swaps one algorithm via a plugged-in object; Decorator layers many wrappers, each adding a slice of behaviour. Watch out for lots of tiny classes and hard-to-read stack traces.

Facade — Structural

A single class that gives a simple entry point to a complicated subsystem, so callers don't have to orchestrate five collaborators in the right order.

Trigger scenario

"Place an order" really means: reserve inventory, authorise payment, create a shipment, send a confirmation — and every caller currently wires those four services together themselves. One OrderFacade.placeOrder() hides the choreography.

Java — one method over a multi-step flow

class OrderFacade {
    private final InventoryService inventory;
    private final PaymentService payment;
    private final ShippingService shipping;
    private final NotificationSender notifier;

    OrderFacade(InventoryService i, PaymentService p, ShippingService s, NotificationSender n) {
        this.inventory = i; this.payment = p; this.shipping = s; this.notifier = n;
    }

    OrderResult placeOrder(Cart cart, PaymentDetails pd, Address addr) {
        inventory.reserve(cart.getItems());
        PaymentResult pr = payment.authorize(pd, cart.total());
        if (!pr.success()) { inventory.release(cart.getItems()); return OrderResult.failed(pr.reason()); }
        Shipment sh = shipping.schedule(cart.getItems(), addr);
        notifier.send(cart.getCustomerContact(), "Order confirmed, arriving " + sh.getEta());
        return OrderResult.ok(sh.getTrackingId());
    }
}
Interviewer probe

"Does the facade forbid using the subsystem directly?" — no, it's a convenience, not a wall; advanced callers can still talk to PaymentService. "Facade vs Mediator?" — Facade is one-way (caller → subsystem); Mediator sits between peers that talk back and forth. Risk: the facade becomes a god object — keep it to orchestration, no business rules of its own.

Observer — Behavioral

Defines a one-to-many dependency: when the subject's state changes, all registered observers are notified. Decouples "something happened" from "who cares".

Trigger scenario

Multiple, independently-evolving reactions to one event: a stock price tick updates a chart, a ticker, and an alert rule; an order status change emails the customer, updates analytics, and notifies the warehouse. You don't want the subject importing all of them.

Java — subject with register / notify

interface OrderObserver { void onStatusChanged(Order o, OrderStatus from, OrderStatus to); }

class Order {
    private final List<OrderObserver> observers = new CopyOnWriteArrayList<>();
    private OrderStatus status = OrderStatus.CREATED;

    void subscribe(OrderObserver o)   { observers.add(o); }
    void unsubscribe(OrderObserver o) { observers.remove(o); }

    void setStatus(OrderStatus next) {
        OrderStatus prev = this.status;
        this.status = next;
        for (OrderObserver o : observers) o.onStatusChanged(this, prev, next);
    }
}

class EmailNotifier implements OrderObserver {
    public void onStatusChanged(Order o, OrderStatus from, OrderStatus to) {
        if (to == OrderStatus.SHIPPED) { /* send "your order shipped" */ }
    }
}
class WarehouseListener implements OrderObserver { /* ... */ }
Interviewer probe

"Push or pull?" — push passes the changed data in the callback; pull passes only the subject and lets observers query what they need. "Memory leak risk?" — observers that never unsubscribe keep the subject alive (lapsed-listener); use weak references or explicit lifecycle. "Synchronous notify blocks the setter" — hand off to a queue / executor if observers are slow. This is the guts of any event bus / pub-sub.

Strategy — Behavioral

Encapsulates interchangeable algorithms behind one interface and lets the caller pick at runtime. The antidote to a method that's one big switch over "mode".

Trigger scenario

Several ways to do the same job and the choice varies per call or per config: pricing rules (regular / member / surge), route planning (shortest / cheapest / scenic), compression (gzip / brotli / none), parking fees by vehicle type.

Java — pluggable pricing

interface PricingStrategy { long priceFor(Ride ride); }

class RegularPricing implements PricingStrategy {
    public long priceFor(Ride r) { return 5000 + r.getKm() * 1200; }
}
class SurgePricing implements PricingStrategy {
    private final double multiplier;
    SurgePricing(double m) { this.multiplier = m; }
    public long priceFor(Ride r) { return (long) ((5000 + r.getKm() * 1200) * multiplier); }
}

class FareCalculator {
    private PricingStrategy strategy;
    FareCalculator(PricingStrategy s) { this.strategy = s; }
    void setStrategy(PricingStrategy s) { this.strategy = s; }   // swap at runtime
    long fare(Ride ride) { return strategy.priceFor(ride); }
}
Interviewer probe

"Strategy vs State?" — same structure, different intent: with Strategy the client chooses and it rarely changes mid-flight; with State the object transitions itself between states. "Isn't a lambda enough?" — yes for a single method with no config; promote to a class when the strategy has its own fields or multiple methods. "How is the strategy selected?" — often a small factory / map keyed by an enum.

State — Behavioral

Lets an object change its behaviour when its internal state changes, by delegating to a state object instead of checking flags everywhere. Each state class knows what's allowed and which state comes next.

Trigger scenario

An entity has a lifecycle where the same action means different things per stage and many actions are illegal in most stages: a vending machine, an ATM session, a document (draft → in review → published), an order (created → paid → shipped → delivered / cancelled).

Java — vending machine states

interface VendingState {
    void insertCoin(VendingMachine m, int paise);
    void selectItem(VendingMachine m, String code);
    void dispense(VendingMachine m);
}

class IdleState implements VendingState {
    public void insertCoin(VendingMachine m, int paise) {
        m.addBalance(paise);
        m.setState(new HasMoneyState());
    }
    public void selectItem(VendingMachine m, String c) { throw new IllegalStateException("insert coin first"); }
    public void dispense(VendingMachine m)             { throw new IllegalStateException("nothing selected"); }
}

class HasMoneyState implements VendingState {
    public void insertCoin(VendingMachine m, int paise) { m.addBalance(paise); }
    public void selectItem(VendingMachine m, String code) {
        if (m.priceOf(code) <= m.getBalance()) m.setState(new DispensingState(code));
        else throw new IllegalStateException("insufficient balance");
    }
    public void dispense(VendingMachine m) { throw new IllegalStateException("select an item"); }
}

class VendingMachine {
    private VendingState state = new IdleState();
    void setState(VendingState s) { this.state = s; }
    void insertCoin(int p) { state.insertCoin(this, p); }
    void selectItem(String c) { state.selectItem(this, c); }
    void dispense() { state.dispense(this); }
    // + addBalance / getBalance / priceOf ...
}
Interviewer probe

"Who owns the transitions?" — the state classes themselves here (each calls m.setState(...)); alternatively a central table. "State vs Strategy again?" — Strategy objects are usually stateless and externally chosen; State objects encode transition rules. "State explosion?" — if you have 8 states × 6 events, consider a transition table or a small state-machine library rather than 8 classes.

Chain of Responsibility — Behavioral

Passes a request along a chain of handlers; each either handles it or forwards it. Decouples the sender from knowing which handler will act.

Trigger scenario

A request must go through an ordered series of checks / processors, any of which might stop it or pass it on: expense approval by amount (manager → director → VP → CFO), servlet filters / middleware, logging levels, a support-ticket escalation ladder.

Java — expense approval ladder

abstract class Approver {
    protected Approver next;
    Approver linkTo(Approver next) { this.next = next; return next; }

    void handle(ExpenseRequest req) {
        if (canApprove(req)) approve(req);
        else if (next != null) next.handle(req);
        else throw new IllegalStateException("no approver for " + req.amount());
    }
    protected abstract boolean canApprove(ExpenseRequest req);
    protected abstract void approve(ExpenseRequest req);
}

class Manager extends Approver {
    protected boolean canApprove(ExpenseRequest r) { return r.amount() <= 50_000_00; }
    protected void approve(ExpenseRequest r) { /* stamp APPROVED by manager */ }
}
class Director extends Approver {
    protected boolean canApprove(ExpenseRequest r) { return r.amount() <= 5_00_000_00; }
    protected void approve(ExpenseRequest r) { /* ... */ }
}
class CFO extends Approver {
    protected boolean canApprove(ExpenseRequest r) { return true; }
    protected void approve(ExpenseRequest r) { /* ... */ }
}

Approver chain = new Manager();
chain.linkTo(new Director()).linkTo(new CFO());
chain.handle(new ExpenseRequest(2_00_000_00));   // Director approves
Interviewer probe

"What if nobody handles it?" — decide explicitly: throw, or have a guaranteed catch-all at the tail. "Can a handler do work and pass on?" — yes (that's the filter/middleware variant: pre-process, call next, post-process). "How is order decided?" — it's part of the config; the wrong order is a common bug.

Classic LLD problems

Each problem below is a walkthrough, not full code: the key classes and their one-line responsibility, the pattern(s) that fit, and the trade-off the interviewer will probe. Do the exercise of writing your own class list first — the gap between yours and this is the lesson.

Parking Lot

Scope to state up front: multiple floors, spot sizes (motorcycle / compact / large), hourly pricing, entry/exit gates with tickets. Park the rest (monthly passes, EV charging, license-plate OCR).

Key classes & responsibilities

ParkingLot          — singleton; holds floors; entry point park()/unpark()
ParkingFloor        — owns a list of ParkingSpot; can find a free spot by size
ParkingSpot         — one physical spot; type, isFree, currentVehicle
Vehicle (abstract)  — Car / Motorcycle / Truck; each maps to a required SpotType

LRU Cache

Scope: fixed capacity, get and put both O(1), evict the least-recently-used entry on overflow.

Key classes & responsibilities

LRUCache<K,V>   — capacity, get(K), put(K,V)
Node<K,V>      — key, value, prev, next (doubly linked)
HashMap<K, Node>— O(1) lookup from key to its node
Doubly linked list — order by recency; head = most recent, tail = LRU
  · on get/put: unlink the node, move it to head
  · on overflow: remove tail node, also remove its key from the map
EvictionPolicy (optional) — make LRU / LFU / FIFO pluggable

Java — the core moves

class LRUCache<K,V> {
    private final int capacity;
    private final Map<K, Node<K,V>> map = new HashMap<>();
    private final Node<K,V> head = new Node<>(null, null); // sentinels
    private final Node<K,V> tail = new Node<>(null, null);

    LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail; tail.prev = head;
    }

    V get(K key) {
        Node<K,V> n = map.get(key);
        if (n == null) return null;
        moveToFront(n);
        return n.value;
    }

    void put(K key, V value) {
        Node<K,V> n = map.get(key);
        if (n != null) { n.value = value; moveToFront(n); return; }
        if (map.size() == capacity) {
            Node<K,V> lru = tail.prev;
            unlink(lru); map.remove(lru.key);
        }
        Node<K,V> fresh = new Node<>(key, value);
        map.put(key, fresh); insertFront(fresh);
    }

    private void moveToFront(Node<K,V> n) { unlink(n); insertFront(n); }
    private void unlink(Node<K,V> n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void insertFront(Node<K,V> n) {
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
    static class Node<K,V> { K key; V value; Node<K,V> prev, next;
        Node(K k, V v) { key = k; value = v; } }
}
Interviewer probe

Why the doubly linked list? a singly linked list can't unlink a middle node in O(1). Shortcut: LinkedHashMap with accessOrder=true and an overridden removeEldestEntry — mention it, then show you can build it by hand. Thread safety: wrap in a lock, or segment the cache; a fully lock-free LRU is hard. Extension: pull eviction behind an interface so LFU / TTL drop in.
